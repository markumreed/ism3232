Write the Functions

Teaching goal: four business-rule functions, each with a docstring, type hints, and a return — genuinely new syntax (type hints) combined with the "functions return, they don't print" discipline stated up front. Say to the class (verbatim): "Four functions. Every single one needs three things: a docstring explaining what it does, type hints on its parameters and return value, and a return statement — never a print(). Watch for that last rule specifically as we go." Line-by-line: APPROVAL_LIMIT = 1000 — Week 6's named-constant convention, now at the module level, available to every function in the file without being passed as a parameter. def calculate_total(price: float, quantity: int) -> float: — type hints, new syntax today: price: float annotates the expected argument type, -> float the expected return type; Python does not enforce these at runtime — they are documentation, for humans and for external tools (linters, IDEs). """Return total cost including 7% tax.""" — a docstring, a string literal immediately after the def line, retrievable with help(calculate_total) and shown by editor hover tooltips. return price * quantity * 1.07 — the whole body is one line, and it's a return, never a print(): "if I wanted to see this value, I do that in main.py." get_approval_tier — the richest function, an if/elif/else chain classifying an amount into three string tiers; the single-line branch bodies (if amount <= 500: return 'auto') are a valid but unusual style — the conventional multi-line form is equally fine. apply_discount — pct is a percentage on a 0–100 scale (documented in the docstring, since "0 to 100" isn't a Python type): apply_discount(100.00, 10) means "10%", computed as price * (1 - pct/100) = 90.0. Common mistakes: adding a print() inside a function "just to check it's working" and forgetting to remove it — walk the room checking for this; suggest calling the function from the REPL instead. Confusing the boundary logic in get_approval_tier — <=500 and <=2000 are inclusive. Forgetting type hints, or applying them inconsistently. Check for understanding (asked at the end of this part): "Without running it, what does get_approval_tier(500) return — exactly at the first boundary?" Answer: 'auto' — since the check is <= 500, inclusive; a direct preview of Part 4's test_tier_boundary_500.

The idea

Concept

Every function needs three things: a docstring (a string literal right after def, describing what it does), type hints (price: float on parameters, -> float on the return), and a return — never a print().

Type hints are not enforced at runtime. calculate_total('bad', 'input') wouldn't raise just from the hints — they're documentation, for humans and for tools (linters, IDEs) that check them separately. Worth using anyway: they make a function's contract readable without opening its body.

APPROVAL_LIMIT = 1000 lives at the module level, above every function — so any function that needs it can read it without it being passed as a parameter.

The single-line if/elif/else bodies in get_approval_tier are a valid but unusual compact style; the conventional multi-line form (each return on its own indented line) is equally correct and a student's preference for it is completely fine. apply_discount's pct is on a 0–100 scale, documented in the docstring because "0 to 100" isn't expressible as a Python type — a student who passed 0.10 instead of 10 would get a wildly, non-obviously wrong result.

Part 4 · 0:38–0:58

Eight pytest Tests — boundary cases

Teaching goal: write eight tests, including at least two genuine boundary cases — testing the exact edge where a rule's behavior changes, not just an obviously-true and obviously-false case. Say to the class (verbatim): "Eight tests, and I want to spend real time on two of them specifically — the boundary tests. A boundary case tests the exact edge of a rule, where behavior flips. For a threshold of 1000, that's testing with exactly 1000, not just a comfortably-above or comfortably-below number. This is where the most dangerous real bugs actually hide — an off-by-one in a threshold check, a > where you meant >=." Line-by-line: from business_rules import ... — tests import the module under test exactly the same way any other code would. test_total_includes_tax — round(calculate_total(100.00, 2), 2) == 214.00; the round(..., 2) is a Week 5 floating-point precaution (raw binary float may not land on an exact 214.00). test_requires_review_over / test_requires_review_under — the two "obviously true / obviously false" cases; not sufficient testing on their own. test_boundary_at_limit — the featured boundary case: requires_review(1000) should be False, since the condition is amount > APPROVAL_LIMIT (strictly greater), not >=. If a developer had written >= by mistake, both "obvious" tests would still pass — only this boundary test catches it. test_tier_boundary_500 — the second required boundary case: 500 itself (inclusive) lands in 'auto'. test_discount_ten — plain ==, no round(): 100.00 * (1 - 10/100) happens to compute to an exact 90.0 here; floating-point precision issues are input-dependent, not universal. Live demo, if time: change requires_review's > to >=, re-run pytest -v — test_boundary_at_limit fails, every other test still passes — then revert. Common mistakes: treating requires_review(1500) is True as risky chained-comparison syntax per Week 5 — reassure: it's a single function call evaluated first, then compared with is True; the Week 5 hazard was chaining a comparison operator directly against is in one expression. Writing only "obviously true/false" tests and skipping genuine boundary cases. Check for understanding (asked at the end of this part): "For get_approval_tier's second threshold, at 2000, what boundary test would you write, and what should it assert?" Answer: assert get_approval_tier(2000) == 'manager' — since the condition is <= 2000, inclusive.

The idea

Concept

A boundary case tests the exact edge of a rule, where behavior flips. For a threshold of 1000, that means testing with exactly 1000 — not a comfortably-above or comfortably-below number.

test_requires_review_over (1500 → True) and test_requires_review_under (500 → False) are the "obvious" cases. If a developer wrote >= instead of >, both would still pass. Only test_boundary_at_limit — requires_review(1000) is False — catches that specific mistake.

This is the single most important idea in the lab: comfortable, clearly-true/false tests can give false confidence; boundary tests catch the bugs that actually matter — an off-by-one, a > where you meant >=.

test_total_includes_tax wraps its call in round(..., 2) as a Week 5 floating-point precaution; test_discount_ten uses a bare == because 100.00 * (1 - 10/100) happens to land on an exact 90.0 — precision issues are input-dependent, not universal. requires_review(1500) is True is safe: the function call is evaluated first, then compared with is True — not the Week 5 chained-comparison hazard.

Type the tests as provided — tests/test_business_rules.py

from business_rules import calculate_total, requires_review, get_approval_tier, apply_discount

def test_total_includes_tax():
    assert round(calculate_total(100.00, 2), 2) == 214.00

def test_requires_review_over():
    assert requires_review(1500) is True

def test_requires_review_under():
    assert requires_review(500) is False

def test_boundary_at_limit():
    # Exactly at 1000 should NOT require review (> not >=)
    assert requires_review(1000) is False

def test_tier_auto():
    assert get_approval_tier(400) == 'auto'

def test_tier_boundary_500():
    assert get_approval_tier(500) == 'auto'  # exactly at limit

def test_tier_manager():
    assert get_approval_tier(1500) == 'manager'

def test_discount_ten():
