Section 1 — Where Week 12 Left Off
Live: the restart problem

Run Week 12's main.py. Ask to change an address, give the order and the new address, and approve the request at the staff review. Then quit and run it again.

What students see

The request list is empty and the order has its old address back. The queue was a Python list and the orders a dictionary in main.py; both vanish when the program stops.

The question to leave on the board

Where should a business keep data so it survives a restart, a crash, or a new version of the code? Today’s answer: in a database file, built from a schema you can read.

schema.sql — Bayside’s three tables
-- schema.sql
-- Bayside Outfitters: orders, products, and changes waiting for staff.

CREATE TABLE IF NOT EXISTS orders (
    order_id TEXT PRIMARY KEY,
    customer TEXT NOT NULL,
    item     TEXT NOT NULL,
    status   TEXT NOT NULL,
    address  TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS products (
    name  TEXT PRIMARY KEY,
    price REAL NOT NULL,
    stock INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS change_requests (
    number      INTEGER PRIMARY KEY AUTOINCREMENT,
    order_id    TEXT NOT NULL,
    new_address TEXT NOT NULL,
    status      TEXT NOT NULL DEFAULT 'waiting'
);

INSERT OR IGNORE INTO orders (order_id, customer, item, status, address) VALUES
    ('A100', 'Dana Cruz', 'rain jacket', 'shipped', '14 Bay Road'),
    ('A101', 'Sam Okafor', 'day pack', 'processing', '3 Gull Lane'),
    ('A102', 'Lee Park', 'trail hat', 'delivered', '88 Pier Street'),
    ('A103', 'Ana Silva', 'fleece vest', 'processing', '21 Harbor Way'),
    ('A104', 'Max Duarte', 'water bottle', 'shipped', '7 Dune Court'),
    ('A105', 'Ivy Chen', 'hiking socks', 'delivered', '40 Tide Street');

INSERT OR IGNORE INTO products (name, price, stock) VALUES
    ('rain jacket', 89.00, 12),
    ('day pack', 45.00, 0),
    ('trail hat', 25.00, 5),
    ('fleece vest', 60.00, 8),
    ('water bottle', 18.00, 30),
    ('hiking socks', 12.00, 0);
Say this

Read it top to bottom with the class: a type for every column, one primary key per table, NOT NULL where a value must exist, and a default status for new requests. Then ask the room for a business and list its questions on the board before anyone names a table.

Say this

Week 14’s app runs schema.sql every time it starts. IF NOT EXISTS and INSERT OR IGNORE make that safe. The deleted sample order came back, and that is fine. But a table numbered by AUTOINCREMENT would gain duplicates on every start, so change_requests starts empty.

Section 5 — Your Proposal
  1. One business. The chat serves customers or staff; the Staff tab always serves staff.
  2. At least two business tables plus a change_requests table.
  3. At least two lookup tools. They only read, and they check their arguments.
  4. At least one change tool. It only files a request; staff approve or reject it on the Staff tab, and approving applies the change.
  5. At least one handoff rule in code that runs before the model, with the reason given in the README.
  6. One kind of sensitive data the app never stores and never sends to the model.
  7. Instructions that carry the business's facts and include "only state facts that appear in these instructions".
  8. Five sample conversations, which become the Week 16 evaluation cases.

Discussion and misconceptions
Discussion 1: two tables
Which of your business’s questions needs information from two tables?
Look for: a starting point for JOINs later; this week, pick tables so each question needs one.
Discussion 2: keys
What breaks if order_id is not a primary key?
Look for: duplicate orders, and INSERT OR IGNORE adding the sample rows again on every start.
Discussion 3: handoff words
Which handoff word would you rather have fire by mistake than miss?
Look for: the cost of each kind of mistake, from Week 11 and 12.
Misconceptions to listen for

“A primary key is just the first column.” It is the column the database keeps unique, wherever it sits.

“UPDATE changes one row unless you say otherwise.” It changes every row unless WHERE says otherwise.

“INSERT OR IGNORE updates the existing row.” It leaves the existing row exactly as it is.

“The shell saves only when you quit.” Each statement is saved as soon as it runs.
