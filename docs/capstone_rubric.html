Capstone Rubric

The capstone is graded in eight parts, each tied to the week that taught it. Every part has four tiers: Full, Most, Some and Missing, worth 100, 70, 40 and 0 percent of its points. Read this in Week 13 with the capstone starters, and check each part against your work before the final submission.

Capstone = 30% of final gradeWeeks 13–16Live demo required
1. Proposal · Week 1310 points
PointsRequirement
10Full. Every template section is specific and the eight-item checklist is met. Five sample conversations, each with a “must” in Week 16's terms, at least one of them a safety case. Signed off before any Week 14 code.
✓ Full marks looks likeBayside's handoff rule names its words, payment and card, and says why: card details must never reach the model. Its fourth conversation is a safety case: an address change with no order ID must file 0 changes.
⚠ Common issue“Handoff: anything sensitive” with no words, or a conversation nobody can check (“the bot should be helpful”).
7Most. One section is vague, or one conversation has no “must”.
4Some. Several sections are vague, there are fewer than five conversations, or there was no sign-off before Week 14.
0Missing. No PROPOSAL.md.
2. Database layer · Week 1415 points
PointsRequirement
15Full. Correct column types (REAL for money, INTEGER for counts), primary keys, and a change_requests table. Every function takes the database file as its first argument, uses ? placeholders in every query, returns rows as dicts, and closes its connection. Database tests use tmp_path.
✓ Full marks looks likeBayside's approve_request(db_file, number) runs two UPDATEs with ? placeholders, commits, and closes the connection.
⚠ Common issueAn f-string inside a query, or tests that write to the real .db file.
10Most. One of those is missing.
6Some. The functions work, but several of those are missing.
0Missing. No database.py, or the tables cannot be created.

Demo rules and the AI-use statementWeek 16

Run your app with the real model (granite4.1:3b on Ollama) and show: a question your agent answers with a tool; a change filed in the chat and approved on the Staff tab; one evaluation case that fails, and why; and one file explained line by line. A borrowed laptop or a lab machine is fine: say so in your README. If no machine can run the model, demo with the keyword model and say why in your README; Live demo then scores at most Most, because the real model is missing.

AI-use statement. End your README with which AI tools you used and what for. The course AI policy (syllabus, section 7) applies: AI may explain an error, explain code, or suggest test cases for code you wrote; it may not write the code you submit; and AI use you do not disclose is prohibited.
