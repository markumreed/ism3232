Section 1 — What a Language Model Is
It writes a likely continuation

A language model has read an enormous amount of text and learned which words tend to follow which. Give it some text and it writes what would probably come next. A chat is that trick applied to a conversation.

It is not a database

It does not look facts up. It writes text that sounds right, which is sometimes true and sometimes invented.

It has no memory

Every call starts from nothing. If earlier messages matter, you send them again.

Ollama

Ollama is a free program that downloads models and runs them on your own computer. Your Python code sends it a list of messages and gets a reply. The conversation never leaves the laptop, there is no account, and there is no API key.

first_chat.py — write together
# first_chat.py
# Author: [Your Name]

from ollama import chat

MODEL_NAME = "granite4.1:3b"

INSTRUCTIONS = """You are Sunny, a support assistant for Bayside Outfitters.
Answer in one short sentence."""

messages = [
    {"role": "system", "content": INSTRUCTIONS},
    {"role": "user", "content": "What are your store hours?"},
]

response = chat(model=MODEL_NAME, messages=messages)
print(response.message.content)
Three real runs of the same file
Run 1: Our store hours are Monday to Saturday, 9 AM to 9 PM, and Sunday, 12 PM to 6 PM.
Run 2: Our store hours are Monday to Friday, 9 AM to 9 PM, and Saturday, 9 AM to 6 PM.
Run 3: Our store hours are Monday to Saturday, 9:00 AM to 6:00 PM, and Sunday, 11:00 AM to 5:00 PM.
What to notice

The instructions never mention store hours. The model did not say so. It wrote three different, confident, invented answers.

Section 4 — The Model as a Part
mock_model.py — a stand-in that needs nothing installed
# mock_model.py
# Author: [Your Name]


class MockModel:
    """A stand-in for an AI model. It gives the same simple replies every time."""

    def reply(self, instructions, history):
        """Return a fixed reply based on the last message in the history."""
        last_message = history[-1]["content"].lower()
        if "hello" in last_message:
            return "Hello! How can I help you today?"
        return "I'm not sure how to help with that. I can check an order or stock."
ollama_model.py — the real one
# ollama_model.py
# Author: [Your Name]

from ollama import ResponseError, chat


class OllamaModel:
    """A real AI model that runs on this computer through Ollama."""

    def __init__(self, model_name):
        """Remember which model to ask."""
        self.model_name = model_name

    def reply(self, instructions, history):
        """Send the instructions and the conversation to the model. Return its reply."""
        messages = [{"role": "system", "content": instructions}]
        messages = messages + history
        try:
            response = chat(model=self.model_name, messages=messages)
        except ConnectionError:
            return None
        except ResponseError:
            return None
        return response.message.content
What to notice

Both classes have a method named reply that takes the instructions and the history. That is all the chatbot needs. It can be handed either one.

MockModel has no __init__, because it has nothing to remember.

messages = messages + history joins two lists: the instructions first, then the conversation.

No inheritance was needed. Two unrelated classes agree on one method.

Section 5 — Rules First, the Model for the Rest
chatbot.py — choose_reply and model_reply
    def choose_reply(self, user_message):
        """Use a rule when one applies. Otherwise ask the model."""
        text = user_message.lower()
        if self.needs_human(text):
            return "I can't help with that here. I'm passing you to a human agent."
        if "order" in text:
            return self.order_reply(user_message)
        if "stock" in text:
            return self.stock_reply(user_message)
        return self.model_reply()

    def model_reply(self):
        """Ask the model for a reply. Give a safe answer if the model has none."""
        reply = self.model.reply(self.instructions, self.history)
        if reply is None:
            return "Sorry, I can't answer that right now. Please try again in a moment."
        return reply

What to notice

Three replies came from the model: the greeting, the store hours, and the price-match question.

Three did not: the order and stock answers came from tools, and the address request never reached the model.

Code does the same thing every time, so it handles what must be right. The model handles language.

Section 6 — When the Model Fails
Ollama is not running: the last line of the traceback
ConnectionError: Failed to connect to Ollama. Please check that Ollama is downloaded, running and accessible. https://ollama.com/download
Without try
orders = {"A100": "shipped"}

print(orders["A999"])
print("The program keeps running.")
Output
Traceback (most recent call last):
  File "crash.py", line 3, in <module>
    print(orders["A999"])
          ~~~~~~^^^^^^^^
KeyError: 'A999'
With try and except
orders = {"A100": "shipped"}

try:
    print(orders["A999"])
except KeyError:
    print("No such order.")

print("The program keeps running.")
Output
No such order.
The program keeps running.
What to notice

try: starts code that might fail. except KeyError: names one error and says what to do if it happens. With no error, the except block is skipped.

Name the error you expect. Catching everything hides your own typos.

OllamaModel.reply returns None on failure, the same signal the tools give.

What stays in code

The instructions say 7 pm. A customer said 11 pm and the model agreed, five times out of five. Instructions help a great deal and they are not a guarantee.

Facts that matter come from tools. Actions that change something are decided in code or by a person. The model writes the sentences in between.

Discussion
Discussion 1: whose job is it?
The model invented store hours. Whose job is it to stop that: the model's, the instructions', or the code's?
Look for: the model cannot stop itself; instructions carry facts and reduce invention; code and tools supply what must be right.
Discussion 2: which replies would you send?
Look at the real conversation. Which replies would you let a shop send without checking, and which not?
Look for: the tool and rule replies are safe to send; a model reply about policy needs the fact to be in the instructions.
Discussion 3: the expensive mistake
Sunny agreed the store closes at 11 pm. What is the most expensive false statement a customer could get a chatbot to make?
Look for: refunds, prices, delivery dates, anything the business would have to honor or publicly refuse.
Discussion 4: local or online
This model runs on your laptop. What changes for a business that uses an online AI service?
Look for: customer messages leave the building; cost per use; an API key to protect; a more capable model.
Misconceptions to listen for
  • “The model knows our store.” It knows what the instructions tell it.
  • “It remembers me.” Your program resends the history.
  • “Good instructions make it safe.” They make it better. A customer talked it out of a fact.
  • “A mock model is cheating.” It is how you test a program whose real part is unpredictable.
  • “try fixes the error.” It decides what happens next. The cause is still there.
Where this goes next

The keyword rules are brittle: Has my package A101 shipped? misses the order rule, and Do you sell gift cards? trips the handoff. Next week the model decides when to use a tool, and you add checks around every tool call, an approval step for anything that changes something, and tests that use a fake model.
