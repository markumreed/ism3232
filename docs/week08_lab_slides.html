Set Up and Read the First Traceback

Teaching goal: copy a genuinely broken script exactly as given, run it, and read the resulting traceback methodically — bottom-up, extracting the error type, location, and meaning — before attempting any fix. Say to the class: "Type this exactly as shown — bugs included, on purpose. Do not fix anything yet. Run it, and we're going to read the error together, slowly, before touching a single line of code."

cd ~/ism3232/module05_functions source .venv/bin/activate touch week8_buggy.py debug_log.md

Shown for reference — source (venv activation) can't run in the browser. Reuse the module05_functions venv from Week 7. Then type the buggy script (next slide) into week8_buggy.py exactly as shown, bugs and all.

touch creates the two empty files; source .venv/bin/activate reuses Week 7's virtual environment.

Type this into week8_buggy.py exactly as shown — bugs included

# week8_buggy.py -- three bugs -- do not fix yet records = [ {'id': 1, 'name': 'Taylor', 'amout': 1200}, {'id': 2, 'name': 'Jordan', 'amount': 450}, {'id': 3, 'name': 'Morgan', 'amount': 3500}, ] def get_total(records): total = 0 for rec in records: total += rec['amount'] return total def is_over_limit(amount): return amount > '1000' def format_summary(total, count): return f'Total: ${total:.2f} across {count} records' total = get_total(records) print(format_summary(total, len(records))) print(is_over_limit(total))

Press Run. It crashes — that is the point. Read the traceback on the next slide before touching any code.

The three "bugs": record 1's key is misspelled 'amout' (Bug 1, a KeyError); is_over_limit compares to the string '1000' (Bug 2, a TypeError, only visible after Bug 1 is fixed); and the Stretch invites a third. Type it, do not paste — noticing your own typos is part of the skill.

Verified traceback

Traceback (most recent call last):
  File "week8_buggy.py", line 19, in <module>
    total = get_total(records)
            ^^^^^^^^^^^^^^^^^^
  File "week8_buggy.py", line 10, in get_total
    total += rec['amount']
             ~~~^^^^^^^^^^
KeyError: 'amount'

The load-bearing content is the last line: KeyError: 'amount'. Pyodide's file path shows <exec> and its line numbers may differ from the guide's week8_buggy.py line 10 / 19 — the guide's numbering is shown here; the error type and message are what matter.

Read it together, from the bottom up, exactly as the three questions ask: 1. "What is the error type on the last line?" — KeyError, specifically KeyError: 'amount'. 2. "Which file and line number is highlighted?" — week8_buggy.py, line 10, inside get_total(), at total += rec['amount']. The traceback shows a whole chain — line 19 (where get_total was called) and line 10 (where the actual failure happened) — both matter, but line 10 is where the bug physically lives. 3. "What does that error type mean?" — KeyError means: code tried to access a dictionary using a key ('amount') that doesn't exist in that specific dictionary. The error doesn't say the key is always missing — it says the key is missing from this specific dictionary, on this specific pass through the loop. Three records exist; only one is broken; the traceback alone doesn't tell you which — that's what Part 2's print() debugging is for. Common mistakes: reading the traceback top-down and getting stuck on the "Traceback (most recent call last):" boilerplate; skipping the rubber-duck step as "silly"; guessing at "what the error means" instead of decomposing KeyError: 'amount' literally.

Rubber duck it — genuinely, not as a formality

Technique

Explain get_total() out loud, to the duck, one line at a time. Not what it should do — what it literally does. "This line sets total to zero. This line starts a loop over records. This line adds rec['amount'] to total." Say it.

What you catch yourself hesitating on — "this adds the amount field… assuming it's called 'amount' in every record" — is the diagnostic insight arriving. That hesitation becomes your next two log entries.

# debug_log.md
# Author: [Your Name]

## Bug 1
Error type: KeyError
File + line: week8_buggy.py, line 10 (inside get_total)
What the error means: code tried to access a dictionary key
  ('amount') that doesn't exist in one of the records
What I told the duck: [student's own words]
What I tried: [to be filled in during Part 2]
How I fixed it: [to be filled in during Part 2]
Fill in the Bug 1 section of debug_log.md before touching any code. Circulate and listen for a student narrating rec['amount'] — "assuming it's called 'amount' in every record" is the actual insight; reinforce it if you hear it.

Knowledge check

The traceback names line 10, inside get_total(). Does that mean line 10 itself is wrong, or could the bug actually be somewhere else?

The bug could be — and in this case, is — somewhere else. Line 10's code is correct in general; the actual problem is in the data being fed into it, back at the typo'd 'amout' key. A traceback shows you where the failure was detected, not necessarily where the mistake was made.

Guide's Part 1 Check for understanding, verbatim answer. The distinction — failure detected vs mistake made — is the genuinely important takeaway.

Common pitfalls

Watch for

Reading the traceback top-down and getting stuck on the "Traceback (most recent call last):" line — that line is boilerplate, always identical, never the actual information. The real content is at the bottom.

Skipping the rubber-duck step as "silly" and going straight to fixing — the exercise's grading explicitly values the documented process; skipping it produces a thinner, less honest debug_log.md.

Guessing at "what the error means" rather than decomposing the literal words: KeyError, about the key 'amount' specifically.

This lab is graded on process, not just working code.
Part 2 · 0:18–0:30

Fix Bug 1 — the KeyError

Teaching goal: use print() debugging to inspect the actual data flowing through the loop, spot the typo, and fix it at its source. Say to the class: "The traceback told us where the failure happened, not why the data was wrong. Now we look at the data itself, directly, with a debug print."

Live-code — add one print() inside get_total()

records = [ {'id': 1, 'name': 'Taylor', 'amout': 1200}, {'id': 2, 'name': 'Jordan', 'amount': 450}, {'id': 3, 'name': 'Morgan', 'amount': 3500}, ] def get_total(records): total = 0 for rec in records: print(f'DEBUG: rec = {rec}') # add this total += rec['amount'] return total def format_summary(total, count): return f'Total: ${total:.2f} across {count} records' total = get_total(records) print(format_summary(total, len(records)))

Press Run. The DEBUG line prints once, then the same KeyError crashes it — but now you can see the record it choked on.

The DEBUG print shows each record's actual contents before the key access that was failing. This is the "inspect the data directly" step.

Verified output — before the crash

DEBUG: rec = {'id': 1, 'name': 'Taylor', 'amout': 1200}
Traceback (most recent call last):
  ...
KeyError: 'amount'

There it is, in plain sight: {'id': 1, 'name': 'Taylor', 'amout': 1200} — read the key names out loud. 'amout', not 'amount'. One missing letter.

Say explicitly, pointing at the printed dictionary: "A single missing letter, and Python has no way to know it was a typo rather than a deliberately different key — it just faithfully reports that 'amount' isn't there, because it genuinely isn't, under that exact spelling."

Fix it at the source — correct the typo in records, remove the DEBUG print

records = [ {'id': 1, 'name': 'Taylor', 'amount': 1200}, # fixed: was 'amout' {'id': 2, 'name': 'Jordan', 'amount': 450}, {'id': 3, 'name': 'Morgan', 'amount': 3500}, ] def get_total(records): total = 0 for rec in records: total += rec['amount'] return total def is_over_limit(amount): return amount > '1000' def format_summary(total, count): return f'Total: ${total:.2f} across {count} records' total = get_total(records) print(format_summary(total, len(records))) print(is_over_limit(total))

Bug 1 is fixed at the data source, not by matching the typo in the access. The DEBUG print is gone (Week 7's "no print() in business logic" rule). Press Run — a new, different error appears. That's Bug 2, which was always there, hidden behind Bug 1 crashing first.

Fixing the typo by changing rec['amount'] to rec['amout'] instead would "work" narrowly but breaks the moment any correctly-spelled record is processed — fix the data source, not the access point. Update debug_log.md's Bug 1 section: "What I tried: added a DEBUG print inside get_total() to see each record's actual contents…"; "How I fixed it: corrected the typo 'amout' to 'amount' in the first record's dictionary; removed the DEBUG print afterward."

Verified output — Bug 1 gone, Bug 2 surfaces

Total: $5150.00 across 3 records
Traceback (most recent call last):
  File "week8_buggy.py", line 21, in <module>
    print(is_over_limit(total))
          ^^^^^^^^^^^^^^^^^^^^
  File "week8_buggy.py", line 14, in is_over_limit
    return amount > '1000'
           ^^^^^^^^^^^^^^^
TypeError: '>' not supported between instances of 'int' and 'str'

The first line printed correctly — Total: $5150.00 across 3 records — confirming Bug 1's fix is solid. The crash is on the next line, in a completely different function. Load-bearing: TypeError: '>' not supported between instances of 'int' and 'str'.

Say explicitly: fixing one bug doesn't mean the whole program is correct — it means that specific bug is gone.

Knowledge check

If all three records had used 'amout' consistently — the same typo everywhere — would the original KeyError have looked any different?

No — it would still fail with the exact same KeyError: 'amount', on the very first record instead of just one specific one. The print() debugging step would have been just as necessary, since the traceback alone never shows the dictionary's actual keys — only names the one it was looking for and failed to find.

Guide's Part 2 Check for understanding, verbatim answer. The point: the traceback never reveals the dictionary's real keys.

Common pitfalls

Watch for

Fixing the typo by changing rec['amount'] (the access) to match rec['amout'] (the typo) instead of fixing the data — it stops crashing on record 1 but produces a new KeyError the moment Jordan's or Morgan's correctly-spelled record is processed.

Leaving the DEBUG print in place after the fix — walk the room checking it's removed, per the explicit instruction and the Week 7 callback.

Fix the data source, not the access point.
Part 3 · 0:30–0:42

Fix Bug 2 — the TypeError

Teaching goal: a TypeError from comparing incompatible types — diagnose it the same disciplined way (read, duck, document) before fixing, reinforcing that the process from Bug 1 generalizes to a genuinely different kind of bug. Say to the class: "New error, new type entirely. Same process: read it, explain it to the duck, document before fixing."

Rubber duck the comparison itself

Ask the duck

What type is amount at this point in the program? What type is '1000'? Is > defined between those two types?

"amount is total, which came from get_total() — that returns a number. '1000' has quotes, so it's a string. Comparing a number to a string with > — Python doesn't know how to say a number is 'greater than' a piece of text." That reasoning, said out loud, is the fix arriving.

## Bug 2
Error type: TypeError
File + line: week8_buggy.py, line 14 (inside is_over_limit)
What the error means: Python cannot compare an int and a string
  with > -- the two sides of the comparison are different types
How I fixed it: [to be filled in below]
Update debug_log.md's Bug 2 section before fixing. A student narrating this correctly arrives at the fix on their own.

Fix it — remove the quotes around 1000

records = [ {'id': 1, 'name': 'Taylor', 'amount': 1200}, {'id': 2, 'name': 'Jordan', 'amount': 450}, {'id': 3, 'name': 'Morgan', 'amount': 3500}, ] def get_total(records): total = 0 for rec in records: total += rec['amount'] return total def is_over_limit(amount): return amount > 1000 # fixed: '1000' (string) -> 1000 (int) def format_summary(total, count): return f'Total: ${total:.2f} across {count} records' total = get_total(records) print(format_summary(total, len(records))) print(is_over_limit(total))

Both bugs fixed. Press Run — clean output, no traceback.

Converting amount to a string instead (str(amount) > '1000') runs without error but compares alphabetically, not numerically — e.g. '9' > '1000' is True alphabetically even though 9 < 1000. A "technically works, but quietly wrong" fix worth flagging. Bug 1 was about a missing piece of data (wrong key name); Bug 2 is about mismatched types being compared — different diagnostic categories.

Verified final output

Total: $5150.00 across 3 records
True

Matches the lab page's own stated expected result exactly. debug_log.md Bug 2: "How I fixed it: removed the quotes around 1000 so is_over_limit compares two integers instead of an int and a string."

Verified with CPython 3.12.2 (the version Pyodide 0.26.4 bundles).

Knowledge check

If is_over_limit were called with a float instead of an int — say is_over_limit(1500.50) — would the fixed version still work correctly?

Yes — 1500.50 > 1000 compares a float to an int just fine, since Python allows numeric comparisons across int/float freely. The type mismatch that actually caused Bug 2 was specifically between a number and text, not between two different numeric types.

Guide's Part 3 Check for understanding, verbatim answer. A check that the fix's scope is understood precisely, not over-generalized.

Common pitfalls

Watch for

Converting amount to a string instead of converting '1000' to an integer — str(amount) > '1000' runs, but compares alphabetically, not numerically. Quietly wrong for many inputs.

Treating this as the "same bug" as Bug 1 — Bug 1 was a missing piece of data; Bug 2 is mismatched types. Different diagnostic categories, both worth recognizing by name.

Same disciplined process (read, duck, document, fix) — genuinely different error.
Part 4 · 0:42–0:55

Write Tests for the Fixed Code

Teaching goal: five pytest tests verifying the now-fixed functions, including a boundary case for is_over_limit — direct reinforcement of Week 7's boundary-testing lesson, applied to code that was, minutes ago, genuinely broken. Say to the class: "Now that both bugs are fixed, let's prove it stays fixed — five tests, including the exact boundary-case discipline from last week."

tests/test_week8.py — five tests

from week8_buggy import get_total, is_over_limit, format_summary

def test_get_total_correct():
    recs = [{'amount': 100}, {'amount': 200}]
    assert get_total(recs) == 300

def test_is_over_limit_true():
    assert is_over_limit(1500) is True

def test_is_over_limit_false():
    assert is_over_limit(500) is False

def test_is_over_limit_boundary():
    assert is_over_limit(1000) is False

def test_format_summary():
    result = format_summary(1234.56, 3)
    assert '1234.56' in result
    assert '3' in result

Shown for reference — pytest has no runner in the browser. The next slide runs the same five assertions live; the one after shows the real pytest -v output.

Line by line: - from week8_buggy import … — imports directly from the (now-fixed) file; the name still says "buggy" even though the bugs are gone, since renaming isn't part of today's task. - test_get_total_correct — a fresh, independent test list, not reusing the module-level records; tests define their own isolated input data. - test_is_over_limit_boundary — the required boundary case: is_over_limit(1000) should be False, since the fixed condition is amount > 1000, strictly greater. If Bug 2's fix had accidentally used >=, this test specifically would catch it. - test_format_summary — uses in to check substrings, not an exact ==, so it's robust to minor formatting details while still confirming the dollar amount and the count are present.

Run the same five checks live

Knowledge check

Which of the five tests would have caught Bug 1 (the KeyError), if it had run before the fix?

test_get_total_correct exercises get_total() on data with correctly-spelled keys, so it wouldn't itself have shown the typo bug — which was in the original records list's data, not in get_total()'s logic. This test verifies get_total()'s logic is correct; a typo in a different list literal is a data-entry mistake this specific test was never designed to catch. Logic correctness vs. data correctness.

Guide's Part 4 Check for understanding, verbatim answer — a slightly tricky question. The valuable takeaway: logic correctness vs. data correctness are different things tests must be designed for separately.

Common pitfalls

Watch for

Forgetting that week8_buggy.py has module-level code that runs the moment it's imported — its print() output appears when pytest runs (captured for passing tests, visible on failure or with -s). The cause — importing a file with top-level executable code runs that code — is worth naming.

This is exactly why Week 7's "no module-level side effects in business-logic files" rule matters once tests import them.
