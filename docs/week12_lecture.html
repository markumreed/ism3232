Section 1 — Where Week 11 Left Off
The rules missed things

Has my package A101 shipped? has no word order, so the order rule never ran and the model answered from memory. It once said A101 had shipped. It had not.

The rules caught too much

Do you sell gift cards? contains card, so it went to a person without the model ever seeing it.

And nobody could tell who said what

Every reply in the history had the role assistant, whether a rule, a tool or the model wrote it. Today fixes the first and third problems, and keeps the second on purpose. By the end of the hour you will be able to say why.

Section 2 — Tool Calls
The model asks; your code decides

Along with the conversation, the chatbot now sends a list of tools. The model either writes a reply or sends back a tool call: a tool's name and the values to use. It never runs anything. Your code decides whether to run the tool.

A decision is a dictionary
decision = {"tool": "look_up_order", "arguments": {"order_id": "A101"}}
print("text" in decision)
print(decision["tool"], decision["arguments"]["order_id"])

order_tool.py — a method the model may ask for
    def look_up_order(self, order_id):
        """Look up the status of one order.

        Args:
            order_id: The order ID, like A100.
        """
        found = self.find_order_id(order_id)
        if found is None:
            return "No order with that ID was found. Order IDs look like A100."
        return f"Order {found} is {self.find_status(found)}."
What to notice

The first line of the docstring says what the tool does. The Args: section says what each value should look like. The ollama package reads both and builds the description the model sees.

Until today a docstring was for people. Now a program reads it too.

Section 3 — The Tool Loop
ollama_model.py — the new method, decide
    def decide(self, instructions, history, tools):
        """Send the conversation and the tools. Return a reply or a tool request."""
        messages = [{"role": "system", "content": instructions}]
        for message in history:
            if message["role"] == "tool":
                messages = messages + self.tool_messages(message)
            else:
                messages.append(message)
        try:
            response = chat(model=self.model_name, messages=messages, tools=tools)
        except ConnectionError:
            return None
        except ResponseError:
            return None
        if response.message.tool_calls:
            call = response.message.tool_calls[0]
            return {"tool": call.function.name, "arguments": call.function.arguments}
        return {"text": response.message.content}
Why a new method?

reply returns text, and the Week 11 mini-project still calls it. A model that can ask for tools returns a decision, so it gets a second method and reply stays as it was.

chatbot.py — model_reply, write together
    def model_reply(self):
        """Ask the model. Run each tool it asks for, then ask again, up to a limit."""
        rounds = 0
        while rounds < MAX_TOOL_ROUNDS:
            tool_list = self.tools.tool_list()
            decision = self.model.decide(self.instructions, self.history, tool_list)
            if decision is None:
                return "Sorry, I can't answer that right now. Please try again in a moment."
            if "text" in decision:
                return decision["text"]
            name = decision["tool"]
            arguments = decision["arguments"]
            result = self.tools.run(name, arguments, self.history)
            self.history.append(
                {
                    "role": "tool",
                    "tool_name": name,
                    "arguments": arguments,
                    "content": result,
                }
            )
            rounds += 1
        return "Sorry, I couldn't finish that. I'm passing you to a human agent."

What to notice

Two trips to the model for one customer message: one to ask for the tool, one to answer. The middle line is the new tool entry. The model's reply and the tool's result are no longer mixed up.

rounds stops a model that never answers. After three trips the customer goes to a person.

ollama_model.py — tool_messages
    def tool_messages(self, message):
        """Turn one tool entry into the two messages Ollama expects."""
        name = message["tool_name"]
        request = {"function": {"name": name, "arguments": message["arguments"]}}
        return [
            {"role": "assistant", "content": "", "tool_calls": [request]},
            {"role": "tool", "tool_name": name, "content": message["content"]},
        ]
Ollama needs to see its own request

Store only the result and the model cannot tell it already asked. It asked for the same lookup twice in five out of five runs of Where is order A100? tool_messages turns one history entry into the two messages Ollama expects.

Section 4 — One Door
toolbox.py — run, the one door
    def run(self, name, arguments, history):
        """Check one tool request. Run the tool only if every check passes."""
        if name == "look_up_order":
            order_id = self.clean(arguments, "order_id")
            if order_id == "":
                return "The order ID is missing. Ask the customer for it."
            if not self.customer_said(history, order_id):
                return "The customer has not given that order ID. Ask them for it."
            return self.order_tool.look_up_order(order_id)
        if name == "check_stock":
            item = self.clean(arguments, "item")
            if item == "":
                return "The product is missing. Ask the customer which product."
            return self.stock_tool.check_stock(item)
        if name == "request_address_change":
            order_id = self.clean(arguments, "order_id")
            new_address = self.clean(arguments, "new_address")
            if order_id == "" or new_address == "":
                return "The order ID and the new address are both needed."
            if not self.customer_said(history, order_id):
                return "The customer has not given that order ID. Ask them for it."
            if not self.customer_said(history, new_address):
                return "The customer has not given that address. Ask them for it."
            return self.change_queue.request_address_change(order_id, new_address)
        return f"There is no tool named {name}."
toolbox.py — clean and customer_said
    def clean(self, arguments, key):
        """Return one argument as text without extra spaces, or "" if it is missing."""
        return str(arguments.get(key, "")).strip()

    def customer_said(self, history, text):
        """Return True if text appears in a message the customer typed."""
        for message in history:
            if message["role"] == "user" and text.lower() in message["content"].lower():
                return True
        return False

What to notice

Asked to change an address with no details, the model made up an order and an address. The check refused both, and the refusal told the model what to do next: ask the customer.

.strip() is new: it removes spaces from both ends. The empty check comes first because "" in "any text" is True; an empty address once got through an earlier version of this check.

Section 5 — Changes Wait for a Person
change_queue.py — the change tool only files a request
    def request_address_change(self, order_id, new_address):
        """Ask staff to change the shipping address on one order. Staff must approve it.

        Args:
            order_id: The order ID, like A100.
            new_address: The full new shipping address.
        """
        order_id = order_id.upper()
        if self.order_tool.find_status(order_id) is None:
            return "No order with that ID was found. Order IDs look like A100."
        number = len(self.requests) + 1
        request = {
            "number": number,
            "order_id": order_id,
            "new_address": new_address,
            "status": "waiting",
        }
        self.requests.append(request)
        return f"Request {number} was sent to staff. The address has not changed yet."
change_queue.py — approve is the only code that changes an order
    def approve(self, number):
        """Approve one waiting request and make the change."""
        request = self.find(number)
        if request is None:
            return f"There is no request {number}."
        if request["status"] != "waiting":
            return f"Request {number} is already {request['status']}."
        request["status"] = "approved"
        self.order_tool.change_address(request["order_id"], request["new_address"])
        return f"Request {number} approved."

Section 7 — What Tools Did Not Fix
Fixed

A101 was answered from a lookup in five out of five runs.

Not fixed

Told the store now closes at 11 pm, the model repeated it in five out of five runs. No tool knows the hours, so no tool is called.

Kept on purpose: gift cards

The payment rule still looks for card anywhere. Matching only the whole word would miss Can I pay by card? A gift-card question sent to a person costs a short wait; a missed payment question could put card details in front of the model. When a rule protects something, prefer false alarms.

Discussion
Discussion 1: who decides?
The model asked for request_address_change with an address nobody typed. Whose job was it to stop that: the model's, the instructions', or the code's?
Look for: the model cannot check itself; instructions help but do not guarantee; the Toolbox check and the staff approval are code and people.
Discussion 2: which tools need a person?
Bayside wants three more tools: show a product's price, cancel an order, and issue a refund. Which ones may run straight away, and which must wait in the queue?
Look for: looking something up changes nothing; anything that moves money or changes an order waits for a person.
Discussion 3: false alarms
Is it acceptable that Do you sell gift cards? goes to a person?
Look for: the cost of each kind of mistake; a protective rule should prefer the cheap mistake.
Misconceptions to listen for

“The model runs the tool.” It only asks; run does the work.

“A good docstring makes the model safe.” It makes requests better. The checks make them safe.

“If the tool exists, any request for it is fine.” A request can carry made-up values; that is what customer_said is for.

Where this goes next

Approved changes live in a Python list. Stop the program and they are gone. Next week you choose a business of your own, design its data, and keep it in a SQLite database. In Week 14 the database functions become the tools, and the chatbot you wrote today is copied over unchanged.
