Records and Loop

Teaching goal: the list-of-dicts literal syntax, and a first loop that filters on one condition. Say to the class (verbatim): "Five records, each a dictionary with the same five keys. This consistency — every record having exactly the same fields — is what makes looping through them meaningful." Check for understanding (asked at the end of this part): "If a sixth record had 'status': 'pending' (lowercase), would it be included by this filter?" Answer: No — string comparison with == is case-sensitive; 'pending' == 'Pending' is False. A good, concrete reminder of a lesson that recurs constantly whenever real-world data has inconsistent capitalization — a genuine, common data-quality issue, not just a syntax trivia point.

The idea

Concept

A list of dictionaries: square brackets hold five elements, each itself a dictionary in curly braces. Every dictionary has the same five keys (id, name, category, amount, status) — nothing in Python requires this, but consistency is what makes looping and filtering useful.

for rec in records: — rec is bound to one whole dictionary per pass, the same loop shape as any prior list iteration, just holding a richer value each time.

if rec['status'] == 'Pending': — bracket-notation dictionary access, inside a conditional, inside a loop: the three-layer combination doing real filtering work on business data.

In the f-string f"{rec['name']}: ${rec['amount']:,.2f}", note the single quotes inside, double quotes outside — Python requires the inner and outer quote characters to differ so there's no ambiguity about where the string ends. :,.2f adds a thousands separator and two decimals.

Two Business Rules

Teaching goal: accumulate multiple, independent results inside one loop — a running total, plus two separately-filtered lists built from two distinct threshold checks. Say to the class (verbatim): "Same loop shape, but now doing three jobs at once: a running total, and two separate 'flag this record' lists, each with its own threshold. This is the accumulator pattern, applied three times in parallel, inside one pass through the data." Check for understanding (asked at the end of this part): "If a pending record had amount exactly equal to 1000 — right at LIMIT — would it be flagged?" Answer: No — the check is strictly > LIMIT, not >=; a good boundary-condition check, echoing every prior module's repeated emphasis on reading comparison operators precisely.

The idea

Concept

LIMIT = 1000, HIGH = 2000 — named constants, all-caps by convention: if the review threshold ever changes, there's exactly one line to edit rather than hunting for every literal 1000.

total = 0, flagged = [], high_value = [] — three separate accumulators, initialized before the loop, each a different shape for a different purpose.

The two threshold checks are separate ifs, not elif — a record over HIGH ($2000) is by definition also over LIMIT ($1000) and should land in both lists. elif would silently exclude it from the broader review list.

flagged.append(rec) appends the whole dictionary, not just the amount — Part 3's "records needing review" printout needs each record's id and name, so keeping the full dict is a deliberate choice. Ask the room explicitly: "would elif here be correct?" (No — elif would mean a high-value record only ever lands in high_value, never also in flagged.)

Live-code — Part 2: three parallel accumulators (same file)

Formatted Summary and File Output

Teaching goal: print a clean, multi-line summary, and — new today — save it to an actual file on disk, ensuring the target folder exists first. Say to the class (verbatim): "Everything so far has only lived on screen, gone the moment the script ends. Today we save a summary to a real file — and I want to show you the one-line safety net that makes this work reliably regardless of whether the folder it's going into already exists." Check for understanding (asked at the end of this part): "If you ran this script three times in a row without deleting data/week6_summary.txt between runs, what would the file contain after the third run?" Answer: Still just the three summary lines — 'w' mode overwrites completely on every run, not accumulating; a direct callback to earlier modules' "w"-vs-append-mode distinction.

The idea

Concept

os.makedirs('data', exist_ok=True) — creates the folder if it's missing; exist_ok=True is the detail that prevents an error if the folder is already there, so re-running the script doesn't crash on the second run. Without makedirs at all, open('data/...', 'w') raises FileNotFoundError — Python won't create missing parent folders for you.

lines = [f'...', f'...', f'...'] — build the content once, as a list, so both the print() loop and the file-write reuse the exact same content and never drift out of sync.

'\n'.join(lines) glues the list elements with a newline between each pair — but not after the last one, which is why + '\n' is added explicitly for a clean trailing newline.

'w' mode is create-or-overwrite — the same overwrite-risk lesson as every prior file-writing exercise. f.write(...) does not add a newline the way print() does — that contrast is exactly why the '\n'.join(...) + '\n' construction is needed. The final loop over flagged reuses Part 2's accumulated list directly.

The idea

Concept

sum(a for a in amounts) — a generator expression inside sum(): a for a in amounts produces each value one at a time. For this simple case it's identical to sum(amounts); it's shown to preview the comprehension syntax on the next line.

[r for r in records if r['amount'] > 1000] — a list comprehension: read left to right as "for each r in records, if r['amount'] > 1000, include r in the new list." A compact equivalent of the for/if/.append() accumulator from Part 2 — same logic, tighter syntax.

The order is fixed: [expression for item in iterable if condition], always in that sequence.

Sort and Group Output

Frame as a quick, genuinely reusable pattern if the room reaches it. sorted(records, key=lambda r: r['amount'], reverse=True) — key=lambda r: r['amount'] tells sorted() what to sort by, since a list of dictionaries has no inherent order; the lambda is a tiny unnamed function saying "for each record r, use r['amount'] as the sort value." reverse=True flips it to descending. Any time you need to sort a list of dicts by one field, this key=lambda r: r[...] pattern is the standard tool. {r['amount']:>8,.2f} — >8 right-aligns the value within an 8-character field, so all the dollar amounts line up in a clean column regardless of digit count.

The idea

Concept

sorted(list, key=..., reverse=...) returns a new sorted list; it doesn't modify the original. key is a function applied to each element to decide the sort value.

lambda r: r['amount'] — a one-line unnamed function: given a record r, hand back its amount. This is the standard way to sort a list of dicts by one field.

{value:>8,.2f} — right-align in an 8-wide field (>8), thousands separator and two decimals (,.2f) — so a column of dollar amounts lines up cleanly.

This is genuinely reusable syntax worth naming explicitly — it recurs in later modules whenever data needs ordering by a chosen field. A quick before/after with and without the >8 makes the alignment effect visible.
