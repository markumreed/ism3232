Part 1 — Install sqlite3
1
Install the sqlite3 shell

On Windows, work in your Ubuntu (WSL) terminal:

Terminal — Ubuntu (WSL)
sudo apt update
sudo apt install sqlite3
sqlite3 --version

On a Mac, sqlite3 is already installed:

Terminal — macOS
sqlite3 --version

The last command prints a version line like this:

3.45.1 2024-01-30 16:01:20 e876e51a0ed5c5b3126f52e532044363a014bc594cfefa87ffb5b82257ccalt1 (64-bit)
Your version number and date may differ. On a Mac the columns of a table can be spaced a little differently. The rows are what matter.

-- schema.sql
-- Bayside Outfitters: orders, products, and changes waiting for staff.

CREATE TABLE IF NOT EXISTS orders (
    order_id TEXT PRIMARY KEY,
    customer TEXT NOT NULL,
    item     TEXT NOT NULL,
    status   TEXT NOT NULL,
    address  TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS products (
    name  TEXT PRIMARY KEY,
    price REAL NOT NULL,
    stock INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS change_requests (
    number      INTEGER PRIMARY KEY AUTOINCREMENT,
    order_id    TEXT NOT NULL,
    new_address TEXT NOT NULL,
    status      TEXT NOT NULL DEFAULT 'waiting'
);

Part 3 — Four SQL Exercises
🧩
Same window, in order
Do the exercises in the sqlite3 window from Part 3, one after another. Exercise 3 adds an order and Exercise 4 files a request, so the later results depend on the earlier steps.
4
Exercise 1 — Orders still processing

List the order ID and customer of every order whose status is processing, sorted by customer name.

order_id customer -------- ---------- A103 Ana Silva A101 Sam Okafor
Answer key — Exercise 1
sqlite3
sqlite> SELECT order_id, customer FROM orders WHERE status = 'processing' ORDER BY customer;
order_id  customer  
--------  ----------
A103      Ana Silva 
A101      Sam Okafor

Common mistake: forgetting the quotes around 'processing'. Without them SQLite looks for a column with that name.

5
Exercise 2 — Out of stock

List the name and price of every product with no stock.

name price ------------ ----- day pack 45.0 hiking socks 12.0
Answer key — Exercise 2
sqlite3
sqlite> SELECT name, price FROM products WHERE stock = 0;
name          price
------------  -----
day pack      45.0 
hiking socks  12.0

Common mistake: writing stock = '0'. It works here only because the column is INTEGER, so SQLite turns '0' into a number first. Write 0, a number with no quotes.

6
Exercise 3 — Orders by status

First add one more order. An INSERT prints nothing:

sqlite3
INSERT INTO orders (order_id, customer, item, status, address) VALUES ('A106', 'Kai Moreno', 'trail hat', 'processing', '5 Shell Road');

Now count the orders in each status.

status COUNT(*) ---------- -------- delivered 2 processing 3 shipped 2
Answer key — Exercise 3
sqlite3
sqlite> SELECT status, COUNT(*) FROM orders GROUP BY status;
status      COUNT(*)
----------  --------
delivered   2       
processing  3       
shipped     2

Processing is 3 because of the order you just added.

7
Exercise 4 — Approve a change by hand

The agent filed this request for staff. Type it:

sqlite3
INSERT INTO change_requests (order_id, new_address) VALUES ('A101', '9 Pine Street, Tampa');

Now approve it yourself with two UPDATE statements: change order A101’s address to 9 Pine Street, Tampa, and mark request 1 as approved. Then check your work:

sqlite3
SELECT order_id, address FROM orders WHERE order_id = 'A101';
SELECT number, order_id, status FROM change_requests;
sqlite> SELECT order_id, address FROM orders WHERE order_id = 'A101'; order_id address -------- -------------------- A101 9 Pine Street, Tampa sqlite> SELECT number, order_id, status FROM change_requests; number order_id status ------ -------- -------- 1 A101 approved
Typed the INSERT twice? Then there is a request 2 as well: AUTOINCREMENT gives every insert a new number. That is fine; approve request 1.
Answer key — Exercise 4
sqlite3
sqlite> UPDATE orders SET address = '9 Pine Street, Tampa' WHERE order_id = 'A101';
sqlite> UPDATE change_requests SET status = 'approved' WHERE number = 1;

In Week 14 these two statements become approve_request, the only code that changes an order’s address. Each UPDATE has a WHERE, so exactly one row changes.

Part 5 — Choose a Business and Write PROPOSAL.md
9
Choose your business and write the proposal

Open the capstone starters page. Pick one of the six businesses, or your own idea that meets the checklist. Then create the two files and open the folder:

Terminal
touch PROPOSAL.md schema.sql && code .

Copy the template into PROPOSAL.md and fill in every section. Bayside’s proposal shows a finished one. Before sign-off, tick each item:

  1. One business. The chat serves customers or staff; the Staff tab always serves staff.
  2. At least two business tables plus a change_requests table.
  3. At least two lookup tools. They only read, and they check their arguments.
  4. At least one change tool. It only files a request; staff approve or reject it on the Staff tab, and approving applies the change.
  5. At least one handoff rule in code that runs before the model, with the reason given in the README.
  6. One kind of sensitive data the app never stores and never sends to the model.
  7. Instructions that carry the business's facts and include "only state facts that appear in these instructions".
  8. Five sample conversations, which become the Week 16 evaluation cases.
Part 6 — Write schema.sql
10
Write and check your schema

In schema.sql, create your business tables with CREATE TABLE IF NOT EXISTS and add at least five sample rows to each with INSERT OR IGNORE. Add an empty change_requests table with the columns on the starters page. Then read it twice and compare the counts. Use your business’s name for the database file and your own table names:

Terminal and sqlite3
sqlite3 my_business.db
.read schema.sql
.tables
SELECT COUNT(*) FROM <table>;
.read schema.sql
SELECT COUNT(*) FROM <table>;
.quit

Your schema passes when the second .read prints nothing and the counts after it match the first. This is what Bayside’s check looks like:

sqlite3 — Bayside, first read
sqlite> .read schema.sql
sqlite> .mode column
sqlite> .headers on
sqlite> SELECT COUNT(*) FROM orders;
COUNT(*)
--------
6
sqlite3 — Bayside, read again
sqlite> .read schema.sql
sqlite> SELECT COUNT(*) FROM orders;
COUNT(*)
--------
6

Matching counts alone are not enough. Here Bayside’s schema was saved as plain_insert.sql with every OR IGNORE removed. The counts still match, but the second .read prints errors:

sqlite3 — a schema with plain INSERT, read twice
SQLite version 3.45.1 2024-01-30 16:01:20
Enter ".help" for usage hints.
sqlite> .read plain_insert.sql
sqlite> SELECT COUNT(*) FROM orders;
6
sqlite> .read plain_insert.sql
Runtime error near line 25: UNIQUE constraint failed: orders.order_id (19)
Runtime error near line 33: UNIQUE constraint failed: products.name (19)
sqlite> SELECT COUNT(*) FROM orders;
6
A UNIQUE constraint failed line means an INSERT is missing OR IGNORE. Next week the app runs schema.sql every time it starts, and that error would stop it on every start after the first. If a count grows instead, a table is missing its PRIMARY KEY, or change_requests has sample rows. Fix the file, delete the .db file, and check again.

Terminal

⚠
Why there is no ruff or pytest this week
Your folder has no Python yet. pytest finds no tests, exits with code 5 (“no tests ran”), and the && chain would stop before git. Week 14 adds the tests, and the full ritual comes back. After this first push, git push is enough.
