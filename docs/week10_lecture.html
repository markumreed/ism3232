Section 1 — What Problem Does a Class Solve?
The starting point

So far your data and your functions have lived apart. A chatbot has a name, a set of instructions and a conversation history. It also has things it does, such as responding. A class keeps that data and those actions together, so one chatbot is one thing you can create, pass around and test.

A class organizes code. It does not make a chatbot intelligent. This week's chatbot chooses replies with if statements, and we say so out loud.

Class = the template

Written once. Says what every chatbot remembers and what every chatbot can do. Nothing exists yet.

Object = one real chatbot

Created by calling the class. Has its own copy of every attribute. Sunny and River are two objects.

Section 2 — Step 1: A Class That Stores Data
Step 1 — write together, line by line
class SupportChatbot:
    """A support chatbot. Step 1: it only stores data."""

    def __init__(self, name, instructions):
        self.name = name
        self.instructions = instructions
        self.history = []


bot = SupportChatbot("Sunny", "You are a friendly support assistant.")
print(bot.name)
print(bot.instructions)
print(bot.history)
Output
Sunny
You are a friendly support assistant.
[]
What to notice

__init__ is never called by name. Writing SupportChatbot(...) runs it.

You pass two values and the method has three parameters. Python fills in self with the new object.

self.name = name: the right side is a parameter that disappears when the method ends. The left side is an attribute that stays on the object.

self.history = [] is not a parameter, because every conversation starts empty.

Section 3 — Step 2: A Method That Responds
Step 2 — add two methods
class SupportChatbot:
    """A support chatbot. Step 2: it can respond and remember."""

    def __init__(self, name, instructions):
        self.name = name
        self.instructions = instructions
        self.history = []

    def respond(self, user_message):
        self.history.append({"role": "user", "content": user_message})
        reply = self.choose_reply(user_message)
        self.history.append({"role": "assistant", "content": reply})
        return reply

    def choose_reply(self, user_message):
        text = user_message.lower()
        if "hello" in text:
            return f"Hello! I'm {self.name}."
        return "I'm not sure how to help with that."


bot = SupportChatbot("Sunny", "You are a friendly support assistant.")
print(bot.respond("Hello there"))
print(bot.respond("Where is my order?"))
print(len(bot.history))
print(bot.history[0])
Output
Hello! I'm Sunny.
I'm not sure how to help with that.
4
{'role': 'user', 'content': 'Hello there'}
What to notice

respond does three things in a fixed order: record the user's message, get a reply, record the reply. Every chatbot you build this term keeps that shape.

self.choose_reply(...) is one method calling another on the same object.

Each history entry is a dictionary with a role and a content. Real AI services expect this same shape, which is why we use it now.

choose_reply is the mock. It is two rules. Next week a model replaces it.

Section 4 — Step 3: A Separate Tool
Step 3 — a class with a different job
class OrderLookup:
    """A tool that knows about orders. It knows nothing about chatting."""

    def __init__(self, orders):
        self.orders = orders

    def find_order_id(self, text):
        for order_id in self.orders:
            if order_id in text.upper():
                return order_id
        return None

    def find_status(self, order_id):
        if order_id in self.orders:
            return self.orders[order_id]
        return None


order_tool = OrderLookup({"A100": "shipped", "A101": "processing"})
print(order_tool.find_order_id("Where is order a100?"))
print(order_tool.find_status("A100"))
print(order_tool.find_order_id("Where is my order?"))
print(order_tool.find_status("A999"))
Output
A100
shipped
None
None
What to notice

Nothing here mentions chatting. The tool knows orders and that is all.

find_order_id returns None when no known order ID is in the text. None is the tool's way of saying it has no answer.

You can run and test this class with no chatbot at all.

Section 5 — Step 4: Composition
Step 4 — the chatbot is handed the tool
class SupportChatbot:
    """A mock support chatbot. Its replies come from simple rules, not from AI."""

    def __init__(self, name, instructions, order_tool):
        """Set up one chatbot with its own name, instructions, tool, and history."""
        self.name = name
        self.instructions = instructions
        self.order_tool = order_tool
        self.history = []

    def respond(self, user_message):
        """Record the user's message, choose a reply, record it, and return it."""
        self.history.append({"role": "user", "content": user_message})
        reply = self.choose_reply(user_message)
        self.history.append({"role": "assistant", "content": reply})
        return reply

    def choose_reply(self, user_message):
        """Choose a reply with keyword rules. This is the mock part."""
        text = user_message.lower()
        if self.needs_human(text):
            return "I can't help with that here. I'm passing you to a human agent."
        if "order" in text:
            return self.order_reply(user_message)
        if "hello" in text:
            return f"Hello! I'm {self.name}. I can check an order status for you."
        return "I'm not sure how to help with that. I can check an order status."
Step 4 — the method that uses it
    def order_reply(self, user_message):
        """Use the order tool to answer a question about an order."""
        order_id = self.order_tool.find_order_id(user_message)
        if order_id is None:
            return "Which order? Please send an order ID like A100."
        status = self.order_tool.find_status(order_id)
        return f"Order {order_id} is {status}."
Create the tool first, then hand it over
order_tool = OrderLookup({"A100": "shipped", "A101": "processing"})
bot = SupportChatbot("Sunny", "You are a friendly support assistant.", order_tool)

print(bot.respond("hello"))
print(bot.respond("Where is order A100?"))
print(bot.respond("Where is my order?"))
print(bot.respond("Please change my shipping address"))
print(bot.respond("What is the weather today?"))
Output
Hello! I'm Sunny. I can check an order status for you.
Order A100 is shipped.
Which order? Please send an order ID like A100.
I can't help with that here. I'm passing you to a human agent.
I'm not sure how to help with that. I can check an order status.
What to notice

self.order_tool = order_tool is the whole idea. The chatbot has a tool.

self.order_tool.find_order_id(...) reads left to right: this chatbot's tool, its find_order_id method.

The handoff rule is checked first. A message that mentions both an address and an order goes to a person.

The chatbot never creates its own tool. That lets a test hand it a small one.

Section 6 — Trace One Message
Where is order A100?
  1. bot.respond(...) runs with self set to bot.
  2. The user's message is appended to self.history.
  3. choose_reply checks its rules in order and reaches the order rule.
  4. order_reply asks the tool for an ID. The tool returns A100.
  5. order_reply asks the tool for the status. The tool returns shipped.
  6. The sentence travels back up, is appended to the history, and is returned.
The history before and after
history before: []
reply: Order A100 is shipped.
history after:
  {'role': 'user', 'content': 'Where is order A100?'}
  {'role': 'assistant', 'content': 'Order A100 is shipped.'}
Section 7 — Two Objects, One Class
Two chatbots
order_tool = OrderLookup({"A100": "shipped", "A101": "processing"})
sunny = SupportChatbot("Sunny", "You are cheerful and brief.", order_tool)
river = SupportChatbot("River", "You are formal and detailed.", order_tool)

sunny.respond("hello")
sunny.respond("Where is order A100?")
river.respond("hello")

print(sunny.name, len(sunny.history))
print(river.name, len(river.history))
print(sunny.history[1]["content"])
print(river.history[1]["content"])
Output
Sunny 4
River 2
Hello! I'm Sunny. I can check an order status for you.
Hello! I'm River. I can check an order status for you.
Predict first

Move history = [] out of __init__ and into the class body. Send a message to Sunny only. How long is River's history?

A list in the wrong place
class SupportChatbot:
    history = []  # BUG: written in the class body, so every chatbot shares one list

    def __init__(self, name):
        self.name = name

    def respond(self, user_message):
        self.history.append(user_message)
        return "ok"


sunny = SupportChatbot("Sunny")
river = SupportChatbot("River")
sunny.respond("hello")
print(len(sunny.history))
print(len(river.history))
Output
1
1
Why

A value written in the class body belongs to the class, so every object shares it. In a real chatbot that shows one customer another customer's conversation. Create lists inside __init__.

Section 8 — What a Business Chatbot Can Get Wrong
Unreliable output

Do you sell cardigans? is passed to a human, because cardigans contains card. Rules are brittle. Models are wrong in less predictable ways.

Failed tools

The order may not exist, and a real order system can be down. Sunny asks for a valid ID and never invents a status.

Sensitive data

The history keeps everything a user types. Sunny never asks for payment details.

Actions that need a person

Looking up changes nothing. Changing an address changes where a parcel goes. A person approves changes.

What Is Essential, What Is Optional, What Is Left Out
Essential

Class, object, attribute, method, __init__, self, composition, and tracing a message. Every student should leave able to do these.

Optional enrichment

The functions-and-dictionary version, the real-model preview in the reading, and the second tool in the lab exercises.

Left out on purpose

Inheritance, abstract classes, decorators, metaclasses and design patterns. A chatbot with a tool needs has a, not is a kind of. The reading explains each in one line.

Discussion
Discussion 1: whose mistake is it?
Sunny passed a cardigan question to a human. How would you find mistakes like that before a customer does?
Look for: testing with real messages; the rule is brittle, and the class is not to blame; a model would fail differently, not never.
Discussion 2: what else is a tool?
Name three more tools a shop's chatbot could use. Which only look something up, and which change something?
Look for: stock, store hours, return policy are lookups. Refunds, cancellations and address changes are actions that need a person.
Discussion 3: sharing a tool
Sunny and River share one order tool. When would each chatbot need its own?
Look for: different stores or regions; a small tool with made-up data for testing.
Discussion 4: what is in the history?
If you saved every conversation to a file, what in that file should worry you?
Look for: names, addresses, anything typed by accident such as a card number; who can read the file and how long it is kept.
Misconceptions to listen for
  • “The class is the chatbot.” The class is the template. bot is the chatbot.
  • “self is a keyword I pass in.” Python passes it. You only write it in the definition.
  • “Both chatbots share the history.” Only if the list is created in the wrong place.
  • “Using a class makes it AI.” The replies are if statements.
  • “More in one class is simpler.” It is simpler until the second feature.
Where this goes next

Each later topic attaches to something built today. APIs and local models replace choose_reply. Tool calling lets the model decide when to use order_tool. Conversation state is self.history. Error handling grows from the None check. Privacy is about what the history holds. Evaluation grows from this week's tests. Human approval grows from the handoff rule.
