Learning objectives

By the end of this class period, students should be able to:

  • Connect to a SQLite database from Python with sqlite3.connect(), using a with block for automatic connection handling.
  • Use ? placeholders for every value inserted into a SQL query, and explain concretely why string formatting/concatenation into SQL is a security risk, not just a style issue.
  • Use row_factory = sqlite3.Row to retrieve query results as dictionary-like rows instead of plain tuples.
  • Design every database function to accept an optional db_file parameter, enabling isolated testing.
  • Write pytest tests using the tmp_path fixture to test against a fresh, isolated database file per test.

add_record and get_all_records

Teaching goal: the two most important functions in this file — writing data safely with ? placeholders, and reading it back as usable dictionaries with row_factory. Say to the class (verbatim): "This is where Rule 1 matters most. I'm going to show you what goes wrong if you don't follow it — not just tell you." Line-by-line (add_record): 'INSERT INTO requests (requester, category, amount, notes) VALUES (?,?,?,?)' — the SQL string contains ? placeholders, not the actual values. (requester, category, amount, notes) — a second, separate argument to .execute(): a tuple of actual values, matched positionally to each ? in order. sqlite3 fills in each placeholder itself, safely — not simply substituting text into the string the way an f-string would. The broken f-string version: query = f"INSERT INTO requests (...) Rule 1 — ? placeholders — and readable rows

Rule 1

The SQL string holds ? placeholders; the values go in a separate tuple. conn.execute('INSERT ... VALUES (?,?,?,?)', (requester, category, amount, notes)). sqlite3 fills in each placeholder itself, safely — it is not substituting text the way an f-string would. The value and the SQL structure stay completely separate, no matter what text a value contains. This is how you prevent SQL injection — one of the most common real-world security vulnerabilities in software history.

Reading rows back

conn.row_factory = sqlite3.Row — without it, rows come back as plain tuples accessed only by position. With it, each row is accessible by position and by column name. [dict(row) for row in cur.fetchall()] then converts each to an ordinary dict — usable with every dictionary technique from Weeks 6, 11 and 12.

ORDER BY id DESC — deliberate. The most recently added record comes first. Write it on the board now; Part 5 revisits it as a "read the code carefully" moment.

Guide, Part 2 — "this is Rule 1, worth the most careful explanation of the whole lab". The SQL string contains ?, not values; the tuple is a second, separate argument matched positionally. An f-string version that interpolates untrusted text can build a completely different, malicious statement — SQL injection. ? placeholders make that structurally impossible. row_factory = sqlite3.Row gives name-based access; dict(row) makes it fully ordinary. ORDER BY id DESC puts the newest row first — flagged again in Part 5.

Broken on purpose — an f-string query and a stray apostrophe

import sqlite3 conn = sqlite3.connect(':memory:') conn.execute(''' CREATE TABLE IF NOT EXISTS requests ( id INTEGER PRIMARY KEY AUTOINCREMENT, requester TEXT NOT NULL, category TEXT NOT NULL, amount REAL, status TEXT DEFAULT 'Pending', notes TEXT ) ''') # NEVER DO THIS -- building the SQL string with an f-string (violates Rule 1) requester = "O'Brien" category = 'Travel' amount = 1200 query = f"INSERT INTO requests (requester, category, amount) VALUES ('{requester}', '{category}', {amount})" conn.execute(query) print('inserted')

This is the guide's Part 2 check-for-understanding, done live: the name O'Brien contains an apostrophe. The f-string drops it straight into the SQL, where the ' prematurely ends the string literal. Press Run and read the last line of the traceback.

The f-string builds INSERT INTO requests (...) VALUES ('O'Brien', 'Travel', 1200) — the apostrophe in O'Brien closes the quoted literal early, leaving Brien', 'Travel', 1200) as broken syntax. This is not a bug in the function; it is untrusted text being allowed to become part of the SQL. A malicious value (Taylor', 'Travel', 999); DROP TABLE requests; --) exploits the same hole deliberately — that is SQL injection. Make a student say "the value became part of the SQL structure," not just "it broke." Check for understanding: with ? placeholders (next slide) the exact same O'Brien value inserts correctly, no special handling.

Fixed — a ? placeholder handles the apostrophe automatically

import sqlite3 conn = sqlite3.connect(':memory:') conn.execute(''' CREATE TABLE IF NOT EXISTS requests ( id INTEGER PRIMARY KEY AUTOINCREMENT, requester TEXT NOT NULL, category TEXT NOT NULL, amount REAL, status TEXT DEFAULT 'Pending', notes TEXT ) ''') # add_record with ? placeholders -- the value can contain anything, even a quote conn.execute( 'INSERT INTO requests (requester, category, amount, notes) VALUES (?,?,?,?)', ("O'Brien", 'Travel', 1200, '') ) conn.row_factory = sqlite3.Row row = conn.execute('SELECT * FROM requests ORDER BY id DESC').fetchone() print(dict(row))

The only change from the broken block: the value goes in the tuple, not the string. sqlite3 keeps the value and the SQL structure separate, so O'Brien stores correctly with no escaping code. Press Run — clean insert.

The stored requester reads back as O'Brien, apostrophe intact.

tmp_path — a fresh database file per test

Concept

tmp_path is a pytest fixture — a special parameter name pytest recognises and supplies automatically. It creates a brand-new, empty temporary directory unique to that one test run and passes its path in.

db = tmp_path / 'test.db' — the / is not division. tmp_path is a pathlib.Path, which overloads / to mean "join a path segment", building a full path like /tmp/pytest-.../test0/test.db.

Every call passes db explicitly — create_table(db), add_record(..., db_file=db), get_all_records(db_file=db). This is Rule 2's entire payoff: because no function hardcodes DB_FILE, tests redirect every operation to this test's private temp file — isolated from the real database and from every other test.

Each test function gets its own fresh tmp_path — data from test_add_and_retrieve is not visible in test_default_status_is_pending. That isolation is the whole point.

Live-code — delete_record and the trailing-comma trap

import sqlite3 conn = sqlite3.connect(':memory:') conn.execute(''' CREATE TABLE IF NOT EXISTS requests ( id INTEGER PRIMARY KEY AUTOINCREMENT, requester TEXT NOT NULL, category TEXT NOT NULL, amount REAL, status TEXT DEFAULT 'Pending', notes TEXT ) ''') for requester, category, amount in [('Taylor', 'Travel', 1200), ('Jordan', 'Equipment', 450)]: conn.execute( 'INSERT INTO requests (requester, category, amount, notes) VALUES (?,?,?,?)', (requester, category, amount, '') ) before = conn.execute('SELECT COUNT(*) FROM requests').fetchone()[0] # delete_record(1) -- (record_id,) needs the trailing comma to be a tuple conn.execute('DELETE FROM requests WHERE id=?', (1,)) after = conn.execute('SELECT COUNT(*) FROM requests').fetchone()[0] print(f'before={before} after={after}') assert after == before - 1 print('delete_record removed exactly one row')

Same two rules as the five required functions — a ? placeholder for the id, an optional db_file parameter. The trap: (1,) with the trailing comma is a one-element tuple; (1) is just the integer 1 in parentheses, and .execute() would reject it.

Line-by-line: table + two seeded rows; before counts them (2); conn.execute('DELETE FROM requests WHERE id=?', (1,)) is delete_record's body — the ? placeholder for record_id, and the single-element tuple (1,); after re-counts (1); the assert confirms the count dropped by exactly one, mirroring the guide's suggested tmp_path test. The trailing-comma point is the guide's: (record_id,) is a tuple; (record_id) is not — a classic, worth-flagging Python syntax trap. Passing a bare 1 to .execute()'s parameter argument raises ValueError: parameters are of unsupported type.
