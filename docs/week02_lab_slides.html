Learning objectives

By the end of this class period, students should be able to:

  • Navigate the filesystem using pwd, ls, ls -la, and cd (including cd .. and cd ~) without hesitation.

Part 1 · 0:04–0:20

Navigation

Teaching goal: the four navigation commands (pwd, ls, ls -la, cd) fluent enough to use without thinking — and a first look at tree for visualizing structure at a glance. Say to the class: "Nine commands, in sequence. I want you reading each result before typing the next line — don't paste this whole block at once. The point today is noticing what changes after each command." Setup just before this: cd ~/ism3232/module02_zsh, mkdir week2_lab, cd week2_lab, pwd — "Everything today happens inside a fresh week2_lab/ folder, so today's practice doesn't clutter what you'll build in later weeks."

The idea

Concept

Make pwd your reflex in any unfamiliar terminal.

pwd / ls are Week 1's familiar pair — now the automatic first move in any new terminal session.

ls -la is two flags at once: -l (long format, one entry per line with permissions and size) and -a (all, including hidden files whose names start with a dot, like .gitignore or .zshrc, which plain ls hides). Hidden files aren't rare edge cases here — .venv/, .gitignore, and .zshrc all arrive in Week 3, and ls -la is how you'll confirm they exist.

Making pwd your reflexive first command in any unfamiliar terminal state is exactly the habit this whole unit is building. Emphasise the "read each result before the next line" discipline here.

Live-code — one command at a time, pause for output after each

cd ~/ism3232/module02_zsh/week2_lab pwd ls ls -la cd .. pwd cd ~/ism3232 tree -L 2 cd module02_zsh/week2_lab pwd

The first cd just puts the emulator where the Setup step left you. tree -L 2 then draws the ism3232/ structure two levels deep; the final pwd confirms you are back in week2_lab.

Line by line: - pwd / ls — Week 1's familiar pair, now the automatic first move in any new terminal session. - ls -la — -l (long format: permissions, size, one per line) and -a (all, including hidden dot-files). Hidden files matter: .venv/, .gitignore, .zshrc are coming in Week 3. - cd .. — .. means "the parent of the current directory"; moves up exactly one level. - cd ~/ism3232 — an absolute-from-home jump using ~. Contrast with cd ..: .. is always relative to where you are now; ~/ism3232 works identically from anywhere, anchored to home. - tree -L 2 — new command today. tree draws the folder structure as a text diagram; -L 2 limits the depth to 2 levels so the output stays readable. Fastest way to get an at-a-glance sense of a project's shape. - cd module02_zsh/week2_lab — a relative path with two segments, moving through two levels of nesting in one cd. cd is not limited to one folder at a time. (The emulator labels the tree root . rather than ism3232/ — that is exactly what real tree prints when run from inside the folder; contents also vary by what each student has built so far.)

Predict

Before running: if you ran tree -L 1 instead of tree -L 2 here, what would change?

Only the top-level folder names would show — none of their contents.
-L limits how DEEP tree looks, not WHICH folders appear.
Common misconception: students read -L 2 as limiting which folders show rather than how deep the walk goes. Get a student to state the correct version out loud.

Knowledge check

Starting from ~/ism3232/module02_zsh/week2_lab, what is the shortest cd command to reach ~/ism3232/module01_setup?

cd ../../module01_setup — up two levels to ism3232/, then down into module01_setup. cd ~/ism3232/module01_setup is an equally correct absolute alternative; the tradeoff is that the relative path is shorter here but breaks if you're not starting in week2_lab, while the absolute path works from anywhere.

A relative-path reasoning check. ../module01_setup (B) only goes up one level, to module02_zsh, where module01_setup doesn't exist; module01_setup (C) looks for it inside week2_lab.

Common pitfalls

Watch for

Running cd module02_zsh/week2_lab from somewhere other than directly inside ~/ism3232 — produces No such file or directory, since this is a relative path that requires the right starting point. Have the student run pwd first and reason about it.

Confusing tree's depth limit (-L 2) with somehow limiting which folders show, rather than how deep it looks.

Not noticing hidden files in ls -la output — there simply aren't any yet this early in the semester. That's expected; Week 3 is where ls -la starts showing something genuinely new (.venv/, .gitignore).

Check for understanding: "Starting from ~/ism3232/module02_zsh/week2_lab, what's the shortest cd to reach ~/ism3232/module01_setup?" Answer: cd ../../module01_setup (up two levels, then down), or the absolute cd ~/ism3232/module01_setup — ask the student to name the tradeoff between the two styles.
Part 2 · 0:20–0:38

File Operations

Teaching goal: create, write to, read, copy, and rename files entirely from the terminal, and open a folder properly as a VS Code workspace — the complete "manage files without a file browser" toolkit. Say to the class: "Six file operations, and I want you to genuinely read each output rather than just trusting the command ran. cat and head in particular — I want you to predict what each will print before you run it."

Live-code — file operations

cd ~/ism3232/module02_zsh/week2_lab touch notes.txt commands.txt hello_week2.py ls -la echo 'Week 2 navigation practice' > notes.txt cat notes.txt head -1 notes.txt cp notes.txt notes_backup.txt mv hello_week2.py week2_script.py ls -la

cat and head -1 each print Week 2 navigation practice. The final ls -la shows four files — commands.txt, notes.txt, notes_backup.txt, week2_script.py — hello_week2.py is genuinely gone, replaced by its renamed version. (In VS Code you then add print('Week 2 complete') to week2_script.py and python3 week2_script.py prints that third line.)

Line by line: - touch notes.txt commands.txt hello_week2.py — Week 1's touch, now creating three files in one command (same "multiple arguments" pattern as mkdir last week). - echo 'Week 2 navigation practice' > notes.txt — new syntax: the > redirect operator. echo alone prints to the terminal; > sends that output into a file, overwriting whatever was there. > completely replaces a file's contents — the same "silent overwrite" risk as Python's "w" file mode. The Stretch's >> is the safer alternative. - cat notes.txt — prints a file's entire contents; simplest way to view a small file without an editor. - head -1 notes.txt — prints only the first line. notes.txt has one line, so this looks identical to cat right now; the real value of head shows on a longer file. - cp notes.txt notes_backup.txt — copy: notes.txt stays untouched, a new notes_backup.txt is created with identical contents. - mv hello_week2.py week2_script.py — rename (or move). Unlike cp, mv does not leave the original behind; hello_week2.py no longer exists at all afterward.

The idea

Concept

> replaces a file's contents — a silent overwrite. cp keeps the original; mv does not.

cp source destination leaves source in place and makes a second file. mv source destination renames or moves — after it runs, the original name is gone entirely. Both take arguments in the same order: "this becomes that."

Confusing cp's and mv's argument order is the most common mistake here — a reversed order copies or renames in the wrong direction. If it happens, have the student re-run ls -la and reason about which file now has which name and content before "fixing" it by guessing.

Knowledge check

After mv hello_week2.py week2_script.py, what does ls show?

Unlike cp, mv does not leave the original behind. After this line, hello_week2.py no longer exists at all — only week2_script.py does, with the same content.

If a student picks A, they're thinking of cp. This is the core cp-vs-mv distinction — worth making them say the difference in their own words.

Common pitfalls

Watch for

Confusing cp's and mv's argument order — both take source destination. A reversed order copies or renames in the wrong direction; have the student re-run ls -la and reason before "fixing" it by guessing.

Using > a second time on notes.txt by accident (for example re-running the echo line) — silently replaces the content again rather than adding to it. This is exactly the risk the Stretch's >> avoids.

Opening week2_script.py by double-clicking it in a file browser instead of via code week2_script.py or the already-open workspace — not an error, but it breaks the "everything through the terminal / workspace" discipline this unit is building.

Check for understanding: "If you ran cp notes.txt notes.txt — same source and destination name — what would happen?" Most systems either refuse with an error (cp: notes.txt and notes.txt are identical) or leave the file unchanged. Not something to demonstrate destructively — a reasoning question about what cp's two-argument contract requires: a genuinely different destination.

Then open the folder properly in VS Code

cd ~/ism3232/module02_zsh code .

code . opens the whole folder as a workspace — not a single file. Confirm the Explorer panel shows week2_lab/ and its files.

Reinforces Week 1's "open the whole workspace, not individual files" habit, now one level up from last week — module02_zsh rather than a single lab folder. In the emulator code . just prints a placeholder line; the point is the command and the workspace concept.
Part 3 · 0:38–0:53

Safe File Deletion

Teaching goal: rm's permanence, and the two-step safety ritual (pwd then ls, every single time, before deleting) as an automatic reflex — this is the highest-stakes command taught all semester, and the only one with genuinely no undo. Say to the class: "Everything else today, if you make a mistake, you can fix it — rename it back, recreate it, copy it again. rm is different. There is no Trash, no Recycle Bin, no undo. Once it runs, the file is gone. So before every single rm for the rest of this course, you run two commands first: pwd, then ls. Confirm where you are, confirm what's actually there. I'm going to do this myself, every time, all semester — watch me model it now." State explicitly at the start of this part exactly when you will demonstrate a real rm, and narrate the ritual every single time you run it yourself today.

The idea

Ritual

Before every rm: pwd, then ls. No Trash. No undo.

pwd catches an earlier cd that didn't do what you expected — you could be about to delete in the wrong place entirely. ls confirms the file exists here, spelled the way you expect, and shows what else is here so a typo doesn't silently take the wrong file.

Repetition is the point. Say "this is permanent" out loud each time. The ritual has to become reflexive before speed does.

Live-code — the full ritual, narrating each step

cd ~/ism3232/module02_zsh/week2_lab pwd ls rm notes_backup.txt ls

First ls: commands.txt  notes.txt  notes_backup.txt  week2_script.py. After rm, the final ls has exactly commands.txt  notes.txt  week2_script.py — one fewer, and only the intended file gone.

Line by line: - pwd — confirms you're in the folder you think you're in; catches the case where an earlier cd didn't do what you expected and you're about to delete in the wrong place. - ls — confirms the file you're about to delete actually exists here, spelled the way you expect, and lets you see what else is here so a typo in the rm filename doesn't silently delete the wrong thing. - rm notes_backup.txt — the actual deletion. No confirmation prompt, no warning, no Trash. This is permanent. - Final ls — confirms the deletion happened and that only the intended file is gone, nothing else. (The emulator prints /Users/student/…; on a student machine the pwd line shows their own username.)

Knowledge check

Why does the ritual specifically require both pwd and ls, rather than just one or the other?

pwd confirms where you are; ls confirms what's actually there. You could be in the exact right folder but misremember or mistype a filename — ls catches that. You could see a familiar-looking filename in ls output while actually being in the wrong folder entirely — pwd catches that. Neither check alone covers both failure modes.

Have a student articulate this in their own words, not just recite it. The two checks are not redundant — they cover orthogonal mistakes.

Common pitfalls

Watch for

Skipping straight to rm without the pwd / ls steps, especially once students feel confident and start moving faster. Correct this every time you see it during this part, even though it slows the room down — the point is that the ritual becomes reflexive before speed does.

Using a wildcard carelessly (rm * or rm *.txt) without fully understanding what it will match. rm *.txt deletes every .txt file in the current directory at once, with the same total permanence as a single-file rm. Warn verbally — never demo it live on a real folder.

Attempting to rm a folder with the same syntax as a file — rm alone refuses on a directory (rm: some_folder: is a directory). Removing a folder needs rm -r (recursive), which is more dangerous, not less. Mention as a caution; do not demonstrate live.

Check for understanding: "Why does the ritual require both pwd and ls?" — pwd confirms where you are; ls confirms what's actually there. A student in the right folder can still mistype a filename (ls catches it); a student seeing a familiar filename can still be in the wrong folder (pwd catches it). Neither alone covers both failure modes.

Pipes & Redirect

Genuine bonus — full attention only if time allows. It introduces two new ideas (| and >>) beyond the required parts, worth a few extra minutes only if the room has them, not a rushed add-on.

Live-code — pipes and append

cd ~/ism3232/module02_zsh/week2_lab ls -la | head -5 echo 'extra line' >> notes.txt cat notes.txt wc -l notes.txt

ls -la | head -5 shows only the first 5 lines of the listing. After the append, cat notes.txt shows both lines and wc -l notes.txt reports 2.

- ls -la | head -5 — the pipe (|) takes the output of the command on its left and feeds it as input to the command on its right. ls -la's full listing gets fed into head -5, showing only the first 5 lines. Piping is how you chain simple commands into something more specific without a single built-in command that does exactly what you want — a foundational Unix idea. - echo 'extra line' >> notes.txt — two > characters, not one. >> appends to a file, adding a new line at the end while preserving everything already there; a single > would have erased notes.txt's existing content entirely. This is the fix to Part 2's overwrite risk. wc -l (word count, -l for lines) then confirms the file now has two lines, not one.

Predict

Before running cat notes.txt after the append — how many lines will it show?

Two: the original "Week 2 navigation practice" line,
plus the appended "extra line".

>> adds to the file; a single > would have wiped the first line.
wc -l then reports 2.
Ask the room to predict before running — a good check that the append-vs-overwrite distinction actually landed.
