Why use classes for an AI application?

A chatbot has data that belongs together: its name, the instructions it was given, and the conversation so far. It also has actions that work on that data, such as responding to a message. A class is a way to keep that data and those actions in one place.

That gives you three practical things:

  • One place to look. Everything about the chatbot is in one block of code.
  • Many chatbots from one design. You write the class once and create as many chatbots as you need, each with its own conversation.
  • Parts you can plug in. You can hand the chatbot a tool, such as an order lookup, without mixing the tool's code into the chatbot's code.
⚠ A class organizes code. It does not make anything intelligent.

The chatbot you build this week chooses its replies with if statements. Putting those if statements inside a class makes the program easier to read, extend and test. It does not make the replies any smarter.

You do not always need a class

You could write this week's chatbot with plain functions and one shared dictionary. This version works:

The same idea with functions and one shared dictionary
# The same chatbot, written with functions and one shared dictionary.

ORDERS = {"A100": "shipped", "A101": "processing"}


def find_order_id(orders, text):
    """Return the first known order ID mentioned in text, or None."""
    for order_id in orders:
        if order_id in text.upper():
            return order_id
    return None


def respond(state, user_message):
    """Record the message, choose a reply, record it, and return it."""
    state["history"].append({"role": "user", "content": user_message})
    order_id = find_order_id(state["orders"], user_message)
    if order_id is None:
        reply = "Which order? Please send an order ID like A100."
    else:
        reply = f"Order {order_id} is {state['orders'][order_id]}."
    state["history"].append({"role": "assistant", "content": reply})
    return reply


state = {"name": "Sunny", "history": [], "orders": ORDERS}
print(respond(state, "Where is order A100?"))
print(len(state["history"]))
Output
Order A100 is shipped.
2

Many real agent programs are written this way, and it is a fine choice for a small script. It gets awkward as the program grows. Every function has to be handed state. Nothing stops code somewhere else from changing state["history"]. If you want two chatbots, you have to keep two dictionaries straight yourself. A class solves those three problems, and most chatbot code you will read uses classes, so this module teaches them. Use whichever style keeps your own code clear.

The example: Sunny, a support chatbot

Bayside Outfitters is a made-up outdoor shop. Its chatbot is called Sunny. Sunny does three things:

  • It answers one kind of question: where is my order?
  • It passes two kinds of request to a person: changing a shipping address, and anything about payment or card details.
  • It says so plainly when it does not know how to help.

We use this one example for the whole module.

The mock and a production agent are different things

A mock is a stand-in that behaves like the real thing in a simple, predictable way. Sunny is a mock in two ways. Its replies come from keyword rules, not from an AI model. Its order data is a small dictionary typed into the file, not a company's order system.

A production agent is one that real customers use. It talks to a real AI model, which can be wrong in ways you cannot predict. It reads from real business systems, which can be slow or unavailable. Its mistakes cost money and trust. The class structure you learn this week is the same in both. Everything around it is harder, and later weeks cover that.

Seven words, in plain language

Read these before you look at any code. Each one comes back in the steps below.

classA template you write once. It says what data each chatbot will remember and what each chatbot can do. Think of a blank new-customer form.
objectOne thing made from the template. Sunny is an object. A filled-in form is an object. You can make many objects from one class.
attributeA piece of data that an object remembers, such as its name or its conversation history. An attribute is a variable that belongs to one object.
methodA function that belongs to a class. It is something every object of that class can do, such as respond to a message.
__init__The method Python runs by itself, once, when you create an object. Its job is to give the new object its starting attributes. The name has two underscores on each side.
selfThe object a method is working on right now. Inside the class, self.name means this chatbot's name.
compositionGiving one object another object to use. Sunny is given an order-lookup tool. Sunny has a tool.

Step 1 — A class that stores data

Start with the smallest useful class. It only remembers things.

Step 1
class SupportChatbot:
    """A support chatbot. Step 1: it only stores data."""

    def __init__(self, name, instructions):
        self.name = name
        self.instructions = instructions
        self.history = []


bot = SupportChatbot("Sunny", "You are a friendly support assistant.")
print(bot.name)
print(bot.instructions)
print(bot.history)
Output
Sunny
You are a friendly support assistant.
[]
  • class SupportChatbot: starts the template. By convention a class name is written with a capital letter at the start of each word and no underscores.
  • def __init__(self, name, instructions): defines the setup method. You never call it by name. Python runs it when you write SupportChatbot(...).
  • self.name = name stores the value on the object. The right side is the parameter, which disappears when __init__ finishes. The left side is the attribute, which stays for as long as the object exists.
  • self.history = [] gives every new chatbot its own empty list. It is not a parameter because every conversation starts empty.
  • bot = SupportChatbot("Sunny", "You are a friendly support assistant.") creates one object. You pass two values. Python supplies self for you.
  • bot.name reads an attribute. The dot means the name that belongs to this object.

Step 2 — A method that responds

Now give the chatbot something to do. Add two methods below __init__.

Step 2: add these methods inside the class
    def respond(self, user_message):
        self.history.append({"role": "user", "content": user_message})
        reply = self.choose_reply(user_message)
        self.history.append({"role": "assistant", "content": reply})
        return reply

    def choose_reply(self, user_message):
        text = user_message.lower()
        if "hello" in text:
            return f"Hello! I'm {self.name}."
        return "I'm not sure how to help with that."
Using it
bot = SupportChatbot("Sunny", "You are a friendly support assistant.")
print(bot.respond("Hello there"))
print(bot.respond("Where is my order?"))
print(len(bot.history))
print(bot.history[0])
Output
Hello! I'm Sunny.
I'm not sure how to help with that.
4
{'role': 'user', 'content': 'Hello there'}
  • def respond(self, user_message): is a method. Its first parameter is always self. The caller writes bot.respond("Hello there") and passes only the message.
  • self.history.append({"role": "user", "content": user_message}) adds one dictionary to this chatbot's history. role says who spoke. content is what they said.
  • reply = self.choose_reply(user_message) calls another method on the same object. Inside a class you reach your own methods through self.
  • text = user_message.lower() makes a lowercase copy, so Hello and hello match the same rule.
  • return reply hands the reply back to whoever called respond.
  • After two messages the history holds four dictionaries: two from the user and two from the chatbot.

Step 3 — A separate tool

Looking up an order is a different job from holding a conversation. Give that job its own class. In agent programs, a tool is a piece of code the chatbot can use to get information or do something.

Step 3
class OrderLookup:
    """A tool that knows about orders. It knows nothing about chatting."""

    def __init__(self, orders):
        self.orders = orders

    def find_order_id(self, text):
        for order_id in self.orders:
            if order_id in text.upper():
                return order_id
        return None

    def find_status(self, order_id):
        if order_id in self.orders:
            return self.orders[order_id]
        return None


order_tool = OrderLookup({"A100": "shipped", "A101": "processing"})
print(order_tool.find_order_id("Where is order a100?"))
print(order_tool.find_status("A100"))
print(order_tool.find_order_id("Where is my order?"))
print(order_tool.find_status("A999"))
Output
A100
shipped
None
None
  • OrderLookup has one attribute, orders, a dictionary that maps an order ID to a status.
  • find_order_id(self, text) loops over the order IDs it knows and returns the first one that appears in the text. text.upper() makes an uppercase copy so a100 matches A100.
  • find_status(self, order_id) returns the status, or None when there is no such order. None is how the tool says I have no answer.
  • Nothing in this class mentions chatting. You could test it, reuse it, or replace it without touching the chatbot.

Step 4 — Give the chatbot the tool

This is composition. The chatbot does not contain the order code. It is handed a tool object and keeps it in an attribute.

Step 4: the initializer now accepts a tool
    def __init__(self, name, instructions, order_tool):
        """Set up one chatbot with its own name, instructions, tool, and history."""
        self.name = name
        self.instructions = instructions
        self.order_tool = order_tool
        self.history = []
Step 4: a method that uses the tool
    def order_reply(self, user_message):
        """Use the order tool to answer a question about an order."""
        order_id = self.order_tool.find_order_id(user_message)
        if order_id is None:
            return "Which order? Please send an order ID like A100."
        status = self.order_tool.find_status(order_id)
        return f"Order {order_id} is {status}."
Creating both objects and connecting them
order_tool = OrderLookup({"A100": "shipped", "A101": "processing"})
bot = SupportChatbot("Sunny", "You are a friendly support assistant.", order_tool)

print(bot.respond("hello"))
print(bot.respond("Where is order A100?"))
print(bot.respond("Where is my order?"))
print(bot.respond("Please change my shipping address"))
print(bot.respond("What is the weather today?"))
Output
Hello! I'm Sunny. I can check an order status for you.
Order A100 is shipped.
Which order? Please send an order ID like A100.
I can't help with that here. I'm passing you to a human agent.
I'm not sure how to help with that. I can check an order status.
  • self.order_tool = order_tool stores the tool on the chatbot. From now on the chatbot has a tool.
  • self.order_tool.find_order_id(user_message) reads as: take this chatbot's tool, and call its find_order_id method.
  • if order_id is None: handles a failed lookup. The chatbot asks for a valid ID. It does not guess.
  • The tool is created first, then passed in when the chatbot is created. The chatbot never creates its own tool, so you can hand it a different one, including a small one for testing.

Why two classes and not one?

You could put everything in one class. It runs:

One class doing two unrelated jobs
class SupportChatbot:
    """One class doing two jobs: chatting AND storing every order."""

    def __init__(self, name, instructions):
        self.name = name
        self.instructions = instructions
        self.history = []
        self.orders = {"A100": "shipped", "A101": "processing"}

    def respond(self, user_message):
        self.history.append({"role": "user", "content": user_message})
        reply = "I'm not sure how to help with that."
        for order_id in self.orders:
            if order_id in user_message.upper():
                reply = f"Order {order_id} is {self.orders[order_id]}."
        self.history.append({"role": "assistant", "content": reply})
        return reply


bot = SupportChatbot("Sunny", "You are a friendly support assistant.")
print(bot.respond("Where is order A100?"))

It prints Order A100 is shipped. and it is harder to live with. The order data cannot be tested without building a chatbot. Two chatbots would each carry their own copy of the orders. When you add stock, returns and store hours, the class keeps growing. Giving each job its own class keeps each one short and lets you change one without breaking the other.

Trace one message

Follow Where is order A100? from the user to the reply.

  1. The program calls bot.respond("Where is order A100?"). Python runs respond with self set to bot.
  2. respond appends the user's message to self.history.
  3. respond calls self.choose_reply(...).
  4. choose_reply makes a lowercase copy and checks its rules in order. The message has no handoff word. It does contain order, so it calls self.order_reply(...).
  5. order_reply asks the tool for an order ID. The tool finds A100 in the text and returns it.
  6. order_reply asks the tool for the status of A100. The tool returns shipped.
  7. order_reply builds the sentence and returns it to choose_reply, which returns it to respond.
  8. respond appends the reply to self.history and returns it to the program.
Proof: the history before and after
history before: []
reply: Order A100 is shipped.
history after:
  {'role': 'user', 'content': 'Where is order A100?'}
  {'role': 'assistant', 'content': 'Order A100 is shipped.'}

Two objects from one class

One class can make as many chatbots as you like. Each one keeps its own data.

Two chatbots, one class
order_tool = OrderLookup({"A100": "shipped", "A101": "processing"})
sunny = SupportChatbot("Sunny", "You are cheerful and brief.", order_tool)
river = SupportChatbot("River", "You are formal and detailed.", order_tool)

sunny.respond("hello")
sunny.respond("Where is order A100?")
river.respond("hello")

print(sunny.name, len(sunny.history))
print(river.name, len(river.history))
print(sunny.history[1]["content"])
print(river.history[1]["content"])
Output
Sunny 4
River 2
Hello! I'm Sunny. I can check an order status for you.
Hello! I'm River. I can check an order status for you.

Sunny has four messages in its history and River has two. Sunny's conversation did not leak into River's, because self.history = [] ran once for each object. The two chatbots also greet with different names, because self.name is different for each. They share one thing: both were handed the same order_tool object. That is allowed and useful. One tool can serve many chatbots.

✍ Think before reading on

In the code below, history = [] is written in the class body and not inside __init__. Only Sunny is sent a message. What do the two print lines show?

A list written in the wrong place
class SupportChatbot:
    history = []  # BUG: written in the class body, so every chatbot shares one list

    def __init__(self, name):
        self.name = name

    def respond(self, user_message):
        self.history.append(user_message)
        return "ok"


sunny = SupportChatbot("Sunny")
river = SupportChatbot("River")
sunny.respond("hello")
print(len(sunny.history))
print(len(river.history))
Output
1
1

Both lines print 1. A value written in the class body belongs to the class, so every object shares the one list. River now holds a message that only Sunny received. In a real chatbot that would show one customer another customer's conversation. Create lists inside __init__ with self. in front, and the output becomes 1 and 0.

Three mistakes almost everyone makes

1. Forgetting self in the parameter list

Broken
class SupportChatbot:
    def __init__(self, name, instructions):
        self.name = name
        self.instructions = instructions
        self.history = []

    def greet():  # BUG: no self in the parameter list
        return f"Hello! I'm {self.name}."


bot = SupportChatbot("Sunny", "You are a friendly support assistant.")
print(bot.greet())
What Python prints
Traceback (most recent call last):
  File "missing_self.py", line 12, in <module>
    print(bot.greet())
          ^^^^^^^^^^^
TypeError: SupportChatbot.greet() takes 0 positional arguments but 1 was given

The class is defined without any error. The failure comes on the call. bot.greet() passes bot in automatically, and greet has no parameter to receive it. Fix: def greet(self):.

2. Forgetting self. in front of an attribute

Broken
class SupportChatbot:
    def __init__(self, name, instructions):
        name = name  # BUG: no self. in front, so nothing is stored on the object
        self.instructions = instructions
        self.history = []


bot = SupportChatbot("Sunny", "You are a friendly support assistant.")
print(bot.instructions)
print(bot.name)
What Python prints
You are a friendly support assistant.
Traceback (most recent call last):
  File "missing_self_dot.py", line 10, in <module>
    print(bot.name)
          ^^^^^^^^
AttributeError: 'SupportChatbot' object has no attribute 'name'

name = name only sets a local variable, which disappears when __init__ ends. Nothing was stored on the object, so bot.name does not exist. Fix: self.name = name.

3. Confusing the class with an object

Broken
class SupportChatbot:
    def __init__(self, name, instructions):
        self.name = name
        self.instructions = instructions
        self.history = []

    def greet(self):
        return f"Hello! I'm {self.name}."


print(SupportChatbot.greet())  # BUG: calling the method on the class, not on an object
What Python prints
Traceback (most recent call last):
  File "class_vs_object.py", line 11, in <module>
    print(SupportChatbot.greet())  # BUG: calling the method on the class, not on an object
          ^^^^^^^^^^^^^^^^^^^^^^
TypeError: SupportChatbot.greet() missing 1 required positional argument: 'self'

SupportChatbot is the template. It has no name and no history of its own. You call methods on an object you created: bot = SupportChatbot(...), then bot.greet().

What a business chatbot can get wrong

These four risks apply to the mock, and they apply with more force to a chatbot that uses a real AI model and real business systems.

1. Unreliable output

Two messages
print(bot.respond("Can I pay with a different card?"))
print(bot.respond("Do you sell cardigans?"))
Output
I can't help with that here. I'm passing you to a human agent.
I can't help with that here. I'm passing you to a human agent.

The first reply is right. The second is wrong: Sunny passes a question about cardigans to a human because the word cardigans contains card. Keyword rules are brittle. An AI model is unreliable in a different way: it can give a confident, well-written answer that is false. Either way, you find out by testing with real messages, and you never assume a reply is correct because it sounds correct.

2. Failed tools

A tool can fail to give an answer. Here the order may not exist, so find_order_id returns None. In a real system the order database can also be slow or unavailable. A chatbot needs something sensible to say when a tool has no answer. Sunny asks for a valid order ID. It does not invent a status.

3. Sensitive data

self.history stores everything the user types. If a customer types a card number, that number is now in your list, and in any file or service you later send the history to. Sunny never asks for payment details and hands the conversation to a person when they come up. Collect only what you need, and know where it ends up.

4. Actions that need a person

Looking up a status changes nothing, so a wrong answer can be corrected. Changing a shipping address sends a real parcel somewhere else, and it is a common route for fraud. A good rule for a first agent: the chatbot may look things up, and a person approves anything that changes something. Week 12 builds that approval step properly.

What this module leaves out, and why

OOP is a large subject. You need a small part of it to build agents. These topics are left out on purpose:

  • Inheritance builds a new class on top of an existing one. A chatbot with a tool needs only has a, which is composition. It does not need is a kind of.
  • Abstract classes force a family of classes to share the same method names. That helps large teams and is more than a first agent needs.
  • Decorators are the lines starting with @ above a function. You can use one that a library gives you without knowing how to write your own.
  • Metaclasses are classes that build other classes. Almost no application code needs them.
  • Design patterns are named solutions for problems in large systems. They make sense after you have built a few programs and felt those problems yourself.

If you can write a class with __init__, attributes and methods, and hand one object to another, you know enough OOP to start building agents.

Week 11 sets up Ollama, a free program that runs an AI model on your own laptop. This preview shows how little of the class changes. Read it now and run it next week.

real_model_preview.py (optional)
from ollama import chat

MODEL = "granite4.1:3b"


class SupportChatbot:
    """The same chatbot shape, with a real local model choosing the reply."""

    def __init__(self, name, instructions):
        """Set up one chatbot with its own name, instructions, and history."""
        self.name = name
        self.instructions = instructions
        self.history = []

    def respond(self, user_message):
        """Record the user's message, get a reply, record it, and return it."""
        self.history.append({"role": "user", "content": user_message})
        reply = self.choose_reply()
        self.history.append({"role": "assistant", "content": reply})
        return reply

    def choose_reply(self):
        """Send the instructions and the whole history to the model."""
        messages = [{"role": "system", "content": self.instructions}]
        messages = messages + self.history
        response = chat(model=MODEL, messages=messages)
        return response.message.content


bot = SupportChatbot(
    "Sunny",
    "You are Sunny, a support assistant for Bayside Outfitters. "
    "Answer in one short sentence.",
)
print(bot.respond("Hello, my name is Dana."))
print(bot.respond("What is my name?"))
print(len(bot.history))
One run on the course model
Hello Dana, how may I assist you today?
Your name is Dana.
4

Only choose_reply changed. In place of keyword rules it sends the instructions and the whole history to a model and returns what the model writes. This is where instructions starts to matter: it is sent to the model at the start of every request. The second reply shows why the history matters: the model can answer What is my name? only because the earlier message is sent again.

A real model does not give the same reply every time, and it can be wrong. If Ollama is not running you will see ConnectionError: Failed to connect to Ollama. If the model has not been downloaded you will see model ... not found (status code: 404).

⚠ API keys stay out of your code

Ollama runs on your own machine, so it needs no key. Online AI services give you an API key, which works like a password that is billed to you. A key never goes in a source file or a GitHub repository. It belongs in an environment variable or in a file listed in .gitignore.

Answer
self.order_tool = order_tool — The chatbot is handed another object and keeps it so it can use it later.
Q8 · Multiple Choice
A method is written as def greet(): inside a class. What happens when you call bot.greet()?
  • a) It works normally
  • b) TypeError, because Python passes the object in and there is no parameter to receive it
  • c) NameError at the moment the class is defined
  • d) Python skips the method
Answer
TypeError, because Python passes the object in and there is no parameter to receive it — The message says the method takes 0 positional arguments but 1 was given. The 1 is the object.
Q9 · True / False
Putting a chatbot's code inside a class makes its replies more intelligent.
Answer
False — A class organizes code. The replies are exactly as good as the rules or the model that produce them.
Q10 · Multiple Choice
Which request should this week's chatbot pass to a human?
  • a) Where is order A100?
  • b) hello
  • c) Please change my shipping address
  • d) Where is my order?
Answer
Please change my shipping address — Looking up a status changes nothing. Changing an address changes where a parcel goes, so a person should approve it.
Q11 · Short Answer
Why is the order lookup a separate class, and not more code inside SupportChatbot?
Answer
Looking up orders and holding a conversation are different jobs. Keeping them in separate classes means each class stays short, the tool can be tested on its own, one tool can be shared by several chatbots, and you can replace the tool without changing the chatbot.
