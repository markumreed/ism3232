Turn a business rule into code in four steps

Plan on paper before you write any Python. Code with the wrong structure gives the wrong answer, however clean its syntax.

  1. Mark up the prompt. Underline each input, circle each rule, and box each value you must return or print. Circle the words "unless", "only if", and "except" twice.
  2. Name the limits and the variables. Every number in a rule becomes a constant in capitals. Every value you must calculate gets a variable name.
  3. Pick the structure. Match the wording of the prompt to a tool using the table below.
  4. Order the steps, then trace and test. Each value must be calculated above any line that uses it. Trace the given numbers by hand, then try the value on each side of every limit.

Conditionals: rules with more than one input

A business rule with an exception is still one decision. The exception becomes a second condition inside the same test, not a separate afterthought.

Bug report 1
A preferred customer paid 45 days late and was charged nothing

A supplier charges late fees on overdue invoices. Invoices paid on time owe nothing. Invoices 1 through 30 days late owe 2% of the invoice. Invoices more than 30 days late owe 5%. Preferred customers owe no fee, unless they are more than 30 days late.

A preferred customer paid a $1,200 invoice 45 days late, and this function charged nothing.

def calculate_late_fee(amount: float, days_late: int,
                       preferred: bool = False) -> float:
    if days_late == 0 or preferred:
        rate = 0.0
    elif days_late <= 30:
        rate = 0.02
    else:
        rate = 0.05
    return amount * rate

print(calculate_late_fee(1200.00, 45, preferred=True))    # prints 0.0

Find the bug before you open the answer.

Reveal the bug

The rule has two parts: preferred customers owe nothing, unless they are more than 30 days late. The code kept the first part and dropped the second, so preferred alone switches the fee off. A rule with an exception needs both conditions, joined with and.

FixTranslate the whole rule

The waiver now needs two things to be true: the customer is preferred and the invoice is no more than 30 days late. This version also names its limits as constants and adds the supplier's second rule: any fee that is charged is at least $10.

LATE_LIMIT_DAYS = 30
RATE_LATE       = 0.02
RATE_VERY_LATE  = 0.05
MINIMUM_FEE     = 10.00

def calculate_late_fee(amount: float, days_late: int,
                       preferred: bool = False) -> float:
    """Return the late fee for one invoice."""
    # Decision 1: choose the rate
    if days_late == 0 or (preferred and days_late <= LATE_LIMIT_DAYS):
        rate = 0.0
    elif days_late <= LATE_LIMIT_DAYS:
        rate = RATE_LATE
    else:
        rate = RATE_VERY_LATE

    fee = amount * rate

    # Decision 2: a separate rule, based on the calculated fee
    if fee > 0 and fee < MINIMUM_FEE:
        fee = MINIMUM_FEE

    return fee

Five calls check five different paths through the function:

print(f'{calculate_late_fee(1200.00, 0):.2f}')                    # on time
print(f'{calculate_late_fee(1200.00, 12):.2f}')                   # 12 days late
print(f'{calculate_late_fee(1200.00, 12, preferred=True):.2f}')   # preferred, 12 days late
print(f'{calculate_late_fee(1200.00, 45, preferred=True):.2f}')   # preferred, 45 days late
print(f'{calculate_late_fee(300.00, 12):.2f}')                    # 2% is $6.00, raised to the minimum

Five habits keep a multi-part rule safe:

  • Translate the whole sentence. Words like "unless", "only if", and "except" add a second condition. If your test has fewer conditions than the sentence, part of the rule is missing.
  • Use parentheses when a test mixes and with or. They show which parts belong together, to Python and to the person grading.
  • Name each limit once, as a constant. LATE_LIMIT_DAYS appears in two tests. Changing it in one place keeps both in step.
  • Check tiers in one direction. Go up with <= or down with >=, and never mix the two in one chain.
  • Read which value the rule names. The minimum applies to the calculated fee, not to the invoice amount, so that decision comes after the calculation.

Translate boundary words exactly

The rule saysWrite
up to 30 days, 30 or fewer, no more than 30<= 30
more than 30, over 30> 30
at least $10, $10 or more>= 10
under $10, less than $10< 10

Test both sides of every limit

Every limit has two neighbours, and a wrong comparison only shows up at one of them. These tests pass for the fixed function. Work out by hand why each one is true.

assert calculate_late_fee(1000.00, 30) == 20.00    # day 30 is still the 2% tier
assert calculate_late_fee(1000.00, 31) == 50.00    # day 31 moves to 5%
assert calculate_late_fee(1000.00, 30, preferred=True) == 0.0
assert calculate_late_fee(1000.00, 31, preferred=True) == 50.00
assert calculate_late_fee(500.00, 5) == 10.00      # 2% is exactly $10.00

Bug report 2
The report named the wrong top requester

Finance wants the largest purchase request and who made it. Casey asked for $2,200, the largest amount on the list. The report got the amount right and gave the credit to Morgan.

requests = [
    {'requester': 'Taylor', 'amount': 1250.00, 'status': 'Pending'},
    {'requester': 'Jordan', 'amount':  350.00, 'status': 'Approved'},
    {'requester': 'Casey',  'amount': 2200.00, 'status': 'Pending'},
    {'requester': 'Morgan', 'amount':  900.00, 'status': 'Pending'},
]

highest = 0.0
top_requester = ''

for r in requests:
    if r['amount'] > highest:
        highest = r['amount']
    top_requester = r['requester']

print(f'Largest request: ${highest:,.2f} by {top_requester}')
# Largest request: $2,200.00 by Morgan

Find the bug before you open the answer.

Reveal the bug

The line top_requester = r['requester'] sits outside the if, so it runs on every pass and ends up holding the last name on the list. Two variables that describe the same record must change together, inside the same if.

FixUpdate both together

Indent the name so it moves with the amount. The corrected loop also answers four more questions in the same pass, each with its own variable and its own if.

REVIEW_LIMIT = 1000.00

# Set up every answer before the loop
total = 0.0
pending_total = 0.0
needs_review = []
highest = 0.0
top_requester = ''

for r in requests:
    total += r['amount']

    if r['status'] == 'Pending':
        pending_total += r['amount']

    if r['amount'] > REVIEW_LIMIT:
        needs_review.append(r['requester'])

    if r['amount'] > highest:
        highest = r['amount']
        top_requester = r['requester']

# The average needs the finished total, so it comes after the loop
average = total / len(requests)

print(f'Total requested: ${total:,.2f}')
print(f'Pending total:   ${pending_total:,.2f}')
print(f'Needs review:    {needs_review}')
print(f'Largest request: ${highest:,.2f} by {top_requester}')
print(f'Average request: ${average:,.2f}')
Output
Total requested: $4,700.00
Pending total:   $4,350.00
Needs review:    ['Taylor', 'Casey']
Largest request: $2,200.00 by Casey
Average request: $1,175.00

Five checks work on any list of records:

  • Set up every answer before the loop. A number starts at 0, a list starts empty, a name starts as an empty string.
  • Give each question its own if. One request can be pending, over the limit, and the largest so far, all at once. An elif would let only one of those count.
  • Keep linked variables in step. A value and its label are updated on neighbouring lines, at the same indentation.
  • Finish before you divide. An average, a percentage, or any result that needs the final total belongs after the loop.
  • Read fields with their keys. Inside the loop it is r['amount']. A bare amount is a different variable, or no variable at all.

Functions: small functions that work together

A function does one job, takes what it needs as parameters, and returns its answer. Bigger jobs are built by one function calling another.

Example. A company pays hourly staff each week. Hours up to 40 are paid at the normal rate. Hours above 40 are paid at 1.5 times the rate.

REGULAR_HOURS       = 40
OVERTIME_MULTIPLIER = 1.5

def calculate_pay(hours: float, rate: float,
                  multiplier: float = OVERTIME_MULTIPLIER) -> float:
    """Return gross pay for one week. Hours above 40 earn overtime."""
    if hours <= REGULAR_HOURS:
        return hours * rate
    overtime_hours = hours - REGULAR_HOURS
    return REGULAR_HOURS * rate + overtime_hours * rate * multiplier

That function pays one person. A second function adds up a whole list by calling the first one for each timesheet.

Bug report 3
Payroll for four people came to one paycheck

Four timesheets went in. The total that came back was $1,000.00, which is exactly what Avery earned.

timesheets = [
    {'name': 'Avery', 'hours': 40, 'rate': 25.00},
    {'name': 'Blake', 'hours': 45, 'rate': 20.00},
    {'name': 'Devon', 'hours': 32, 'rate': 30.00},
    {'name': 'Emery', 'hours': 50, 'rate': 22.00},
]

def total_payroll(timesheets: list) -> float:
    total = 0.0
    for t in timesheets:
        total += calculate_pay(t['hours'], t['rate'])
        return total

print(f'Total payroll: ${total_payroll(timesheets):,.2f}')
# Total payroll: $1,000.00

Find the bug before you open the answer.

Reveal the bug

return is indented inside the loop, so the function hands back the total and stops during the first pass. A return ends the function immediately, even in the middle of a loop. It belongs one level out, lined up with for.

FixReturn after the loop

Move return out one level so the loop can finish. The function returns the total and prints nothing, so the script decides how to display it.

def total_payroll(timesheets: list) -> float:
    """Return total gross pay for a list of timesheet records."""
    total = 0.0
    for t in timesheets:
        total += calculate_pay(t['hours'], t['rate'])
    return total

payroll = total_payroll(timesheets)
print(f'Total payroll: ${payroll:,.2f}')
Output
Total payroll: $4,120.00

Check six things on any function answer:

  • One job per function. calculate_pay knows the overtime rule. total_payroll knows how to add up a list. Neither does the other's work.
  • Parameters in, return out. A function that reads a list defined somewhere else, or prints its answer instead of returning it, cannot be reused or tested.
  • Defaults go last. multiplier has a default value, so it comes after hours and rate.
  • return ends the function. Inside a loop it ends the loop too, so the final return lines up with for.
  • Catch what comes back. payroll = total_payroll(timesheets) stores the answer. A call on a line by itself throws it away.
  • Local names stay local. The total inside total_payroll does not exist outside it. The script sees only the returned value.

Test both sides of the limit

The overtime rule changes at 40 hours, so the tests sit at 40 and 41. The last test overrides the default multiplier.

assert calculate_pay(40, 20.00) == 800.00                    # exactly at the limit: no overtime
assert calculate_pay(41, 20.00) == 830.00                    # one hour over: 800 + 1 * 20 * 1.5
assert calculate_pay(0, 20.00) == 0.0
assert calculate_pay(45, 20.00, multiplier=2.0) == 1000.00   # 800 + 5 * 20 * 2.0

Why small functions beat one long script

Expect to explain this in a sentence or two. Four reasons are worth knowing:

  • One place to change. If overtime becomes double time, you edit one constant, not every line that calculates pay.
  • Consistency. Every timesheet goes through identical logic.
  • Readability. total_payroll reads like the business process it describes.
  • Testability. Each rule can be checked on its own with an assert, without running the whole script.

Tracing: be the computer

Tracing means running the code on paper one line at a time and writing down each variable as it changes. It is how you answer "what is the output?" questions, and how you check your own code without a laptop.

Trace a call chain in five moves

Follow Blake's timesheet (45 hours at $20.00) through the fixed code:

  1. The script calls total_payroll(timesheets) and waits for an answer.
  2. On the second pass of the loop, total_payroll calls calculate_pay(45, 20.00) and waits. multiplier takes its default, 1.5.
  3. Inside calculate_pay, 45 <= 40 is false. overtime_hours is 5, and the function returns 40 * 20.00 + 5 * 20.00 * 1.5, which is 950.0.
  4. Back in total_payroll, 950.0 is added to total, which goes from 1000.0 to 1950.0.
  5. After the fourth pass, return total sends 4120.0 back to the script, where it is stored in payroll.

Mistakes that cost points

These fourteen mistakes change what the program does, so neat handwriting will not save them. Read each one, predict what goes wrong, then open it to check.

Translating only half of a rule that says "unless" or "only if"

What goes wrong: The exception never applies, or always applies.

Fix: Count the conditions in the sentence, then count them in your test.

Mixing and with or without parentheses

What goes wrong: Python groups the parts differently from the way you read them.

Fix: Put parentheses around the parts that belong together.

Checking tiers in a mixed order

What goes wrong: A wide test near the top catches values meant for a tier below it.

Fix: Go up with <= or down with >=, all the way through.

> where the rule says "at least", or >= where it says "more than"

What goes wrong: The value exactly at the limit lands in the wrong tier.

Fix: Translate the words, then test the limit and the value next to it.

Testing the original input when the rule names a calculated value

What goes wrong: The second decision uses the wrong number.

Fix: Reread which value the rule names, and calculate it first.

Typing the same limit in several places instead of naming a constant

What goes wrong: One copy gets changed, the others do not, and the tiers stop agreeing.

Fix: One constant in capitals, used everywhere.

Setting up an accumulator inside the loop

What goes wrong: It resets on every pass, so only the last record counts.

Fix: Set it up above the for line.

Updating a value inside an if and its label outside it

What goes wrong: The label ends up describing the last record, not the winning one.

Fix: Update both on neighbouring lines at the same indentation.

Using elif between two questions that can both be true

What goes wrong: The second question is skipped whenever the first one is true.

Fix: A separate if for each question.

Writing == where you meant =

What goes wrong: r['status'] == 'Approved' on a line by itself compares, throws the answer away, and changes nothing.

Fix: One = to store a value, two to compare.

return indented inside a loop

What goes wrong: The function stops during the first pass.

Fix: Line the final return up with for.

print instead of return in a function

What goes wrong: The caller receives None, and every assert on the function fails.

Fix: Return the value and let the script print it.

Calling a function without storing what it returns

What goes wrong: The answer is thrown away, and the variable you passed in is unchanged.

Fix: balance = apply_fee(balance)

Using a function's local variable outside the function

What goes wrong: NameError, because the name only existed while the function ran.

Fix: Return the value and store it under a name in the script.

Practice 1: Event booking

Practice 1 · Conditionals with several inputs

A venue prices event bookings with these rules:

  • Events of up to 50 guests have a $400 room fee.
  • Events of 51 through 150 guests have a $900 room fee.
  • Events of more than 150 guests have a $1,600 room fee.
  • Weekend events add a 20% surcharge to the room fee.
  • Nonprofit clients have the weekend surcharge waived, but only for events of 150 guests or fewer.
  • A $150 cleaning deposit is added when the fee, after any surcharge, is $1,000 or more.

Write a function quote_booking(guests, is_weekend, nonprofit=False) that returns the total price for one booking. Name every limit and amount as a constant, and add type hints and a docstring.

Then write three lines that print the quote for each of these bookings:

  1. 120 guests, on a weekend, not a nonprofit
  2. 150 guests, on a weekend, nonprofit
  3. 151 guests, on a weekend, nonprofit

Finally, write two assert tests for the 50-guest limit: one exactly at it and one just above it, both on a weekday.

Practice 3: Subscription billing

Practice 3 · Functions that work together
