Learning objectives

  • Explain in plain language what a class and an object are.
  • Write a class with __init__, attributes and methods, and say what self refers to.
  • Create several objects from one class and explain why their data differs.
  • Give a chatbot a separate tool to use (composition), and say why the tool is its own class.
  • Trace one user message from respond to the reply.
  • Name four things a business chatbot can get wrong: unreliable output, failed tools, sensitive data, and actions that need a person.

Part 2 · 0:12–0:24

Write the Tool

Teaching goal: a first complete class with __init__, one attribute and two methods, written before the chatbot so students meet the syntax on the simpler class. Say to the class: "A tool is a piece of code the chatbot can use. This one knows about orders. Notice what it does not know: anything about chatting."

Four new pieces of syntax — one small class

Concept

class OrderLookup: — begins a class, like def begins a function. This is a template. Nothing exists yet.

def __init__(self, orders): — the initializer. You never call it by name. It runs once when you write OrderLookup(...).

self — the object the method is working on. Every method lists it first. You do not pass it; Python does.

self.orders = orders — stores a parameter as an attribute. The parameter disappears when __init__ ends. The attribute stays on the object.

Line by line: class OrderLookup: starts the template. The docstring describes the class, the same convention as Week 7's function docstrings. __init__ stores the orders dictionary. find_order_id loops over the known IDs and returns the first one found in the text; text.upper() makes an uppercase copy so a100 matches. find_status returns the status or None. Looping over a dictionary gives its keys: Week 6.

Live-code — order_tool.py: the OrderLookup class

class OrderLookup: """A tool that knows about orders. It knows nothing about chatting.""" def __init__(self, orders): self.orders = orders def find_order_id(self, text): for order_id in self.orders: if order_id in text.upper(): return order_id return None def find_status(self, order_id): if order_id in self.orders: return self.orders[order_id] return None order_tool = OrderLookup({"A100": "shipped", "A101": "processing"}) print(order_tool.find_order_id("Where is order a100?")) print(order_tool.find_status("A100")) print(order_tool.find_order_id("Where is my order?")) print(order_tool.find_status("A999"))

The class matches the lab page's order_tool.py. The five lines at the bottom are a quick check that would not live in the file. Press Run.

Students type the class into order_tool.py, then check it in the Python shell as the lab page shows. Here the check is inline because each block in this deck is a fresh, standalone script.

Expected output

A100
shipped
None
None

a100 is found as A100. Its status is shipped. A message with no known ID gives None, and so does an unknown order.

Verified against python3 3.12. None is the tool saying it has no answer. That is the seed of the failed-tools risk discussed in Part 5.

Knowledge check

What does order_tool.find_status("A999") return when there is no order A999?

None. The method checks if order_id in self.orders first and falls through to return None. A tool that returns None lets the chatbot decide what to say. A tool that crashes takes the whole conversation down with it.

Follow-up: what would self.orders["A999"] do without the if? KeyError, the Week 8 bug.

Common student mistakes

Watch for

Leaving self out of a method's parameter list. The class still defines without error; the failure comes later, on the call.

Writing orders = orders in __init__. Without self. nothing is stored on the object.

Putting conversation text such as “Order A100 is shipped.” inside the tool. The tool returns data. The chatbot decides the wording.

The third one is the first appearance of this week's design idea: one class, one job.
Part 3 · 0:24–0:40

Write the Chatbot

Teaching goal: build SupportChatbot in three moves. First it stores data. Then it responds and remembers. Then it is handed the tool. Say to the class: "Same syntax as the tool, with more to remember and more to do. Watch for the one line that connects the two classes."

Step 1 — a class that only stores data

class SupportChatbot: """A support chatbot. Step 1: it only stores data.""" def __init__(self, name, instructions): self.name = name self.instructions = instructions self.history = [] bot = SupportChatbot("Sunny", "You are a friendly support assistant.") print(bot.name) print(bot.instructions) print(bot.history)

Three attributes. Two are passed in. history always starts as an empty list. Press Run.

Two values are passed and the method has three parameters. Ask who supplies the third. Python does: it passes the new object as self.

Expected output

Sunny
You are a friendly support assistant.
[]

bot.name reads the name that belongs to this object. The history is empty because nothing has been said yet.

Cold-call: which is the class and which is the object? SupportChatbot is the class. bot is the object.

Step 2 — a method that responds and remembers

class SupportChatbot: """A support chatbot. Step 2: it can respond and remember.""" def __init__(self, name, instructions): self.name = name self.instructions = instructions self.history = [] def respond(self, user_message): self.history.append({"role": "user", "content": user_message}) reply = self.choose_reply(user_message) self.history.append({"role": "assistant", "content": reply}) return reply def choose_reply(self, user_message): text = user_message.lower() if "hello" in text: return f"Hello! I'm {self.name}." return "I'm not sure how to help with that." bot = SupportChatbot("Sunny", "You are a friendly support assistant.") print(bot.respond("Hello there")) print(bot.respond("Where is my order?")) print(len(bot.history)) print(bot.history[0])

respond records the message, gets a reply, records the reply, and returns it. choose_reply is the mock: two rules. Press Run.

self.choose_reply(...) is one method calling another on the same object. Inside a class you reach your own methods through self. Each history entry is a dictionary with a role and a content. Real AI services expect this same shape, which is why we use it now.

Expected output

Hello! I'm Sunny.
I'm not sure how to help with that.
4
{'role': 'user', 'content': 'Hello there'}

Two messages in, four history entries: two from the user and two from the chatbot.

Ask what bot.history[1] holds: the assistant's greeting.

The missing-self bug on purpose

class SupportChatbot: def __init__(self, name, instructions): self.name = name self.instructions = instructions self.history = [] def greet(): # BUG: no self in the parameter list return f"Hello! I'm {self.name}." bot = SupportChatbot("Sunny", "You are a friendly support assistant.") print(bot.greet())

greet is defined with no self. The class defines without any error. Press Run and read the last line of the traceback.

Python checks the number of arguments when the method is called, not when it is defined. bot.greet() passes bot in automatically, and there is no parameter to receive it. Have a student say that in their own words.

What it raises

Traceback (most recent call last):
  ...
TypeError: SupportChatbot.greet() takes 0 positional arguments but 1 was given

The load-bearing line is the last one. The “1 was given” is bot itself. In the browser the file name and line number differ from a real python3 run; the error type and message are what matter.

Fix: def greet(self):. This is the single most common error in the first week of classes. Students who have seen it once recognize it for the rest of the term.

Composition — the chatbot is handed a tool

Concept

Composition means giving one object another object to use. The chatbot has a tool.

self.order_tool = order_tool — the whole idea in one line. The tool is stored on the chatbot like any other attribute.

self.order_tool.find_order_id(...) — read it left to right: this chatbot's tool, its find_order_id method.

The chatbot never creates its own tool. It is handed one. That is why a test can hand it a small one with two made-up orders.

Say to the class: "The chatbot does not contain the order code. It holds a tool and asks it questions." This is the only relationship between classes that this module teaches. Inheritance is left out on purpose: a chatbot with a tool needs has a, not is a kind of.

Knowledge check

In bot.respond("hello"), what does self refer to inside respond?

self is the object on the left of the dot. In bot.respond(...) it is bot. In river.respond(...) it would be river. The same method works on whichever object it is called on.

If a student answers B, return to the board: the class is the template, bot is the thing made from it.

Knowledge check

Which line is the composition?

The chatbot is handed another object and keeps it so it can use it later. self.history = [] creates a plain list, and text is a local variable.

Extension: why is the tool passed in, and not created inside __init__? So the caller chooses the tool: real data in main.py, two made-up orders in a test.

Common student mistakes

Watch for

Calling a method on the class: SupportChatbot.respond("hello"). The class is the template. Call methods on the object you created.

Writing choose_reply(user_message) inside respond without self.. That fails with NameError, because the method belongs to the object.

Believing the instructions change the replies. In this mock they are stored and never read. They start to matter next week, when they are sent to a model.

Misconceptions to listen for: “the class is the chatbot”; “self is something I pass in”; “using a class makes it AI”.

tests/test_chatbot.py — eight tests

from chatbot import SupportChatbot
from order_tool import OrderLookup


def make_bot():
    """Build a fresh chatbot with its own tool for each test."""
    orders = {"A100": "shipped", "A101": "processing"}
    return SupportChatbot("Sunny", "Be friendly.", OrderLookup(orders))


def test_tool_finds_known_status():
    tool = OrderLookup({"A100": "shipped"})
    assert tool.find_status("A100") == "shipped"


def test_tool_returns_none_for_unknown_order():
    tool = OrderLookup({"A100": "shipped"})
    assert tool.find_status("A999") is None


def test_respond_records_both_messages():
    bot = make_bot()
    bot.respond("hello")
    assert len(bot.history) == 2
    assert bot.history[0]["role"] == "user"
    assert bot.history[1]["role"] == "assistant"


def test_order_question_uses_the_tool():
    bot = make_bot()
    assert bot.respond("Where is order A100?") == "Order A100 is shipped."


def test_order_question_without_an_id_asks_for_one():
    bot = make_bot()
    assert "order ID" in bot.respond("Where is my order?")


def test_address_change_goes_to_a_human():
    bot = make_bot()
    assert "human" in bot.respond("Please change my shipping address")


def test_unknown_request_gets_a_safe_reply():
    bot = make_bot()
    assert "not sure" in bot.respond("What is the weather today?")


def test_two_chatbots_keep_separate_histories():
    first = make_bot()
    second = make_bot()
    first.respond("hello")
    assert len(first.history) == 2
    assert len(second.history) == 0

Shown static — pytest has no runner in the browser. Type this into tests/test_chatbot.py and run pytest -v on your own machine.

make_bot() builds a fresh chatbot with a two-order tool for each test. That is composition paying off: the test chooses the tool. The last test is the independence test: one chatbot's messages never appear in another's history.

Why does make_bot() hand the chatbot a tool with only two made-up orders?

The chatbot is handed its tool, so a test can hand it a small one. If the chatbot created its own tool from the real data, every test would depend on that data.

Teaching goal: every student leaves knowing what the mini-project requires and how it is checked.

Mini-project — an assistant of your own

What to build

Choose an FAQ assistant, an appointment helper, an order-status assistant for a different business, or an approved idea of your own.

Two classes in two files: a tool that knows the data, and an assistant that is handed the tool and keeps a history.

It must: accept typed messages until quit; answer one kind of request with the tool; reply helpfully when a lookup finds nothing; say so when it cannot help; pass one kind of request to a person.

Also: at least four tests, and a short README section on what is mock and what could go wrong with real customer data.

The lab page has the checklist, a sample interaction, a 10-point rubric and a reference solution (an appointment helper) that opens on a click. Tell students to compare with it after they have a working version, and to build for a different business. Ask two or three students what business they will pick and what its tool would know.
