Say to the class (verbatim): "One class, five new pieces of syntax. Five new pieces of syntax — one class

Concept

class BusinessRequest: — begins a class definition, like def begins a function. This is a blueprint, not yet a real object — nothing exists in memory as a "business request" until Part 2 builds one from it.

def __init__(self, ...): — the constructor. Never called directly by name; it runs automatically, once, whenever BusinessRequest(...) is called. Double underscores mark it a special method Python itself recognises.

self — the single most important word in this lab. It refers to this specific object being created or acted on. Every method takes it first, because that is how Python passes "which object is this method being called on" in automatically. Mechanically: req_101.approve() is secretly BusinessRequest.approve(req_101).

self.request_id = request_id — stores a plain parameter as an attribute of this object. The parameter and the attribute share a name but are not the same thing: the parameter lives only while __init__ runs; the attribute persists on the object.

def __repr__(self): — another special method, controlling what print() shows. Without it, printing an object shows <models.BusinessRequest object at 0x...> — a memory address, not useful information.

Line-by-line (guide, Part 1): - class BusinessRequest: — class begins a definition like def; a blueprint, nothing in memory yet. - """Represents a single business purchase or travel request.""" — a docstring for the class itself, same convention as Week 7's function docstrings, now at class level. - def __init__(self, request_id, requester, category, amount): — the constructor, called automatically the moment a new object is created. Not called directly by name anywhere in this lab. Double underscores = special method Python recognises and calls at a specific moment. - self — explain more than once, more than one way. self refers to this specific object; when Part 2 runs req_101 = BusinessRequest(101, 'Taylor', 'Travel', 1200), inside __init__ self is req_101, even though it doesn't have that name yet. Mechanical framing: req_101.approve() == BusinessRequest.approve(req_101) — Python passes req_101 in as self; dot-notation just hides that first argument. Write both forms on the board. - self.request_id = request_id (and the three below) — stores a parameter as an attribute of this object, later readable as self.request_id inside any method or req_101.request_id from outside. The parameter and the attribute are not the same thing despite the shared name. - self.status = 'Pending' # default — takes no parameter; every new BusinessRequest starts with status = 'Pending' unconditionally. This answers Part 3's reflection question 5 — flag that connection now. - def approve(self): — an instance method; still takes self first, no other parameters. self.status = 'Approved' modifies this specific object's status, permanently. - def requires_review(self): — return self.amount > 1000 reads (not modifies) this object's own amount, the same comparison as Week 7's standalone function, now living inside the object. - def __repr__(self): — special method controlling what print() shows; without it, a BusinessRequest prints as <models.BusinessRequest object at 0x...>. This __repr__ builds a readable string from the object's current attribute values. Common mistakes: forgetting self as the first parameter (doesn't error at definition, fails confusingly on the call — TypeError: ... takes 0 positional arguments but 1 was given); confusing self.amount with a bare amount; writing def __init__(self): with no parameters and hardcoding values, producing identical instances. Check for understanding: see the Part 1 divider notes — removing self from requires_review then calling it raises TypeError about too many arguments.

The missing-self bug on purpose — what the CFU asks about

class BusinessRequest: """Represents a single business purchase or travel request.""" def __init__(self, request_id, requester, category, amount): self.request_id = request_id self.requester = requester self.category = category self.amount = amount self.status = 'Pending' def requires_review(): # BUG: no self in the parameter list return self.amount > 1000 req_101 = BusinessRequest(101, 'Taylor', 'Travel', 1200) print(req_101.requires_review())

This is the guide's Part 1 check-for-understanding, done live: requires_review is defined with no self. The class still defines fine — the failure only happens on the call. Press Run and read the last line of the traceback.

The definition def requires_review(): does not error — Python only checks the argument count when the method is called. req_101.requires_review() is secretly BusinessRequest.requires_review(req_101), so Python passes one argument (req_101) into a method whose parameter list has zero slots. Make a student say "the call passes self in automatically; there's no parameter to catch it," not just "it broke."

Fixed — self restored as the first parameter

The single change from the broken block is adding self back. Takeaway: every method inside a class takes self as its first parameter — not by developer choice, but because that is how Python hands the method "which object am I acting on."

Part 2 · 0:20–0:32

Create Instances

Teaching goal: create three genuinely independent objects from the same class, call methods on them, and witness — concretely, not just by assertion — that changing one never affects the others. Say to the class (verbatim): "Three requests, from the same blueprint, about to become three genuinely separate things in memory. Watch closely when we approve one and reject another — the third stays completely untouched. This is the payoff of everything in Part 1." Check for understanding (asked at the end of this part): "If I added a fourth line, req_104 = req_101, and then called req_104.approve(), would req_101.status also become 'Approved'?" Answer: Yes — req_104 = req_101 doesn't create a new object at all, it just gives a second name to the same existing object; req_104.approve() and req_101.approve() would be indistinguishable. Contrast with BusinessRequest(101, ...) called a second time, which would create a genuinely new, independent object even with identical data.

Three calls, three separate objects in memory

Concept

req_101 = BusinessRequest(101, 'Taylor', 'Travel', 1200) is where __init__ actually runs — once, right now — with self bound to whatever req_101 ends up naming. Three separate calls create three separate objects, each with its own independent set of attributes, even though all three come from the same blueprint.

print(req_101) fires __repr__ automatically — print() on any object calls __repr__ (or the related __str__, not covered today) to decide what to show. This isn't special handling for this class; it's general Python behaviour this class customises.

req_101.approve() and req_102.reject() touch only their own object. There is no code anywhere that could make them reach req_103 — which is exactly why req_103.status is still 'Pending' at the end.

Line-by-line (guide, Part 2): - from models import BusinessRequest — importing the class itself (not a function) from the local module; same import mechanics as Week 7. - req_101 = BusinessRequest(101, 'Taylor', 'Travel', 1200) — __init__ runs here, once; self inside that run is whatever req_101 refers to. Three calls, three separate objects with independent attributes. - print(req_101) (before any methods) — __repr__ fires; a general Python behaviour, not something print() does specially for this class. - req_101.requires_review(), req_102.requires_review() — same method, two objects, two results (True for the $1,200 request, False for the $450 one) because each call's self is a different object with its own amount. - req_101.approve(), req_102.reject() — pause here dramatically. Neither call touches req_103; there is no code that could. - the three status prints — concrete proof of independence: 'Approved', 'Rejected', and 'Pending' (unaffected). Say explicitly, pointing at the final two __repr__ lines: "__repr__ picks up the current status automatically — req_101's printed representation now says Approved, not Pending, even though we never touched __repr__. It reads self.status fresh every time it's called." Common mistakes: expecting req_103.status to have changed from a vague sense that "something happened"; confusing the variable names (req_101…) with the request_id values (101…) — they correspond numerically here by deliberate readability choice, not a rule. Check for understanding: req_104 = req_101 then req_104.approve() — yes, req_101.status also becomes 'Approved', because it is a second name for the same object, not a new one.

def test_default_status_is_pending():
    req = BusinessRequest(1, 'Test', 'Travel', 500)
    assert req.status == 'Pending'

def test_approve_changes_status():
    req = BusinessRequest(2, 'Test', 'Travel', 500)
    req.approve()
    assert req.status == 'Approved'

def test_reject_changes_status():
    req = BusinessRequest(3, 'Test', 'Travel', 500)
    req.reject()
    assert req.status == 'Rejected'

def test_requires_review_over_limit():
    req = BusinessRequest(4, 'Test', 'Travel', 1500)
    assert req.requires_review() is True

def test_requires_review_under_limit():
    req = BusinessRequest(5, 'Test', 'Travel', 500)
    assert req.requires_review() is False

def test_requires_review_at_boundary():
    req = BusinessRequest(6, 'Test', 'Travel', 1000)
    assert req.requires_review() is False  # > not >=

def test_instances_are_independent():
    req1 = BusinessRequest(7, 'A', 'Travel', 500)
    req2 = BusinessRequest(8, 'B', 'Travel', 500)
    req1.approve()
    assert req2.status == 'Pending'

Live-code — add summary() to BusinessRequest

class BusinessRequest: """Represents a single business purchase or travel request.""" def __init__(self, request_id, requester, category, amount): self.request_id = request_id self.requester = requester self.category = category self.amount = amount self.status = 'Pending' def approve(self): """Mark this request as approved.""" self.status = 'Approved' def summary(self): """Return a one-line, human-readable summary of this request.""" return f'Request {self.request_id} by {self.requester} | {self.category} | ${self.amount:,.2f} | {self.status}' req_101 = BusinessRequest(101, 'Taylor', 'Travel', 1200) req_101.approve() print(req_101.summary())

A new method on an existing, working class. summary() reads all five of the object's attributes at once and formats them into one line — ${self.amount:,.2f} gives a thousands separator and two decimals. Called after approve(), so the status reads Approved.

Line by line: summary(self) takes only self — no outside information needed. f'Request {self.request_id} by {self.requester} | {self.category} | ${self.amount:,.2f} | {self.status}' pulls together request_id, requester, category, amount (formatted 1,200.00), and the current status. req_101.approve() runs first, so self.status is 'Approved' when summary() reads it. This is a natural use for a method: pulling together everything an object knows about itself into one readable output.
