Part 1 · 0:04–0:22

Virtual Environment Workflow

Teaching goal: create, activate, and populate a venv — and, critically, prove its isolation concretely, not just assert it. Say to the class: "Three steps: create, activate, verify it's actually isolated — not just trust that it is." Setup just before this: students are in ~/ism3232/module02_zsh from Weeks 1–2. Everything in Part 1 happens there. Check for understanding (asked at the end of this part): "If you closed this terminal entirely and opened a brand new one tomorrow, would the venv still be active?" Answer: No — activation is a per-session shell state, not a permanent setting; source .venv/bin/activate needs to be re-run every time you open a new terminal and want to work on this project. "Why isn't my venv active anymore" is one of the most common beginner Python questions.

The idea

Concept

A venv is a private room for one project. Activate = walk in; every package installs on that room's shelves only. Deactivate = walk out; other projects are untouched.

python3 -m venv .venv creates a folder holding its own copy of the Python interpreter and its own place to install packages — nothing installed inside touches the system-wide Python. The leading dot makes it hidden (Week 2's ls -la lesson).

source .venv/bin/activate is the step that actually "walks into the room": source runs the activation script in the current shell, editing PATH so python3 and pip resolve to the venv's copies first. The (.venv) prompt prefix is your visual confirmation — train yourself to glance at it reflexively.

Emphasise: the (.venv) prefix is worth training yourself to glance at reflexively, the same way Week 1 trained checking for % vs $. A fresh venv starts essentially empty, deliberately, so whatever gets installed next is fully visible and attributable to this specific project.

Live-code — create, activate, verify (run on your own machine)

cd ~/ism3232/module02_zsh python3 -m venv .venv source .venv/bin/activate # Prompt should now show (.venv) which python3 # should point inside .venv/ pip list # should show minimal packages

Shown for reference — python -m venv, source, and pip can't execute in the browser. Run this in the VS Code integrated terminal on your own machine; the next slide shows the shape of a correct result.

Line by line: - python3 -m venv .venv — -m venv runs Python's built-in venv module, which creates a new, self-contained Python environment inside a folder named .venv. This folder now contains its own copy of the Python interpreter and its own separate place to install packages — nothing installed here touches the system-wide Python. - source .venv/bin/activate — this is the step that actually "walks into the room." source runs a script in the current shell session (rather than a separate subprocess, which is why the effect persists) — the activation script modifies your shell's PATH so that python3 and pip now resolve to the venv's copies first. - The (.venv) prefix appearing in the prompt — a visual confirmation, built into most shell configurations, that a venv is currently active. - which python3 — Week 1's command, now revealing something new: instead of a system path like /usr/bin/python3 or /opt/homebrew/bin/python3, it should now point inside the .venv folder itself — the first concrete, checkable proof that activation changed something. - pip list — should show only a minimal handful of packages (pip itself, maybe setuptools) — a fresh venv starts essentially empty. Common mistake: running pip install before activating — installs to the system Python instead. If a student's which python3 didn't show a .venv path, stop and fix activation before installing anything. Forgetting source and running .venv/bin/activate directly runs the script in a subprocess that exits immediately — the (.venv) prefix simply won't appear, which is the tell.

The payoff — "isolated" is a checkable fact

Concept

Open a second terminal tab and do not activate the venv. In it, which python3 points to the system interpreter and pip list does not include pytest or ruff.

That second terminal never ran source .venv/bin/activate — so the two tabs resolve python3 to different interpreters, right now, on the same machine. That is what "isolated" concretely means: not a promise, a checkable fact about two sessions.

Say explicitly, since this is the exercise's real payoff: "This second terminal never ran source .venv/bin/activate — and which python3 proves it's using a completely different interpreter, and pip list proves pytest/ruff simply aren't there. This is what 'isolated' concretely means: not a promise, a checkable fact about two different terminal sessions on the same machine, right now." Common mistake: checking isolation in the same terminal tab instead of a genuinely separate one — this doesn't test anything, since the same terminal still has the venv active. The isolation check specifically requires a fresh, non-activated session.

.gitignore

Teaching goal: create a .gitignore before any files are committed, specifically to keep .venv/ out of version control — and understand why committing a venv is a genuine mistake, not just a style preference. Say to the class: "One rule, stated as absolutely as anything in this course: .venv/ must never be committed to Git. We're creating the .gitignore now, before Week 4's first commit, specifically so this mistake never happens." Check for understanding (asked at the end of this part): "If a classmate cloned your GitHub repo and it had properly excluded .venv/, what would they need to run to get a working environment on their own machine?" Answer: python3 -m venv .venv, source .venv/bin/activate, then pip install -r requirements.txt — exactly the Stretch section's sequence.

The idea

One rule

.venv/ must never be committed to Git. Create the .gitignore now — before Week 4's first commit — so the mistake never happens.

A venv folder can be hundreds of megabytes, is regeneratable from requirements.txt in seconds, and often contains machine-specific paths and binaries that won't work on another computer. Committing it bloats the repo with something that gives a collaborator zero value and can actively break on their machine.

First line uses a single > (nothing to preserve yet); the next two use >> to append — because the file now has content that must not be overwritten. Week 2's overwrite-vs-append distinction, now with real consequences.

Ask the room explicitly: "what would happen if I'd used > instead of >> on these last two lines?" Each would have erased the previous line, leaving .gitignore with only the single most recent entry. __pycache__/ and *.pyc are Python's automatically-generated compiled bytecode files — pure clutter, regenerated automatically, never something a human wrote.

Live-code — this one runs here

cd ~/ism3232/module02_zsh echo '.venv/' > .gitignore echo '__pycache__/' >> .gitignore echo '*.pyc' >> .gitignore cat .gitignore ls -la

echo, >, >>, cat and ls -la all run in the emulator. Watch the single > create the file, then the two >> append to it.

Line by line: - echo '.venv/' > .gitignore — Week 2's redirect operator, creating a brand-new .gitignore with one line — note the single >, correctly, since this is the first line and there's nothing to preserve yet. - echo '__pycache__/' >> .gitignore and echo '*.pyc' >> .gitignore — Week 2 Stretch's append operator, >>, used correctly here specifically because the file already has content from the line above that must be preserved, not overwritten. - cat .gitignore — confirms all three lines landed in order. - ls -la — .gitignore and .venv both appear (both hidden dot-entries, shown by -a). Common mistake: creating .gitignore after already running git add . on a prior commit that included .venv/ — once a file is tracked, adding it to .gitignore afterward does not untrack it (needs git rm -r --cached .venv, not covered here). This is exactly why the lab's sequencing — .gitignore in Week 3, before Week 4's first commit — is deliberate.

.zshrc Aliases and Functions

Teaching goal: add custom aliases and a shell function to .zshrc, apply changes without restarting the terminal, and verify each one — building the exact shorthand vocabulary Week 4's Git ritual will lean on. Say to the class: "Second half of today: customizing the shell itself. .zshrc is a configuration file that runs every time you open a new terminal — anything you put here becomes available every session, automatically. We're adding nine shortcuts today, and I want every single one tested before we move on, not just typed and assumed correct." Check for understanding (asked at the end of this part): "If you typed gs in a folder that isn't a Git repository yet, what would happen?" Answer: git status would report something like fatal: not a git repository — the alias still runs the underlying command exactly as typed; it has no awareness of whether that command will succeed in the current context.

The idea

Concept

An alias is a simple text substitution: typing ll runs ls -la exactly as if you'd typed it out. Pure shorthand — no new functionality.

gs, ga, gcmsg, gp, gl are the Git shorthand Week 4's ritual will use — that's why these particular five were chosen.

mkcd() is a function, not an alias — a different mechanism. It takes an argument ($1 = the first word typed after mkcd) and runs multiple commands: mkdir -p "$1" then, only if that succeeded (&&), cd "$1". It replaces the two-step mkdir foldername then cd foldername pattern used in every lab so far.

-p on mkdir (new here) means "create any necessary parent folders too, and don't error if it already exists." && means "run the next command only if the first one succeeded." source ~/.zshrc is the step students most often forget: .zshrc only runs automatically when a new terminal session starts, so an already-open terminal needs source to re-run the file's contents into the current session. Closing and reopening the terminal achieves the same effect, but source is faster and doesn't lose your location/history.

Edit ~/.zshrc — add these lines, delete nothing (run on your own machine)

code ~/.zshrc # ISM3232 required aliases alias ll='ls -la' alias c='clear' alias py='python3' alias gs='git status' alias ga='git add .' alias gcmsg='git commit -m' alias gp='git push' alias gl='git log --oneline' alias tree2='tree -L 2' # Required shell function mkcd() { mkdir -p "$1" && cd "$1" }

Shown for reference — editing ~/.zshrc and defining alias/functions can't execute in the browser. Append these lines in VS Code; do not delete anything already in the file.

Line by line: - alias ll='ls -la' — an alias is a simple text substitution: typing ll from now on runs ls -la. Purely a shorthand, not new functionality. - alias gs='git status', ga='git add .', gcmsg='git commit -m', gp='git push', gl='git log --oneline' — these five specifically are the Git shorthand Week 4's ritual will use — flag this connection now, since it won't be obvious why these five were chosen until next week's lab makes them load-bearing. - mkcd() { mkdir -p "$1" && cd "$1" } — a shell function, not an alias. It takes an argument ($1 = the first word typed after mkcd) and runs multiple commands: mkdir -p "$1" creates a folder named whatever was typed (the -p flag means "create parent folders too, don't error if it exists"); && means "run the next command only if the first succeeded"; cd "$1" then moves into that folder. This single command replaces the two-step mkdir then cd pattern used in every lab so far. Common mistake: deleting or overwriting existing .zshrc content while adding the new lines — append, don't replace. Have unsure students run cat ~/.zshrc before editing to see the starting state. A typo (mismatched quotes, missing =) can make the entire .zshrc fail to load on every new terminal — walk through the added lines character by character if an error appears on terminal open.

Line by line: - source ~/.zshrc — the step students most often forget. .zshrc only runs automatically when a new terminal session starts; since this terminal was already open when the file was edited, the new aliases don't exist in it until source re-runs the file's contents into the current session. - ll — tests the simplest alias first; if this doesn't work, source ~/.zshrc likely didn't run, or there's a typo in the edit. - mkcd testdir then pwd — the real test of the function: pwd should now show a path ending in .../testdir, proving both that the folder was created and that cd genuinely happened inside the same function call. Common mistake: forgetting source ~/.zshrc after saving, then being confused that the new aliases "don't work" — the fix is almost always just running source ~/.zshrc, not re-editing the file.
