Section 2

Tables from Questions

Start from what customers ask, never from tables.

Questions become tables

  • Has A101 shipped yet? → an order → orders, found by order_id
  • Is the day pack in stock? → a product → products, found by name
  • What happened to my address change? → a request → change_requests, found by number
Each question points to a kind of record; each kind of record is a table; the value you look it up by is the primary key.

⌨ schema.sql

-- schema.sql
-- Bayside Outfitters: orders, products, and changes waiting for staff.

CREATE TABLE IF NOT EXISTS orders (
    order_id TEXT PRIMARY KEY,
    customer TEXT NOT NULL,
    item     TEXT NOT NULL,
    status   TEXT NOT NULL,
    address  TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS products (
    name  TEXT PRIMARY KEY,
    price REAL NOT NULL,
    stock INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS change_requests (
    number      INTEGER PRIMARY KEY AUTOINCREMENT,
    order_id    TEXT NOT NULL,
    new_address TEXT NOT NULL,
    status      TEXT NOT NULL DEFAULT 'waiting'
);

INSERT OR IGNORE INTO orders (order_id, customer, item, status, address) VALUES
    ('A100', 'Dana Cruz', 'rain jacket', 'shipped', '14 Bay Road'),
    ('A101', 'Sam Okafor', 'day pack', 'processing', '3 Gull Lane'),
    ('A102', 'Lee Park', 'trail hat', 'delivered', '88 Pier Street'),
    ('A103', 'Ana Silva', 'fleece vest', 'processing', '21 Harbor Way'),
    ('A104', 'Max Duarte', 'water bottle', 'shipped', '7 Dune Court'),
    ('A105', 'Ivy Chen', 'hiking socks', 'delivered', '40 Tide Street');

INSERT OR IGNORE INTO products (name, price, stock) VALUES
    ('rain jacket', 89.00, 12),
    ('day pack', 45.00, 0),
    ('trail hat', 25.00, 5),
    ('fleece vest', 60.00, 8),
    ('water bottle', 18.00, 30),
    ('hiking socks', 12.00, 0);
Read it top to bottom: types, one primary key per table, NOT NULL, the default status, AUTOINCREMENT for request numbers, INSERT OR IGNORE for sample rows.

⌨ A first look

SQLite version 3.45.1 2024-01-30 16:01:20
Enter ".help" for usage hints.
sqlite> .read schema.sql
sqlite> .tables
change_requests  orders           products       
sqlite> .schema products
CREATE TABLE products (
    name  TEXT PRIMARY KEY,
    price REAL NOT NULL,
    stock INTEGER NOT NULL
);
sqlite> SELECT * FROM products;
rain jacket|89.0|12
day pack|45.0|0
trail hat|25.0|5
fleece vest|60.0|8
water bottle|18.0|30
hiking socks|12.0|0
Dot-commands talk to the shell; SQL ends with a semicolon. Default output separates values with a bar.

⌨ Readable output, then choosing columns

sqlite> .read schema.sql
sqlite> .mode column
sqlite> .headers on
sqlite> SELECT order_id, customer, status FROM orders;
order_id  customer    status    
--------  ----------  ----------
A100      Dana Cruz   shipped   
A101      Sam Okafor  processing
A102      Lee Park    delivered 
A103      Ana Silva   processing
A104      Max Duarte  shipped   
A105      Ivy Chen    delivered
.mode column lines values up; .headers on names each column.

⌨ WHERE keeps matching rows

sqlite> SELECT order_id, item FROM orders WHERE status = 'shipped';
order_id  item        
--------  ------------
A100      rain jacket 
A104      water bottle
Text values go in single quotes.

⌨ ORDER BY sorts

sqlite> SELECT name, price FROM products ORDER BY price DESC;
name          price
------------  -----
rain jacket   89.0 
fleece vest   60.0 
day pack      45.0 
trail hat     25.0 
water bottle  18.0 
hiking socks  12.0
DESC means largest first.

⌨ COUNT and GROUP BY

sqlite> SELECT COUNT(*) FROM products WHERE stock = 0;
COUNT(*)
--------
2       
sqlite> SELECT stock, COUNT(*) FROM products GROUP BY stock;
stock  COUNT(*)
-----  --------
0      2       
5      1       
8      1       
12     1       
30     1
GROUP BY stock puts both out-of-stock products in one row. Ask which question a GROUP BY on status would answer; students write that one in the lab.
Section 4

Changing Rows Safely

UPDATE with and without WHERE, INSERT, and reading the schema twice. Run them live in this order in one database.

⌨ UPDATE with WHERE

sqlite> UPDATE products SET stock = 20 WHERE name = 'day pack';
sqlite> SELECT name, stock FROM products;
name          stock
------------  -----
rain jacket   12   
day pack      20   
trail hat     5    
fleece vest   8    
water bottle  30   
hiking socks  0
Only the day pack changes.

⌨ UPDATE without WHERE, on a copy

cp bayside.db practice_copy.db
sqlite3 practice_copy.db

sqlite> .mode column
sqlite> .headers on
sqlite> UPDATE products SET stock = 0;
sqlite> SELECT name, stock FROM products;
name          stock
------------  -----
rain jacket   0    
day pack      0    
trail hat     0    
fleece vest   0    
water bottle  0    
hiking socks  0
Every row changes, with no warning and no undo. That is why it is done on a copy. A new session starts with the display off, so turn it on again first.

⌨ Back in the practice database: INSERT, then a duplicate

sqlite3 bayside.db

sqlite> .mode column
sqlite> .headers on
sqlite> INSERT INTO products (name, price, stock) VALUES ('beach towel', 22.00, 15);
sqlite> SELECT * FROM products WHERE name = 'beach towel';
name         price  stock
-----------  -----  -----
beach towel  22.0   15   
sqlite> INSERT INTO products (name, price, stock) VALUES ('beach towel', 22.00, 15);
Runtime error: UNIQUE constraint failed: products.name (19)
Quit the copy and reopen bayside.db (display on again). The second INSERT fails: there is already a product with that name.

⌨ Reading the schema twice

sqlite> SELECT COUNT(*) FROM orders;
COUNT(*)
--------
6       
sqlite> DELETE FROM orders WHERE order_id = 'A105';
sqlite> SELECT COUNT(*) FROM orders;
COUNT(*)
--------
5       
sqlite> .read schema.sql
sqlite> SELECT COUNT(*) FROM orders;
COUNT(*)
--------
6
Six, five, six: the deleted sample row came back. Week 14 runs schema.sql on every start, which is why change_requests starts empty.
Section 5

Your Proposal

The checklist, the template, the starters.

The checklist, in short

  • One business; a chat for customers or staff; a Staff tab for staff
  • Two business tables plus change_requests
  • Two lookup tools and one change tool that only files requests
  • A handoff rule in code; one kind of data never stored
  • Instructions with “only state facts…”; five sample conversations
The full wording is on the starters page and in the reading. The instructor checks these eight items at sign-off.

Every section becomes code

  • Tables → schema.sql (Week 13)
  • Tools → tools.py; handoff → HANDOFF_WORDS; instructions → settings.py (Week 14)
  • Change tool → the Staff tab (Week 15)
  • Five conversations → evaluation.py (Week 16)
