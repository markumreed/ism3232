Write RequestManager

Say to the class (verbatim): "Five methods. Composition, in one line

Concept

def __init__(self): self.requests = [] — this is composition, in one line. self.requests is an attribute, exactly like Week 10's self.status — but instead of a string it holds a list, initially empty, that will come to hold actual BusinessRequest objects. A RequestManager doesn't inherit anything from BusinessRequest and shares no code with it — it simply has a list that contains instances of it.

add_request(self, request) — takes an already-created BusinessRequest object as a parameter and appends it. This method doesn't create a request; it receives one that already exists (Part 2 shows how) and adds it to the collection.

list_pending, get_by_status — list comprehensions filtering self.requests. Note r.status, not r['status'] — these are real objects with attributes, read with dot notation, not dictionaries with keys. The shape [r for r in collection if condition] is identical to Week 6; only the access syntax changed.

total_amount — sum(r.amount for r in self.requests), a generator expression, exactly Week 6's accumulator pattern, now summing an attribute across a collection of objects.

summary_report — calls self.list_pending() and self.get_by_status('Approved'): the manager calling its own other methods via self, reusing logic rather than duplicating it. print(f' {r}') uses Week 10's __repr__ automatically.

Line-by-line (guide, Part 1): - def __init__(self): self.requests = [] — this is composition, in one line. self.requests holds a list, initially empty, that will hold BusinessRequest objects. A RequestManager doesn't inherit from or share code with BusinessRequest; it simply has a list of its instances. - def add_request(self, request): — takes an already-created BusinessRequest (parameter named request, distinct from self) and appends it to self.requests. Doesn't create a new request itself. - list_pending, get_by_status — list comprehensions filtering self.requests; note r.status, not r['status'] — real objects with attributes, dot notation, not dictionary keys. Same comprehension shape as Week 6; only the item-access syntax changed. - total_amount — sum(r.amount for r in self.requests), a generator expression, exactly Week 6's test_accumulator pattern, now over an attribute across objects. - summary_report — calls self.list_pending() and self.get_by_status('Approved'): methods can call other methods on the same object via self, reusing logic. print(f' {r}') — r is a BusinessRequest; printed in an f-string it uses Week 10's __repr__ automatically. Common mistakes: using r['status'] (dictionary bracket access) out of Week 6 habit instead of r.status — raises TypeError: 'BusinessRequest' object is not subscriptable; forgetting self.requests = [] in __init__, or initializing it to something other than an empty list — every downstream method assumes it is a list. The two classes meet

Concept

from models import BusinessRequest, RequestManager — importing two names from the same module now, both classes side by side. The import line itself is a visible signal of the two-class design.

mgr.add_request(BusinessRequest(101, 'Taylor', 'Travel', 1200)) — read inside-out: BusinessRequest(...) creates a brand-new object first; that object, with no named variable of its own, is immediately passed into mgr.add_request(...), which appends it to mgr.requests. An object doesn't need its own name to be used immediately as an argument.

mgr.requests[0].approve() — a double access: mgr.requests gets the list, [0] indexes into it (the first request added, Taylor), .approve() calls a method on that specific object. This line reaches through the manager, into its held collection, to act on one request directly — no approve_first() method needed.

total_amount() counts every request; list_pending() is filtered to one status. They answer different questions over the same data — neither is "more correct".

Line-by-line (guide, Part 2): - from models import BusinessRequest, RequestManager — two classes imported side by side; the import line signals the two-class design. - mgr = RequestManager() — creates the initially-empty manager; no arguments, since __init__(self) takes none. - mgr.add_request(BusinessRequest(101, 'Taylor', 'Travel', 1200)) — read inside-out: the BusinessRequest is created first, then passed straight into add_request with no variable of its own. Concept

class TravelRequest(BusinessRequest): — the parentheses specify a parent class. TravelRequest is a BusinessRequest, inheriting everything it already has (approve(), reject(), __repr__, …) automatically, without redefining any of it.

super().__init__(request_id, requester, 'Travel', amount) — calls the parent's __init__ directly, running BusinessRequest's original constructor logic (setting request_id, requester, category hardcoded to 'Travel', amount, and the default status = 'Pending') — all without retyping those four lines.

self.destination = destination — a genuinely new attribute, specific to TravelRequest, that plain BusinessRequest objects don't have at all.

def requires_review(self): — this name already exists on the parent. Redefining it here overrides the inherited version for TravelRequest objects: their .requires_review() uses this $500 threshold, not BusinessRequest's $1,000 — while ordinary BusinessRequest objects keep using $1,000.
