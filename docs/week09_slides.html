Midterm Structure and Weighting

The Midterm Is a Project

  • At home, on your own computer
  • A project brief in Canvas: one business and its pricing rules
  • Turn the rules into a tested repository, the shape of Lab 7
  • Submit the GitHub URL, and nothing else
  • Open about a week · plan for 2 to 3 hours of work
The midterm is one at-home project worth 100 points. Each student gets a project brief in Canvas: one business and its pricing rules in plain English. They turn those rules into a small, tested Python project, the same shape as Lab 7, and submit the link to a public GitHub repository. The window is open about a week. The work itself is 2 to 3 hours and does not have to be done in one sitting. The project goes further than Lab 7: the rules have more parts, one function works through a list of records, and students write the tests themselves.

What You Build

  • business_rules.py — five functions
  • main.py — a report that matches the brief
  • tests/test_business_rules.py — 10+ tests you write
  • README.md — six sections
  • requirements.txt · .gitignore · tests/__init__.py
  • At least five commits, made as each part works
business_rules.py: five functions that carry out the brief's rules. Type hints, docstrings, named constants, return. No print(). main.py: imports the functions, loops over a list of records given in the brief, and prints a report that matches the brief line for line. tests/test_business_rules.py: at least 10 pytest tests the student writes, including the value on each side of a limit. README.md: six sections: title block, what the program does, the business rules, how to run, how to test, AI use statement. Suggested pace: set-up 15 minutes, functions 50, main.py 15, tests 40, README 15, with the ritual and commits throughout. These are not separately timed sections.

How the 100 Points Are Earned

  • Functions correct · 30 points
  • Tests you wrote · 20 points
  • Complete submission · 15 points
  • Commit history · 15 points
  • ruff · 10 points
  • README.md · 10 points
Functions correct · 30: the instructor's tests run against the student's functions, at ordinary values and at every limit. Functions are tested by name, so the names and parameter order must match the brief exactly. Tests you wrote · 20: at least 10 passing tests, every function covered, both sides of at least two limits. Complete submission · 15: every required file, a main.py whose output matches, and well-formed functions. Commit history · 15: at least five commits with descriptive messages, built in stages. ruff · 10: ruff format --check . and ruff check . both clean. README.md · 10: all six sections, correct commands, clean Markdown.

One of the five functions adds up a list of records. Its total must come from the student's own for loop. Do not use sum(), max(), min(), sorted(), or comprehensions. Say this out loud the week before the exam opens.

What Each Part Leans On

  • Functions: every parameter read · exact boundaries · tiers in one order · return, not print
  • Tests: the value at each limit and its neighbour · expected values worked out by hand
  • Project: exact file names · tests/__init__.py · output that matches line for line
  • Workflow: format, check, test · a commit each time a part works
Functions: every parameter the rule mentions is read. Boundary words are translated exactly: "or more" is >=, "below" is <. Tiers are checked in one order. return, not print. return after the loop, not inside it. Tests: the value exactly at each limit and the value next to it. Expected values worked out by hand from the rules. A list built inside the test. Names that say what is checked. Project: exact file names, tests/__init__.py, no .venv/ in the repository, output that matches line for line. Workflow: format, then check, then test. A commit each time a part works. A README whose commands actually run.
Section 3

Samples — Format Only

These show the format, not the difficulty. Each sample comes from the purchase-approval rules students know from Lab 7. The exam uses a business they have not seen, and its rules have more parts. The Study Guide works a full example, with seven bugs to find and a practice project at exam size.

⌨ Part 2 format — a business rule turned into a function

# Rule: a request of $1,000 or more goes to a director.
# A request of at least $500 goes to a manager, and so does
# any request from a department that is over budget.
# Everything else is approved automatically.
DIRECTOR_LIMIT = 1000.00
MANAGER_LIMIT = 500.00


def get_approver(amount: float, over_budget: bool = False) -> str:
    """Return who must approve a request."""
    if amount >= DIRECTOR_LIMIT:
        return "Director"
    elif amount >= MANAGER_LIMIT or over_budget:
        return "Manager"
    else:
        return "Automatic"
Read the rule aloud first. Ask which words set the limits and which sentence mentions the True/False input. Point out the order of the tiers, the named constants, the type hints and docstring, and that "and so does any request from a department that is over budget" becomes the or in the second test. Code label: Part 2 format — a business rule turned into a function

⌨ Part 4 format — tests on both sides of a limit

from business_rules import get_approver


def test_director_at_exactly_1000():
    assert get_approver(1000.00) == "Director"


def test_manager_one_cent_below_1000():
    assert get_approver(999.99) == "Manager"


def test_over_budget_small_request_goes_to_manager():
    assert get_approver(300.00, over_budget=True) == "Manager"
Two of these tests sit on either side of the $1,000 limit: one exactly at it and one a cent below. A wrong comparison shows up only at the limit. The third test shows the True/False input changing the answer. Ask the class what the fourth test should be: the $500 limit has two sides as well. Code label: Part 4 format — tests on both sides of a limit

⌨ Part 6 format — the ritual, then a commit that says what changed

# The ritual: all three must come back clean
ruff format .
ruff check .
pytest -v

# Then a commit whose message says what changed
git add .
git commit -m "Add approver function with boundary tests"
git push
The ritual comes before every push: format, then check, then test. All three must come back clean. ruff format changes layout only. ruff check finds mistakes such as unused imports and unsorted imports. Passing one says nothing about the other. The commit message is a verb and a thing. Messages such as final, update, or done earn nothing. Code label: Part 6 format — the ritual, then a commit that says what changed
