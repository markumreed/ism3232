Part 1 · 0:05–0:18

Verify Your Environment

Teaching goal: confirm the terminal itself is zsh (not bash), and that Python, Git, and the home directory are all correctly configured — before touching a single line of course content. Say to the class: "Open the VS Code integrated terminal. Look at the prompt character right now, before typing anything: if it ends in %, you're in zsh — correct. If it ends in $, you're in bash — stop, raise your hand, don't run anything else yet. This distinction matters because zsh and bash have real, different behaviors, and every script and alias this course teaches assumes zsh specifically."

The idea

Stop if this is wrong

Prompt ends in % → zsh → correct. Prompt ends in $ → bash → stop, raise your hand, run nothing else.

This isn't a cosmetic preference — every alias, function, and .zshrc configuration this course teaches from Week 3 on assumes zsh. A bash setup is a real compatibility problem, not a style difference.

Walk the room during Part 1 specifically — a wrong shell is the single highest-leverage thing to catch early. Fixing one student one-on-one now is far faster than untangling a Week-3 .zshrc mystery later. macOS (Catalina+) defaults to zsh; Windows students are on WSL or Git Bash per the precourse setup — confirm the course's specific Windows path.

Verify — run each on your own machine, read every line of output

echo $SHELL # Expected: /bin/zsh zsh --version # Expected: zsh 5.x or higher python3 --version # Expected: Python 3.10 or higher git --version # Expected: git version 2.x pwd # Expected: your home directory ls # Expected: Desktop Documents Downloads etc.

Shown for reference — version checks and $SHELL expansion can't run in the browser, so run these in the VS Code integrated terminal on your own machine. The next slide shows the shape of a correct result.

Line by line: - echo $SHELL — prints the SHELL environment variable: the shell your terminal is configured to launch. This checks configuration, not necessarily what's currently running. - zsh --version — confirms zsh itself is installed and reports a real version — a different check from the line above, since $SHELL could point somewhere zsh isn't installed on a broken setup. - python3 --version — same check as ISM2411's Module 02, framed here as step three of six. - git --version — confirms Git is installed; the course reaches Git formally in Week 4, but a broken install should surface today. - pwd — should print the home directory (e.g. /Users/yourname), the terminal's default starting location; establishes a known baseline before Part 2. - ls — should show the standard top-level folders (Desktop, Documents, ...); a sanity check that the home directory isn't unusual or corrupted.

Verified example output — check the pattern, not the exact numbers

/bin/zsh
zsh 5.9 (arm64-apple-darwin25.0)
Python 3.12.2
git version 2.51.2
/Users/yourname
Desktop Documents Downloads Library Movies Music Pictures Public

Exact values vary by machine. What matters: $SHELL is /bin/zsh, Python is 3.10+, Git is 2.x, and pwd shows your real home directory.

Reproduces the guide's "Verified example output" verbatim (guide Part 1). If echo $SHELL prints /bin/bash, stop that student before they proceed — walk them through chsh -s /bin/zsh on Mac, or the course's Windows/WSL guidance. Python below 3.10 or command not found → route to the precourse setup page, don't attempt a live install fix.

Knowledge check

You open the terminal and the prompt ends in $, not %. What should you do?

A $ prompt means bash. Every alias, function, and .zshrc configuration taught from Week 3 on assumes zsh specifically — this is a real compatibility requirement, not a cosmetic preference. Get the default shell fixed (chsh -s /bin/zsh on Mac, or the course's Windows path) before doing anything else.

Option C is a trap: typing zsh starts a subshell for this one session but leaves the default wrong, so the problem silently returns next time and .zshrc work later won't apply. The fix is changing the login shell.

Knowledge check

If your echo $SHELL had printed /bin/bash instead of /bin/zsh, what specifically would that mean for the rest of this course?

Every alias, function, and shell-specific syntax taught starting Week 3 — .zshrc configuration specifically — would not apply the same way, or at all, to a bash setup. This isn't a cosmetic preference, it's a real compatibility requirement.

Guide's Part 1 Check for understanding, verbatim answer. Get a student to say out loud that this is a compatibility requirement, not a preference.

Common pitfalls

Watch for

A $ prompt instead of % — stop this student before they proceed. Walking them through changing the default shell now, one-on-one, beats letting them continue into folder creation on the wrong shell.

python3 --version reporting below 3.10, or command not found entirely — route to the precourse setup page rather than a from-scratch install fix in front of the whole room.

Confusing the VS Code integrated terminal with a separate system Terminal app that may have different defaults — if a student's results look inconsistent with a neighbour's, confirm they're using the integrated terminal.

Part 2 · 0:18–0:35

Course Folder Structure

Teaching goal: build a complete, multi-module folder structure entirely from the terminal — the physical home for every remaining assignment this semester — and open it properly in VS Code as a workspace, not by double-clicking individual files. Say to the class: "Eight folders, one command. This structure is going to hold every assignment for the rest of the semester — get the names exactly right now, and you'll never think about 'where does this go' again."

The idea

Concept

mkdir takes many names at once — one command creates eight folders.

code . opens the current directory as a VS Code workspace. This is the correct way to start work on a project: open the whole folder, not double-click one file at a time. A proper workspace is what makes the file explorer, integrated terminal, and Git integration work together coherently.

The backslash (\) at the end of a line is a line continuation — "this command isn't finished, keep reading the next line as part of the same command." Purely a readability convenience for a long command; typing it all on one physical line works identically. The runnable block below uses the one-line form.

Live-code — build the structure, then open it as a workspace

cd ~ mkdir ism3232 cd ism3232 mkdir module01_setup module02_zsh module03_git_github module04_programming module05_functions module06_oop module07_final_project data screenshots ls code .

The guide writes the mkdir line with \ line continuations for readability; this runs it as one line — identical result. ls confirms all eight folders exist; code . opens ism3232/ as the workspace (the emulator prints a stand-in for the real VS Code window).

Line by line: - cd ~ — ~ is shorthand for the home directory: the same location pwd confirmed in Part 1. - mkdir ism3232 then cd ism3232 — create the course's top-level folder, then move inside it. - mkdir module01_setup module02_zsh ... data screenshots — creates eight folders at once, since mkdir accepts multiple names as separate arguments. - ls — confirms all eight folders now exist. - code . — opens the current directory (.) as a VS Code workspace. Open the whole folder as a workspace, not loose individual files — that's what keeps the explorer, terminal, and Git integration coherent.

Expected output

data  module01_setup  module02_zsh  module03_git_github  module04_programming  module05_functions  module06_oop  module07_final_project  screenshots
(VS Code would open: .)

ls lists the nine created folders (case-folded sort puts data first). In VS Code, the Explorer panel should show all eight module/data/screenshots subfolders nested under ism3232.

Verified against ism3232/assets/lab-shell.mjs: the seeded home plus the mkdir line produces exactly this ls output. On a real machine ls would show the folders in the same set; ordering matches a stock zsh ls.

Knowledge check

If you ran code . from inside module01_setup/ instead of from ism3232/, what would the VS Code Explorer show — and would that be wrong?

It would show only module01_setup/'s own contents as the workspace root, not the whole course structure — not strictly wrong for working on that one module in isolation, but a smaller, less useful view. code . opens whatever the current directory is as the workspace, not some fixed course-level location.

Guide's Part 2 Check for understanding, verbatim answer. The point is that code . resolves . to the current directory — there is no "course root" magic.

Common pitfalls

Watch for

Running mkdir from the wrong location (not inside ~/ism3232) — produces eight folders in the wrong place. Have students run pwd immediately before the mkdir line.

Misspelling a folder name (a stray underscore, a typo) — not an error, just a folder that won't match what future labs expect. Check the Explorer panel against the required eight names now — far easier than discovering it three weeks later when a lab's cd module02_zsh fails.

Defaulting to code filename.py later in the semester instead of code . once per project — the workspace-first habit established today is the one to reach for when starting a module's work.

Walk the room checking the Explorer panel against the exact eight names.
Part 3 · 0:35–0:58

First Python Script

Teaching goal: the complete write-save-run loop, in module01_setup/ specifically — plus a required comment-block reflection asking students to explain, in their own words, what actually happened when the script ran. Say to the class: "First real script. I want you to type every character — not copy-paste — because the muscle memory of typing Python, including the mistakes you'll inevitably make and fix, is itself part of learning to code. Then, once it runs, you're going to answer four questions about why it worked, in a comment block. This is not busywork — if you can't answer these four questions, you don't yet understand what just happened, even if the script ran."

Live-code — create the file, open it in the workspace

cd ~/ism3232/module01_setup touch hello_ism3232.py code hello_ism3232.py ls

touch creates the empty file; code opens it inside the already-open workspace from Part 2; ls confirms it exists.

- touch hello_ism3232.py — creates an empty file with that exact name (touch's original purpose was updating a timestamp; creating a new empty file is a well-known side effect). - code hello_ism3232.py — opens that specific file in VS Code, inside the workspace from Part 2.

Type this into the file — type it, do not paste

# hello_ism3232.py # ISM3232 - Business Application Development # Author: [Your Name] print('Hello, ISM3232!') course_name = 'Business Application Development' credit_hours = 3 weekly_hours = credit_hours * 2 print(f'Course: {course_name}') print(f'Expected weekly hours: {weekly_hours}') print('Environment verified. Week 1 complete.')

On your machine you would save with ⌘S / Ctrl+S and run python3 hello_ism3232.py in the terminal. Here, press Run to execute it in the browser.

Line by line: - The header comment block — a file-identification convention worth establishing from the first script: any reader can see what this file is and who wrote it without reading code. - print('Hello, ISM3232!') — single quotes, not double. Python treats single and double quotes identically for defining a string; this is purely a style choice, and this course's materials consistently use single quotes. Consistency within a codebase is itself a professional habit. - course_name = '...' — the extra spaces before = align it with the two lines below: a manual alignment style choice (echoing ISM2411 Module 03's aligned print labels), purely cosmetic. - credit_hours = 3 — an int. - weekly_hours = credit_hours * 2 — a derived value: the "compute once, store in a named variable" pattern, modeling a course-planning calculation. - The three final print() calls, two of them f-strings — nothing new syntactically for students with prior Python exposure.

Verified output

Hello, ISM3232!
Course: Business Application Development
Expected weekly hours: 6
Environment verified. Week 1 complete.

Matches the guide's "Verified output" for Part 3. On your machine this appears in the terminal, not the editor pane.

Verified with CPython 3.12.2 (the version Pyodide 0.26.4 bundles). weekly_hours = credit_hours * 2 = 6.

Required reflection — answer it, don't guess

# --- What happened when I ran this script? ---
# 1. The shell found the python3 interpreter at: ___
# 2. Python read the file from top to bottom: True / False
# 3. The f-string on line 11 evaluated {weekly_hours} to: ___
# 4. The output appeared in: the editor / the terminal / both

Add this comment block below the header and fill it in from real checks — not guesses.

Model strong answers: 1. Run which python3 right now, live, and use its actual output — a real, checkable fact about this machine, not a guess. (which reports the full path a bare command name resolves to.) 2. True — Python executes a script's statements top to bottom. Prove it to a skeptic: reorder two print() lines, re-run, watch the output order change. 3. 6 — credit_hours * 2 with credit_hours = 3. 4. The terminal — the editor pane shows the source code; the integrated terminal is where print()'s output appears. Editing and running produce output in two visually separate places in the same VS Code window.

Knowledge check

You move hello_ism3232.py to module02_zsh/ but keep running python3 hello_ism3232.py from inside module01_setup/. What happens?

python3: can't open file 'hello_ism3232.py': No such file or directory — the classic "wrong directory" failure. python3 hello_ism3232.py looks for the file relative to where you are now, and it's no longer there.

Guide's Part 3 Check for understanding. Same "wrong directory" failure mode covered at length in the ISM2411 terminal modules; a check that this error type is recognizable even in a brand-new course.

Common pitfalls

Watch for

Copy-pasting despite the explicit "type it" instruction — restate the why: typing builds the muscle memory of noticing your own typos, which pasting bypasses.

Answering the reflection with guesses rather than checking — e.g. guessing a plausible path for question 1 instead of running which python3. Walk the room confirming question 1's answer matches a live which python3 on that student's machine.

Running the script from the wrong directory — a quick pwd check if python3 hello_ism3232.py reports "No such file or directory".

The reflection is the actual learning artifact here — a script that runs but can't be explained means the concept hasn't landed yet.

Stretch · 1:10–1:15

Configure Git Identity

Frame as a quick, required-for-later two-command task, not optional depth: "This is a one-time setup, and Week 4's first-ever git commit will fail without it — doing it now, while it's fresh and low-stakes, saves a confusing moment later. --global means this identity applies to every Git repository on this machine, not just this course's, so use your real name and an email you're comfortable having attached to your commit history — many students use their GitHub account's email specifically, since that's what will show up on their public commit history there."

One-time Git identity — run on your own machine

git config --global user.name 'Your Name' git config --global user.email 'you@email.com' git config --global --list

Shown for reference — git can't run in the browser. The last line prints back what you just set, so you can confirm it took.

Week 4's first git commit fails without this. --global = every repo on the machine.

Illustrative result — not run here

user.name=Your Name
user.email=you@email.com

git config --global --list echoes back the identity you just configured (plus any other global settings already on the machine). Screenshot this for your own records — Week 4 depends on it.

Shows the two lines the Stretch's --list is meant to confirm. A real machine may also list init.defaultbranch, core.editor, etc. depending on prior setup.
