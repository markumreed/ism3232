Setup and All Four Data Types

Teaching goal: a fresh project setup (new venv, new .gitignore) in a new folder, and the four core Python types — str, int, float, bool — confirmed with type(). Say to the class (verbatim): "New module, new folder, new venv — this is genuinely a fresh project, not a continuation of Week 4's. Set it up the same way, every time, from muscle memory now." Check for understanding (asked at the end of this part): "If I asked for is_over_limit to check whether the order needs approval at a $2,000 threshold instead of $1,000, what's the one-character change?" Answer: change 1000 to 2000 — a quick confirmation that students can read and modify the comparison, not just recognize it.

The idea

Concept

Every value in Python has a type, and the type determines behavior. Today's four: str (text in quotes), int (whole number, no decimal), float (has a decimal point — even .00), bool (exactly True or False).

type(value) is how you ask Python what it thinks a value is; it prints as <class 'str'> — that display format is just Python's way of saying "the string type."

unit_price * quantity > 1000 reads with order of operations: * binds tighter than >, so it computes (unit_price * quantity) > 1000 → 1350.0 > 1000 → True, a bool.

Ask the room to confirm is_over_limit is True before running it, not after — 450.00 * 3 = 1350.0, and 1350.0 > 1000 is True. print() accepts any number of comma-separated arguments and prints them all on one line, space-separated — new relative to one-type-per-line patterns.

Operators and f-strings

Teaching goal: derived business calculations (subtotal, tax, total) and a fully formatted, multi-line business summary using f-strings. Say to the class (verbatim): "Three more calculated values, then a clean, formatted printout — this is what a real business script's output should look like, not just raw numbers." Check for understanding (asked at the end of this part): "If subtotal were exactly $1000.00, would requires_approval be True or False, given tax is added on top?" Answer: True — $1000.00 + 7% tax pushes the total to $1070.00, over the $1000 threshold, even though the subtotal alone sits exactly at the boundary; requires_approval checks the post-tax total specifically.

The idea

Concept

subtotal → tax → total are chained arithmetic: each derived value feeds the next. requires_approval = total > 1000 is a second, independently-computed boolean, distinct from Part 1's is_over_limit (a different threshold check on the pre-tax amount) — the two could, in principle, disagree.

:.2f on every dollar amount is the currency format spec, consistent across all three lines. Printing a bool directly in an f-string displays the literal word True or False — no special handling.

Flag now for Part 4: subtotal * 0.07 does not always produce a perfectly clean decimal in floating-point arithmetic, even though the math looks simple on paper. Hold that thought.

The tax line is a deliberate foreshadow of Part 4's Bug 1 — 0.07 cannot be represented exactly in binary floating-point. Don't unpack it here; just plant the flag so it pays off in Part 4.

User Input with Type Conversion

Teaching goal: input() always returns a string — convert with int() before arithmetic, or hit a genuinely instructive TypeError. Say to the class (verbatim): "One line of new user-facing input, and I want to show you the single most common Week 5 bug on purpose, before it happens to you by accident." Check for understanding (asked at the end of this part): "Why does the error say 'can't multiply sequence' — what does Python mean by calling a string a 'sequence' here?" Answer: a string is one specific kind of Python sequence — an ordered collection of characters — and sequences in general support multiplication-as-repetition by an integer; the error is using that general vocabulary, not something specific to strings alone.

The idea

Concept

int(input('Enter a new quantity: ')) reads inside-out: input(...) displays the prompt and returns whatever was typed, as a string, always — int(...) then converts that string to a genuine integer.

unit_price * user_qty * 1.07 applies the 7% tax inline in one step — a more compact style than Part 2's separate subtotal / tax / total variables. Both are valid; this one is terser, Part 2's is more explicit about each intermediate value.

Read int(input(...)) inside-out, the same pattern as prior modules. Quantity specifically calls for int() rather than float() — a fractional number of laptops doesn't make business sense.

Live-code — Part 3: input() with int() conversion

product_name = 'Laptop' quantity = 3 unit_price = 450.00 user_qty = int(input('Enter a new quantity: ')) new_total = unit_price * user_qty * 1.07 print(f'New total for {user_qty} units: ${new_total:.2f}') print(f'Requires approval: {new_total > 1000}')

The stdin box is pre-filled with 5 — the answer to the one input() prompt. Run it: 450.00 * 5 * 1.07 = 2407.5 → $2407.50.

Line by line: - int(input('Enter a new quantity: ')) — input(...) displays the prompt and returns what was typed, as a string, always; int(...) converts that string to a genuine integer. - unit_price * user_qty * 1.07 — an equivalent, more compact way of computing a taxed total than Part 2's separate variables: multiplying by 1.07 directly applies the 7% tax inline. Both styles are valid — a real style tradeoff, not a correctness difference. - new_total > 1000 evaluated inside the f-string braces — displays True / False directly. Common mistakes: converting with float() instead of int() for a quantity (runs, but prints 5.0 not 5); entering non-numeric text like five → ValueError: invalid literal for int() with base 10: 'five', a different error from the multiplication TypeError on the next slide. Check for understanding: "what does Python mean by calling a string a 'sequence'?" Answer: a string is an ordered collection of characters — a kind of sequence — and sequences support repetition by an integer, so the error uses that general vocabulary.

Now the bug on purpose — "the most common Week 5 bug"

Bug 1 — floating-point equality: print the actual value

print(200.00 * 0.07)

test_tax_at_seven_percent asserts tax == 14.0. Run this to see what tax really is.

Explain (verbatim): "0.07 cannot be represented exactly in binary floating-point — the same limitation behind nearly every 'why doesn't my decimal math come out exactly right' surprise in any programming language, not just Python. tax really is 14.000000000000002, not 14.0 — so tax == 14.0 is, correctly, False. This is not a bug in Python; it's an inherent property of how computers represent most decimal fractions in binary. The fix: never compare floats with == when you expect a computed decimal result — use a tolerance-based comparison instead." This is a bare print(x) of a raw float — the output is the exact repr, not a rounded display; that rawness is the whole point.

Output

14.000000000000002

Reproduces the guide's stated output exactly. tax is 14.000000000000002, not 14.0 — so tax == 14.0 is, correctly, False, and the test fails for a genuinely real reason.

Verified against python3 3.12.2: print(200.00 * 0.07) emits exactly 14.000000000000002. Raw print() of a float shows its full repr — no rounding — which is exactly why == against 14.0 fails. (Part 2's 1350.0 * 0.07 happened to land on 94.5 exactly; 200.00 * 0.07 does not — the value matters, which is why == on computed floats is unreliable in general.)

Bug 1 fix — tolerance-based comparison

import math subtotal = 200.00 tax = subtotal * 0.07 print(math.isclose(tax, 14.0))

The corrected test body: assert math.isclose(tax, 14.0) instead of assert tax == 14.0.

math.isclose(a, b) returns True when a and b are within a small relative tolerance — the general, robust pattern for comparing computed decimals. Also accept, if a student proposes it: tax = round(subtotal * 0.07, 2) then assert tax == 14.0 — this works for this specific case, but flag that math.isclose() doesn't depend on the numbers happening to round cleanly.

Output

True

math.isclose(14.000000000000002, 14.0) is True — the corrected assertion passes.

Verified against python3 3.12.2: the block prints True. Under pytest the corrected test_tax_at_seven_percent then passes.

Bug 2 — chained comparison: print the raw expression

print(1500 > 1000 is True)

test_over_limit_true asserts exactly this expression. It looks like it should ask "is 1500 > 1000 equal to True" — run it and see.

Explain slowly (verbatim): "This looks like it should ask 'is 1500 > 1000 equal to True' — but Python doesn't read it that way. Python supports chained comparisons: a > b is c is actually evaluated as a > b and b is c — comparing b on both sides at once, not evaluating a > b first and then comparing that result against c. So 1500 > 1000 is True really means 1500 > 1000 and 1000 is True — and 1000 is True is False (an integer is never identical to the boolean True, even though 1000 is 'truthy' — is checks genuine identity, not truthiness). True and False is False — exactly the failing result we saw." Point out: Python itself prints a SyntaxWarning: "is" with 'int' literal.
