Section 1

What Problem Does a Class Solve?

Until now data and functions lived apart. A chatbot has data that belongs together (name, instructions, history) and actions that work on it (respond). A class keeps both in one place.

Data in one place, functions in another

  • A chatbot has a name, instructions, and a conversation history.
  • It also has actions: respond to a message.
  • A class keeps that data and those actions together.
  • Class = the template. Object = one real chatbot made from it.
  • A class organizes code. It does not make anything intelligent.
Ask: where did the data live in Lab 6? In a list of dictionaries. Where did the logic live? In functions. Nothing tied them together. You could build today's chatbot with functions and one shared dictionary. The reading shows that version. It works, and it gets awkward when you want two chatbots or want to plug in a tool. Misconception to pre-empt: students often think 'class' is the advanced, smart way. It is one way to organize code.

Section 2

Step 1 — A Class That Stores Data

⌨ Step 1 — write together, line by line

class SupportChatbot:
    """A support chatbot. Step 1: it only stores data."""

    def __init__(self, name, instructions):
        self.name = name
        self.instructions = instructions
        self.history = []


bot = SupportChatbot("Sunny", "You are a friendly support assistant.")
print(bot.name)
print(bot.instructions)
print(bot.history)

# Output:
# Sunny
# You are a friendly support assistant.
# []
Walk through each line. Students type along. Do not rush. class SupportChatbot: starts the template. Nothing exists yet. def __init__(self, name, instructions): the setup method. Never called by name. self.name = name: right side is a parameter that disappears; left side is an attribute that stays. self.history = []: not a parameter, every conversation starts empty. bot = SupportChatbot(...): two values passed, three parameters. Python supplies self.

Four things to notice

  • __init__ runs by itself when you write SupportChatbot(...).
  • You pass two values. The method has three parameters. Python fills in self.
  • self.name is an attribute. It stays on the object.
  • bot.name reads the name that belongs to this object.
Cold-call check: 'In bot = SupportChatbot("Sunny", "..."), which is the class and which is the object?' Class: SupportChatbot. Object: bot.
Section 3

Step 2 — A Method That Responds

⌨ Step 2 — add two methods

class SupportChatbot:
    """A support chatbot. Step 2: it can respond and remember."""

    def __init__(self, name, instructions):
        self.name = name
        self.instructions = instructions
        self.history = []

    def respond(self, user_message):
        self.history.append({"role": "user", "content": user_message})
        reply = self.choose_reply(user_message)
        self.history.append({"role": "assistant", "content": reply})
        return reply

    def choose_reply(self, user_message):
        text = user_message.lower()
        if "hello" in text:
            return f"Hello! I'm {self.name}."
        return "I'm not sure how to help with that."
respond does three things in a fixed order: record the user's message, get a reply, record the reply. Every chatbot this term keeps that shape. self.choose_reply(...) is one method calling another on the same object. choose_reply is the mock. It is two rules. Next week a model replaces it. .lower() makes a lowercase copy so Hello and hello match the same rule.

⌨ Step 2 — use it

bot = SupportChatbot("Sunny", "You are a friendly support assistant.")
print(bot.respond("Hello there"))
print(bot.respond("Where is my order?"))
print(len(bot.history))
print(bot.history[0])

# Output:
# Hello! I'm Sunny.
# I'm not sure how to help with that.
# 4
# {'role': 'user', 'content': 'Hello there'}
Two messages produce four history entries: two from the user, two from the chatbot. Each entry is a dictionary with a role and a content. Real AI services expect this same shape, which is why we use it now.
Section 4

Step 3 — A Separate Tool

Looking up an order is a different job from holding a conversation. Give it its own class. In agent programs a tool is code the chatbot can use to get information or do something.

⌨ Step 3 — a class with a different job

class OrderLookup:
    """A tool that knows about orders. It knows nothing about chatting."""

    def __init__(self, orders):
        self.orders = orders

    def find_order_id(self, text):
        for order_id in self.orders:
            if order_id in text.upper():
                return order_id
        return None

    def find_status(self, order_id):
        if order_id in self.orders:
            return self.orders[order_id]
        return None
Nothing here mentions chatting. The tool knows orders and that is all. find_order_id returns None when no known order ID is in the text. None is the tool saying it has no answer. text.upper() makes an uppercase copy so a100 matches A100.

⌨ Step 3 — try the tool on its own

order_tool = OrderLookup({"A100": "shipped", "A101": "processing"})
print(order_tool.find_order_id("Where is order a100?"))
print(order_tool.find_status("A100"))
print(order_tool.find_order_id("Where is my order?"))
print(order_tool.find_status("A999"))

# Output:
# A100
# shipped
# None
# None
The tool runs with no chatbot at all. That is the point of keeping it separate: you can test it, reuse it, or replace it.
Section 5

Step 4 — Composition

Composition means giving one object another object to use. The chatbot has a tool.

⌨ Step 4 — the chatbot is handed the tool

    def __init__(self, name, instructions, order_tool):
        """Set up one chatbot with its own name, instructions, tool, and history."""
        self.name = name
        self.instructions = instructions
        self.order_tool = order_tool
        self.history = []

    def order_reply(self, user_message):
        """Use the order tool to answer a question about an order."""
        order_id = self.order_tool.find_order_id(user_message)
        if order_id is None:
            return "Which order? Please send an order ID like A100."
        status = self.order_tool.find_status(order_id)
        return f"Order {order_id} is {status}."
self.order_tool = order_tool is the whole idea. self.order_tool.find_order_id(...) reads left to right: this chatbot's tool, its find_order_id method. if order_id is None: handles a failed lookup. The chatbot asks for a valid ID. It does not guess.

⌨ Step 4 — create the tool first, then hand it over

order_tool = OrderLookup({"A100": "shipped", "A101": "processing"})
bot = SupportChatbot("Sunny", "You are a friendly support assistant.", order_tool)

print(bot.respond("hello"))
print(bot.respond("Where is order A100?"))
print(bot.respond("Where is my order?"))
print(bot.respond("Please change my shipping address"))
print(bot.respond("What is the weather today?"))

# Output:
# Hello! I'm Sunny. I can check an order status for you.
# Order A100 is shipped.
# Which order? Please send an order ID like A100.
# I can't help with that here. I'm passing you to a human agent.
# I'm not sure how to help with that. I can check an order status.
The chatbot never creates its own tool. That lets a test hand it a small one. Point at reply four: an address change goes to a human. The handoff rule is checked before the order rule.

Section 6

Trace One Message

Where is order A100?

  • bot.respond(...) runs with self set to bot.
  • The message is appended to self.history.
  • choose_reply checks its rules and reaches the order rule.
  • order_reply asks the tool for an ID, then for its status.
  • The sentence travels back up, is recorded, and is returned.
Have a student narrate the path while you point at the code. Tracing is learning outcome 7. Proof to show after: the history is empty before the call and holds two dictionaries after it.

Section 7

Two Objects, One Class

⌨ Two chatbots

order_tool = OrderLookup({"A100": "shipped", "A101": "processing"})
sunny = SupportChatbot("Sunny", "You are cheerful and brief.", order_tool)
river = SupportChatbot("River", "You are formal and detailed.", order_tool)

sunny.respond("hello")
sunny.respond("Where is order A100?")
river.respond("hello")

print(sunny.name, len(sunny.history))
print(river.name, len(river.history))
print(sunny.history[1]["content"])
print(river.history[1]["content"])

# Output:
# Sunny 4
# River 2
# Hello! I'm Sunny. I can check an order status for you.
# Hello! I'm River. I can check an order status for you.
Sunny has four messages and River has two. self.history = [] ran once per object. Both share one order_tool. That is allowed: one tool can serve many chatbots. Predict question: move history = [] into the class body, outside __init__. Send a message to Sunny only. How long is River's history? Answer: 1. A value in the class body is shared by every object. In a real chatbot that leaks one customer's conversation to another.
Section 8

What a Business Chatbot Can Get Wrong

Four risks

  • Unreliable output. Cardigans contains card. Rules are brittle; models are wrong in less predictable ways.
  • Failed tools. The order may not exist. Ask for a valid ID. Never invent a status.
  • Sensitive data. The history keeps everything a user types.
  • Actions that need a person. Looking up changes nothing. Changing an address does.
Discussion 1: How would you find mistakes like the cardigan one before a customer does? Look for: test with real messages. Discussion 2: Name three more tools a shop's chatbot could use. Which only look something up, and which change something? Discussion 3: If you saved every conversation to a file, what in that file should worry you?

Essential, optional, left out

  • Essential: class, object, attribute, method, __init__, self, composition, tracing.
  • Optional: the functions version, the real-model preview, the second tool.
  • Left out on purpose: inheritance, abstract classes, decorators, metaclasses, design patterns.
A chatbot with a tool needs 'has a', not 'is a kind of'. That is why inheritance is not in this module. Where this goes next: a local model replaces choose_reply (Week 11); the model decides when to use order_tool (Week 12); error handling grows from the None check; human approval grows from the handoff rule; evaluation grows from this week's tests.
