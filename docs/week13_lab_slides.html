Part 3

Four SQL exercises

Same window, in order.

Exercise 1 — Orders still processing

Try it

Order ID and customer of every processing order, sorted by customer.

Give students five minutes before showing the answer.

Exercise 1 — Orders still processing: answer

SELECT order_id, customer FROM orders WHERE status = 'processing' ORDER BY customer;

Then the output on the next slide.

Ask a student to read the query aloud before you reveal the output.

Exercise 1 — Orders still processing: output

sqlite> SELECT order_id, customer FROM orders WHERE status = 'processing'
    ORDER BY customer;
order_id  customer  
--------  ----------
A103      Ana Silva 
A101      Sam Okafor

Compare with the expected box on the lab page.

Common mistakes: missing quotes around text values; comparing stock with '0'.

Exercise 2 — Out of stock

Try it

Name and price of every product with no stock.

Give students five minutes before showing the answer.

Exercise 2 — Out of stock: answer

SELECT name, price FROM products WHERE stock = 0;

Then the output on the next slide.

Ask a student to read the query aloud before you reveal the output.

Exercise 2 — Out of stock: output

name          price
------------  -----
day pack      45.0

Compare with the expected box on the lab page.

Exercise 3 — Orders by status

Try it

First add order A106 (given on the lab page), then count orders in each status.

Give students five minutes before showing the answer.

Exercise 3 — first add this order

INSERT INTO orders (order_id, customer, item, status, address) VALUES ('A106', 'Kai Moreno', 'trail hat', 'processing', '5 Shell Road');

An INSERT prints nothing.

This makes the counts unequal, so a wrong query cannot match by luck.

Exercise 3 — Orders by status: answer

SELECT status, COUNT(*) FROM orders GROUP BY status;

Then the output on the next slide.

Ask a student to read the query aloud before you reveal the output.

Exercise 3 — Orders by status: output

sqlite> SELECT status, COUNT(*) FROM orders GROUP BY status;
status      COUNT(*)
----------  --------
delivered   2       
processing  3       
shipped     2

Compare with the expected box on the lab page.

Common mistakes: missing quotes around text values; comparing stock with '0'.

Exercise 4 — Approve a change by hand

Try it

Type the request the agent filed (on the lab page).

Write two UPDATEs: change A101’s address to 9 Pine Street, Tampa, and mark request 1 approved.

Check with the two SELECTs on the lab page.

This is the SQL approve_request runs in Week 14. Let them struggle a little.

Exercise 4 — the request the agent filed

INSERT INTO change_requests (order_id, new_address) VALUES ('A101', '9 Pine Street, Tampa');

Typed twice? Then there is a request 2 as well; approve request 1.

AUTOINCREMENT gives every insert a new number.

Exercise 4: answer

UPDATE orders SET address = '9 Pine Street, Tampa' WHERE order_id = 'A101'; UPDATE change_requests SET status = 'approved' WHERE number = 1;

Each UPDATE has a WHERE, so exactly one row changes.

In Week 14 these two statements become approve_request.

Exercise 4: check

sqlite> SELECT order_id, address FROM orders WHERE order_id = 'A101';
order_id  address             
--------  --------------------
A101      9 Pine Street, Tampa
sqlite> SELECT number, order_id, status FROM change_requests;
number  order_id  status  
------  --------  --------
1       A101      approved

A101 has the new address; request 1 is approved.

If the address did not change, the WHERE did not match: check the quotes and the ID.

Part 5

Choose a business, write PROPOSAL.md

The longest part.

The checklist

Sign-off checks these eight items

1. One business. The chat serves customers or staff; the Staff tab always serves staff.

2. At least two business tables plus a change_requests table.

3. At least two lookup tools. They only read, and they check their arguments.

4. At least one change tool. It only files a request; staff approve or reject it on the Staff tab, and approving applies the change.

5. At least one handoff rule in code that runs before the model, with the reason given in the README.

6. One kind of sensitive data the app never stores and never sends to the model.

7. Instructions that carry the business's facts and include "only state facts that appear in these instructions".

8. Five sample conversations, which become the Week 16 evaluation cases.

Starters or their own idea; the checklist is the same.

Every section becomes code

The template’s arrows

Tables → schema.sql today

Tools, handoff words, instructions → Week 14

Change tool → the Staff tab, Week 15

Five conversations → evaluation cases, Week 16

At sign-off, ask: what will you put in tools.py for this section?
Part 6

Write and check schema.sql

Read it twice.

Check your schema

sqlite3 my_business.db .read schema.sql .tables SELECT COUNT(*) FROM <table>; .read schema.sql SELECT COUNT(*) FROM <table>; .quit

Use your business’s name and your own table names.

The counts after the second .read must match the first.

What Bayside’s check looks like

sqlite> SELECT COUNT(*) FROM orders;
COUNT(*)
--------
6       
sqlite> DELETE FROM orders WHERE order_id = 'A105';
sqlite> SELECT COUNT(*) FROM orders;
COUNT(*)
--------
5       
sqlite> .read schema.sql
sqlite> SELECT COUNT(*) FROM orders;
COUNT(*)
--------
6

Six, five after a DELETE, six again.

A deleted sample row comes back; that is INSERT OR IGNORE doing its job.

Matching counts are not enough

SQLite version 3.45.1 2024-01-30 16:01:20
Enter ".help" for usage hints.
sqlite> .read plain_insert.sql
sqlite> SELECT COUNT(*) FROM orders;
6
sqlite> .read plain_insert.sql
Runtime error near line 25: UNIQUE constraint failed: orders.order_id (19)
Runtime error near line 33: UNIQUE constraint failed: products.name (19)
sqlite> SELECT COUNT(*) FROM orders;
6

The counts match, but the second .read printed errors: an INSERT is missing OR IGNORE.

Bayside's schema with every OR IGNORE removed. Week 14's app runs schema.sql on every start, so this error would stop it on every start after the first. The check passes only when the second .read prints nothing.

change_requests starts empty

Watch for

AUTOINCREMENT gives every insert a new number, so INSERT OR IGNORE never sees a repeat.

Sample requests would be added again on every start.

Show requests_twice from the reading if a student asks why.
