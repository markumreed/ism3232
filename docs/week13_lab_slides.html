CREATE TABLE — static this week, real sqlite3 in Week 14

-- Create a table
CREATE TABLE requests (
    id        INTEGER PRIMARY KEY AUTOINCREMENT,
    requester TEXT    NOT NULL,
    category  TEXT    NOT NULL,
    amount    REAL,
    status    TEXT    DEFAULT 'Pending'
);

Shown static, outside any runnable block — this is the conceptual SQL week. In class, run sqlite3 lab13.db first, then type this at the shell. Week 14 runs it for real.

Line-by-line (guide, Part 2): - CREATE TABLE requests (...) — say explicitly, direct callback to Week 11 Part 3's mapping table: this line is the SQL equivalent of class BusinessRequest: — a fixed blueprint for what every row will contain. - id INTEGER PRIMARY KEY AUTOINCREMENT — INTEGER is the column's type; PRIMARY KEY marks this column as the unique identifier for every row (no two rows can share an id); AUTOINCREMENT means SQLite assigns the next number automatically — you never manually specify id when inserting. - requester TEXT NOT NULL — NOT NULL is a constraint: SQLite will refuse to insert a row missing this value. SQL's version of a required field — Python's equivalent would be a parameter with no default value in __init__. - amount REAL — no NOT NULL here, deliberately — this column is allowed to be empty (a NULL value), unlike requester/category. - status TEXT DEFAULT 'Pending' — direct SQL equivalent of Week 10's self.status = 'Pending' in __init__ — a value automatically applied when a row is inserted without explicitly specifying status. Reproduced verbatim from the guide's Part 2.

Design Your Capstone Schema

Teaching goal: write schema.sql for the student's own approved capstone proposal, and test it directly in the sqlite3 shell. Say to the class (verbatim): "Now your own tables, from your own proposal's 'SQL Tables' section. Real types, NOT NULL where it matters, a status column with a default — exactly the pattern from Part 2, applied to your own domain." Do: touch schema.sql && code schema.sql. The one genuinely new element this part introduces is the FOREIGN KEY — SQL's mechanism for expressing the relationship Week 11's Registration.event attribute expressed in Python. Check for understanding (asked at the end of this part): "Why does registrations store event_id (a number) rather than the event's actual name?" Answer: storing just the ID and looking up the name via the relationship avoids duplicating the event's name in every single registration row — if the event were ever renamed, only one row in events needs updating, not every related registration. A genuine, important database design principle — avoiding redundant, duplicated data.

The one new element — FOREIGN KEY

Concept

FOREIGN KEY (event_id) REFERENCES events(event_id) — this is SQL's mechanism for expressing exactly the relationship Week 11's Registration.event attribute expressed in Python (one Registration object holding a reference to a specific Event object).

In SQL, a table can't hold a whole other row inside a cell the way a Python attribute can hold a whole other object — instead, registrations.event_id holds just the id of the related events row, and FOREIGN KEY formally declares that relationship, letting the database enforce it (refusing to insert a registration whose event_id doesn't correspond to a real event).

That enforcement isn't automatic in SQLite by default — a detail beyond today's required depth, but worth a one-sentence flag if a curious student asks why an invalid event_id doesn't immediately error.

Everything else in the schema — types, NOT NULL, a status column with a DEFAULT — is exactly the Part 2 pattern, now applied to the student's own domain.

Line-by-line (guide, Part 3): FOREIGN KEY (event_id) REFERENCES events(event_id) — say explicitly, this is SQL's mechanism for expressing exactly the relationship Week 11's Registration.event attribute expressed in Python. registrations.event_id holds just the id of the related events row; FOREIGN KEY formally declares the relationship, letting the database enforce it — refusing to insert a registration whose event_id doesn't correspond to a real event, if foreign key enforcement is turned on (it isn't automatic in SQLite by default).

schema.sql — the instructor's prepared model (continuing GalaTrack)

-- schema.sql
CREATE TABLE events (
    event_id  INTEGER PRIMARY KEY AUTOINCREMENT,
    name      TEXT    NOT NULL,
    capacity  INTEGER NOT NULL
);

CREATE TABLE registrations (
    reg_id         INTEGER PRIMARY KEY AUTOINCREMENT,
    attendee_name  TEXT    NOT NULL,
    event_id       INTEGER NOT NULL,
    price          REAL    NOT NULL,
    status         TEXT    DEFAULT 'Pending',
    FOREIGN KEY (event_id) REFERENCES events(event_id)
);

Common student mistakes

Watch for

Using a type name that doesn't exist in SQLite (e.g., VARCHAR(50), common in other database systems) — SQLite is famously permissive about types (it will often accept this without error, due to "type affinity" rather than strict typing), but steer students toward SQLite's own core type names (TEXT, INTEGER, REAL) for clarity and consistency with Part 2.

Forgetting NOT NULL on columns that clearly should always have a value (an attendee's name, an event's name) — walk each student's schema checking this against their own proposal's described records.

A FOREIGN KEY line referencing a table or column name that doesn't exactly match the other CREATE TABLE statement (a typo) — SQLite may not immediately error on this depending on settings, so a careful read-through, not just a successful .read, is the real check.

CREATE TABLE   -- define a table
